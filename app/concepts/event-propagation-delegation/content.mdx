## 동작 원리

버튼 안에 별(★) 아이콘을 `span`으로 넣고 버튼에 클릭 리스너를 달았다고 해 봅시다. 아이콘을 누르면 리스너가 실행되는데, 그 안에서 `event.target`을 읽으면 버튼이 아니라 아이콘 `span`입니다. 리스너를 단 요소는 버튼인데 왜 `target`은 버튼이 아닐까요? 이 페이지는 이벤트가 문서 트리를 어떤 순서로 지나가는지, `target`과 `currentTarget`이 각각 무엇을 가리키는지, 이 규칙을 이용해 상위 요소 하나로 여러 요소의 이벤트를 처리하는 이벤트 위임이 어떻게 동작하는지 확인합니다. 이벤트 전파는 ECMAScript가 아니라 호스트(브라우저)의 동작이며, 규칙은 WHATWG DOM 표준과 WHATWG HTML 표준이 정하고 `focus`와 `focusin`의 버블링 여부는 W3C UI Events 명세가 정합니다. 예제의 출력은 모두 테스트가 Chromium에서 실제로 열어 `console.log` 출력을 모은 값이며, 다른 브라우저는 이 페이지에서 확인하지 않았습니다. 예제의 이벤트는 사용자가 실제로 누르는 대신 `click()`이나 `dispatchEvent`로 만들기 때문에 `isTrusted`가 `false`이지만, 이 페이지에서 다루는 경로와 두 번의 순회 규칙은 `isTrusted` 값에 따라 달라지지 않습니다. 노드와 트리는 [DOM 트리와 노드 종류](/concepts/dom-tree-nodes)에서, 호출 방식에 따라 `this`가 정해지는 규칙은 [this 바인딩](/concepts/this-binding)에서 본 것을 전제합니다. `preventDefault`와 `stopPropagation`처럼 전파나 기본 동작을 막는 방법과 같은 함수를 중복 등록하는 문제는 [기본 동작과 전파 막기](/concepts/prevent-default-stop-propagation)에서 다룹니다.

### 이벤트는 경로를 두 번 지나간다

이벤트를 보내는 동작(디스패치)은 먼저 이벤트가 지나갈 경로(path)를 만듭니다. 경로는 타깃에서 시작해 부모를 따라 `document`, `window`까지 이어지는 목록이고, 리스너가 달려 있지 않은 노드도 경로에 들어갑니다. `window`는 `document`의 DOM 부모가 아닙니다(`document.parentNode`는 `null`). 경로는 `parentNode`가 아니라 표준의 'get the parent' 단계로 만들고, `Document`의 get the parent는 이렇게 정의되어 있어 `window`가 경로에 들어갑니다.

> A document's get the parent algorithm, given an event, returns null if event's type attribute value is "load" or document does not have a browsing context; otherwise the document's relevant global object.

`load` 이벤트이거나 문서에 브라우징 컨텍스트가 없으면 `null`이고, 그 밖에는 문서의 전역 객체인 `window`를 돌려준다는 뜻입니다. 경로는 이벤트의 `composedPath()`로 볼 수 있습니다. 그다음 DOM 표준은 경로를 두 번 순회하게 합니다. 먼저 캡처 순회입니다.

> For each item of event's path, in reverse order: If item's shadow-adjusted target is non-null, then set event's eventPhase attribute to AT_TARGET. Otherwise, set event's eventPhase attribute to CAPTURING_PHASE. Invoke with item, event, "capturing", and legacyOutputDidListenersThrowFlag if given.

경로를 거꾸로, 곧 `window`에서 타깃 쪽으로 내려가며 각 항목을 방문합니다. 항목이 타깃이면 `eventPhase`를 `AT_TARGET`으로, 아니면 `CAPTURING_PHASE`로 두고 그 항목의 리스너를 부릅니다. 이어서 버블 순회입니다.

> For each item of event's path: If item's shadow-adjusted target is non-null, then set event's eventPhase attribute to AT_TARGET. Otherwise: If event's bubbles attribute is false, then continue. Set event's eventPhase attribute to BUBBLING_PHASE. Invoke with item, event, "bubbling", and legacyOutputDidListenersThrowFlag if given.

이번에는 경로를 순서대로, 곧 타깃에서 `window`로 올라가며 방문합니다. 타깃이 아닌 항목은 `eventPhase`가 `BUBBLING_PHASE`입니다. 그러므로 타깃이 아닌 노드는 캡처 순회에서 한 번(`eventPhase` 1), 버블 순회에서 한 번(`eventPhase` 3) 방문되고, 타깃은 두 순회에서 모두 방문되며 `eventPhase`는 둘 다 `AT_TARGET`입니다. `eventPhase`의 값은 표준이 이렇게 정합니다.

> NONE (numeric value 0) Events not currently dispatched are in this phase.

> CAPTURING_PHASE (numeric value 1) When an event is dispatched to an object that participates in a tree it will be in this phase before it reaches its target.

> AT_TARGET (numeric value 2) When an event is dispatched it will be in this phase on its target.

> BUBBLING_PHASE (numeric value 3) When an event is dispatched to an object that participates in a tree it will be in this phase after it reaches its target.

흔히 이벤트 전파를 '캡처 단계 → 타깃 단계 → 버블링 단계'의 세 단계로 설명합니다. 이 페이지의 두 번의 순회와 모순되는 설명은 아닙니다. 흔히 말하는 '타깃 단계'는 따로 있는 세 번째 순회가 아니라, 두 순회가 각각 타깃을 방문하는 순간(`eventPhase` 2)을 가리킵니다.

예제 1은 아이콘을 눌렀을 때 이 경로를 그대로 보여 줍니다. 첫 줄의 `composedPath()` 결과에는 `body`와 `html`처럼 리스너가 없는 노드도 들어 있습니다. 그리고 경로를 찍는 `window` 리스너 다음으로, 리스너는 `window`에서 내려갈 때 `card`, `save` 순서로 한 번, 올라갈 때 `save`, `card`, `document` 순서로 한 번 불립니다. 이 한 번씩의 방문이 `addEventListener`의 세 번째 인자 `true`(캡처 리스너)와 생략한 경우(버블 리스너)를 가르는 기준이 되는데, 이는 뒤의 '타깃에서는 캡처 리스너가 먼저 불린다'에서 이어서 봅니다.

### target과 currentTarget

리스너를 부를 때 표준은 지금 방문하는 경로 항목을 `currentTarget`으로 정합니다.

> Initialize event's currentTarget attribute to pathItem's invocation target.

`currentTarget`은 지금 실행되는 리스너가 달린 노드이고, 방문하는 항목이 바뀔 때마다 바뀝니다. 반면 `target`은 이벤트가 향한 가장 안쪽 노드로, 그림자 트리(Shadow DOM)가 없는 이 페이지의 예제에서는 디스패치 동안 바뀌지 않습니다. 그래서 `<button><span>★</span></button>`에서 아이콘을 누르면 버튼에 단 리스너에서도 `target`은 아이콘 `span`이고 `currentTarget`은 버튼입니다. 버튼 리스너가 불릴 때 `eventPhase`는 버튼이 타깃이 아니므로 1(캡처 리스너) 또는 3(버블 리스너)입니다. 예제 1의 `save 캡처 1 icon save`, `save 버블 3 icon save`가 이 경우입니다.

이 차이는 버튼에 담은 정보를 읽을 때 문제가 됩니다. 버튼의 `data-id`를 리스너에서 `e.target.dataset.id`로 읽으면, 아이콘을 눌렀을 때는 `target`이 아이콘이라 값이 `undefined`입니다. 리스너를 단 요소를 가리키는 `e.currentTarget.dataset.id`로 읽으면 어느 쪽을 눌러도 같은 값입니다. 예제 3이 두 경우를 비교합니다.

### 타깃에서는 캡처 리스너가 먼저 불린다

타깃은 두 순회에서 모두 방문되므로 타깃에 단 리스너는 어느 순회에서 불리는가가 문제입니다. 방문 항목의 리스너를 부르는 내부 단계가 순회에 맞지 않는 리스너를 걸러 냅니다.

> If phase is "capturing" and listener's capture is false, then continue. If phase is "bubbling" and listener's capture is true, then continue.

캡처 순회(phase가 "capturing")에서는 `capture`가 `true`인 리스너만, 버블 순회에서는 `capture`가 `false`인 리스너만 부릅니다. 타깃도 이 규칙을 그대로 따릅니다. 타깃에서는 먼저 캡처 순회 방문에서 캡처 리스너가 불리고, 이어서 버블 순회 방문에서 나머지 리스너가 불립니다. 그래서 등록한 순서와 상관없이 타깃에서는 캡처 리스너가 먼저입니다. 예제 2는 버블 리스너 `save 버블`을 먼저 등록하고 캡처 리스너 `save 캡처`를 나중에 등록했는데도 `save 캡처 2`가 `save 버블 2`보다 먼저 출력됩니다. 버튼을 직접 눌러 `save`가 타깃이므로 두 방문의 `eventPhase`가 모두 2입니다.

이 규칙은 2019년 3월 DOM 표준 변경([whatwg/dom 커밋 'Fix event path iteration'](https://github.com/whatwg/dom/commit/994380177ef7e388de51f58ba7a4d91fc221c87d))으로 정해졌습니다. 그 전의 표준은 캡처 순회에서 타깃을 건너뛰고 버블 순회에서 타깃의 리스너를 캡처 여부와 상관없이 한꺼번에 불렀기 때문에, 타깃에서는 등록한 순서대로 리스너가 불렸습니다. 오래된 자료에 '타깃에서는 등록 순서대로'라는 설명이 남아 있는 이유입니다. 각 브라우저가 이 변경을 따르기 시작한 시점은 이 페이지에서 확인하지 않았습니다.

### 이벤트 위임

경로가 이렇게 정해지므로 타깃의 조상에 단 리스너도 버블 순회에서 불립니다. 이벤트 위임은 이 점을 이용해 목록 같은 상위 요소 하나에만 리스너를 달고, 어느 자식에서 일어난 이벤트인지는 `e.target`으로 찾는 방법입니다. 그런데 자식 버튼 안에 `<b>` 같은 요소가 또 들어 있으면 `e.target`이 버튼이 아닐 수 있으므로, `Element.closest()`로 버튼을 찾습니다. DOM 표준은 `closest`를 이렇게 정의합니다.

> Let elements be this's inclusive ancestors that are elements, in reverse tree order. For each element of elements: if match a selector against an element, using selector, element, and scoping root this, returns success, return element. [SELECTORS4] Return null.

요소 자신(inclusive)부터 조상 쪽으로 올라가며 선택자에 맞는 첫 요소를 돌려주고, 없으면 `null`을 돌려줍니다. 예제 4에서 `<b>복사</b>`를 누르면 `target`은 `B`이고 `closest('button')`은 그 부모 버튼을 찾습니다. 버튼 밖인 `구분선`을 누르면 `closest('button')`은 `null`이라 리스너가 "버튼 아님"을 처리합니다. 나중에 `append`로 붙인 버튼도 처리되는 이유는 리스너가 버튼이 아니라 `ul`에 달려 있고, 새 버튼에서 일어난 클릭도 버블 순회에서 `ul`까지 올라오기 때문입니다. 새 버튼마다 리스너를 따로 달 필요가 없습니다.

주의할 점은 `closest`가 리스너를 단 `ul` 안에서 멈추지 않는다는 것입니다. 위 단계의 inclusive ancestors는 요소 자신부터 문서의 가장 바깥 요소까지 모든 조상 요소이고, 인용의 scoping root `this`는 선택자 안의 `:scope`가 가리킬 요소를 정할 뿐 찾는 범위를 좁히지 않습니다. 그래서 `[data-action]`처럼 목록 밖의 조상에도 맞을 수 있는 선택자를 쓰면 `closest`가 `ul` 바깥 요소를 돌려줄 수 있습니다. 이럴 때는 찾은 요소가 목록 안에 있는지 `button && menu.contains(button)`으로 확인하거나, `'#menu button'`처럼 선택자에 범위를 넣습니다. 예제 4는 `ul`의 조상 중에 `button`이 없어서 이 문제가 드러나지 않습니다.

### 버블링하지 않는 이벤트

버블 순회에서 타깃이 아닌 항목은 `bubbles`가 `false`이면 건너뜁니다. 위 디스패치 단계의 `If event's bubbles attribute is false, then continue.`가 그 규칙입니다. 이 줄은 타깃이 아닌 항목에만 적용되므로 타깃의 리스너는 `bubbles`와 상관없이 불리고, 캡처 순회도 `bubbles`와 상관없이 경로 전체를 지납니다. 버블링하지 않는 이벤트도 상위 요소의 캡처 리스너로는 받을 수 있다는 뜻입니다.

`new Event('ping')`으로 이벤트를 만들면 `bubbles`는 `false`입니다. 표준은 `EventInit` 딕셔너리에서 `bubbles`의 기본값을 이렇게 정합니다.

> boolean bubbles = false;

그래서 `bubbles: true`를 옵션으로 줘야 버블링합니다. 반대로 `click()`은 만들어 보내는 이벤트의 `bubbles`를 `true`로 둡니다.

> Initialize event's bubbles and cancelable attributes to true.

`focus`는 대표적인 버블링하지 않는 이벤트이고 `focusin`은 버블링합니다. 이 사실은 DOM이나 HTML이 아니라 W3C UI Events 명세에 있습니다. UI Events의 이벤트 정의 표는 `focus`의 Bubbles 칸을 `No`로, `focusin`의 Bubbles 칸을 `Yes`로 적고, `focusin`을 이렇게 설명합니다.

> The focus event MUST fire before the dispatch of this event type. This event type is similar to focus, but does bubble.

`focus`를 먼저 보내고 `focusin`을 보내며, `focusin`은 `focus`와 비슷하지만 버블링한다는 뜻입니다.

예제 5에서 입력창 `email`에 `focus()`를 하면 `form`에 단 `focus` 버블 리스너는 불리지 않지만 `focus` 캡처 리스너와 `focusin` 버블 리스너는 불립니다. 이 결과는 테스트가 문서에 포커스가 있는 상태로 실행한 것이며, 문서가 포커스를 갖지 않은 상태(예: DevTools 콘솔에 입력 포커스가 있을 때)에서는 다를 수 있습니다. 이 페이지는 `focusout`과 `blur`는 다루지 않습니다. 따라서 이벤트 위임에서 `focus`는 상위 요소의 버블 리스너로 받을 수 없고, 상위 요소에서 받으려면 캡처 리스너를 쓰거나 `focusin`을 써야 합니다.

### 리스너 안의 this

리스너를 부르는 DOM 표준의 단계는 콜백을 호출할 때 `this`로 넘길 값도 정해 둡니다.

> Call a user object's operation with listener's callback, "handleEvent", « event », and event's currentTarget attribute value.

인용의 "handleEvent"는 리스너가 함수가 아니라 `handleEvent` 메서드를 가진 객체일 때 부를 메서드 이름입니다. 리스너가 함수이면 그 함수를 부르고, 마지막 인자가 그 함수의 `this`로 쓰이는 값인 이벤트의 `currentTarget`입니다. 리스너가 `handleEvent` 객체이면 Web IDL 규칙에 따라 `this`는 그 객체가 되며, 이 페이지는 함수 리스너만 다룹니다. 그래서 일반 함수로 만든 리스너의 `this`는 `currentTarget`, 곧 리스너를 단 노드입니다. [this 바인딩](/concepts/this-binding)에서 호출 방식에 따라 `this`가 정해진다고 했는데, 리스너의 경우 호출하는 쪽이 호스트이고 호스트가 `currentTarget`을 `this`로 넘깁니다. 아래 절에서 볼 `onclick` 같은 이벤트 핸들러도 HTML 표준의 처리 단계가 콜백을 부를 때 같은 값을 `this`로 넘기므로, 이 규칙은 핸들러에도 그대로 적용됩니다.

> Let return value be the result of invoking callback with « event », "rethrow", and with callback this value set to event's currentTarget.

[화살표 함수](/concepts/arrow-functions)는 자기 `this`가 없으므로 호스트가 `this`로 무엇을 넘기든 영향을 받지 않고 바깥의 `this`를 씁니다. 예제 6에서 화살표 함수 리스너는 스크립트 최상위에서 만들어졌으므로 `this`가 그 스크립트 최상위의 `this`, 곧 `window`입니다. 그래서 `this === window`는 `true`이고 `this === e.currentTarget`은 `false`입니다. 여기서 말하는 최상위 `this`가 `window`인 것은 이 예제의 일반 `<script>`에 한한 이야기이고, 모듈 같은 다른 경우까지 일반화하지 않습니다.

### 이벤트 핸들러와 addEventListener

`onclick` 같은 이벤트 핸들러는 `addEventListener`와 다른 구조입니다. HTML 표준은 이벤트 핸들러를 이름마다 값 하나를 갖는 구조로 정의하고, 이 핸들러가 리스너로 어떻게 동작하는지 이렇게 적습니다.

> These act as non-capture event listeners for the object on which they are specified.

곧 캡처하지 않는 리스너로 동작합니다. `onclick` 콘텐츠 어트리뷰트(`<button onclick="...">`)와 `onclick` 프로퍼티는 같은 이름의 같은 핸들러를 가리킵니다. 프로퍼티에 값을 대입하면 표준은 핸들러의 값을 바꾸고 핸들러를 활성화합니다.

> Set eventHandler's value to the given value.

활성화 단계는 이미 리스너가 만들어져 있으면 아무것도 하지 않습니다.

> If eventHandler's listener is not null, then return.

그러므로 핸들러가 활성화될 때 한 번만 리스너 목록에 들어가고, 그 뒤에 다시 대입하면 값만 바뀝니다. 목록에서의 자리는 활성화될 때 정해진 그대로입니다. 예제 7의 `<button>`에는 `onclick` 어트리뷰트가 있습니다. HTML 표준의 어트리뷰트 변경 단계(attribute change steps)는 이벤트 핸들러 어트리뷰트가 설정되면 핸들러를 활성화하므로, 스크립트가 `addEventListener`를 부르기 전에 이미 핸들러의 리스너가 목록에 들어 있습니다. 그래서 핸들러가 첫 자리를 차지하고, 스크립트가 등록한 `리스너1`, `리스너2`는 그 뒤에 옵니다. 프로퍼티를 두 번 대입해도 핸들러는 하나이므로 마지막 값인 `프로퍼티B`가 첫 자리에서 실행됩니다. 이때 `onclick` 프로퍼티는 어트리뷰트를 반영하는(reflect) 프로퍼티가 아니라서 `getAttribute('onclick')`은 계속 처음 문자열을 돌려줍니다. 어트리뷰트와 프로퍼티가 항상 같은 값을 반영하지는 않는다는 점은 [HTML 어트리뷰트와 DOM 프로퍼티](/concepts/html-attribute-dom-property)에서 본 것과 이어집니다. `null`을 대입하면 비활성화되어 그 리스너를 목록에서 지웁니다.

> Let listener be eventHandler's listener. If listener is not null, then remove an event listener with eventTarget and listener.

비활성화된 뒤 다시 함수를 대입하면 핸들러가 새로 활성화되어, 그때의 리스너 목록 끝에 들어갑니다. 예제 7의 마지막 줄에서 `프로퍼티C`가 `리스너1`, `리스너2` 뒤에 실행되는 이유입니다. 그러니 '이벤트 핸들러는 항상 첫 자리'가 아니라 '활성화된 시점의 자리'입니다.

### 디스패치가 끝난 이벤트 객체

리스너 안에서 이벤트 객체를 변수에 저장해 두고 디스패치가 끝난 뒤에 읽으면 값이 달라져 있습니다. 표준이 디스패치의 마지막에 이렇게 정리하기 때문입니다.

> Set event's eventPhase attribute to NONE. Set event's currentTarget attribute to null. Set event's path to the empty list.

`eventPhase`는 0(`NONE`), `currentTarget`은 `null`이 되고 경로는 비워집니다. `composedPath()`는 경로가 비면 빈 배열을 돌려줍니다.

> If path is empty, then return composedPath.

반면 `target`은 지워지지 않습니다. 디스패치 마지막 단계의 `target`을 `null`로 되돌리는 조건은 `clearTargets`가 참일 때인데, 그림자 트리(Shadow DOM)가 없는 이 예제에서는 지워지지 않아 `target`이 그대로 남습니다. 예제 8이 리스너 안과 디스패치 뒤의 값을 비교하고, 예제 1의 마지막 줄 `끝 0 null`도 같은 사실입니다.

## 결과와 이유

### 예제 1

첫 줄은 `icon`을 타깃으로 한 경로입니다. `body`와 `html`처럼 리스너가 없는 노드도 경로에 있습니다. 둘째 줄 `card 캡처 1 icon card`와 셋째 줄 `save 캡처 1 icon save`는 캡처 순회에서 경로를 `window`부터 거꾸로 내려오며 각 항목의 캡처 리스너가 불린 것이고, 타깃이 아니라서 `eventPhase`는 1입니다. 아이콘 `icon`에는 리스너가 없어 아무 줄도 찍히지 않지만 타깃으로서 방문됩니다. 이어지는 버블 순회에서 `save 버블 3 icon save`, `card 버블 3 icon card`, `document 버블 3 icon document` 순서로 올라가며 `eventPhase`는 3입니다. 모든 줄에서 `target`은 `icon`이고 `currentTarget`만 바뀝니다. 마지막 줄 `끝 0 null`은 디스패치가 끝난 뒤 저장해 둔 이벤트의 `eventPhase`와 `currentTarget`입니다.

### 예제 2

첫 줄의 경로에는 `card`와 `save`가 있습니다. `card 캡처 1 save card`는 `card`가 타깃이 아니라 `eventPhase`가 1입니다. `save`는 타깃이라 두 줄 모두 `eventPhase`가 2이고, 코드에서는 버블 리스너를 먼저 등록했지만 캡처 순회의 방문이 앞서므로 `save 캡처 2 save save`가 `save 버블 2 save save`보다 먼저 찍힙니다. 마지막 줄 `card 버블 3 save card`는 버블 순회에서 `card`의 버블 리스너가 불린 것입니다. `card` 캡처 리스너는 캡처 순회에서 경로를 찍는 `window` 리스너 다음으로(`save`보다 앞서) 불렸고, 버블 리스너는 `save` 다음에 불립니다.

### 예제 3

첫 줄 `heart undefined 42`는 아이콘을 눌렀을 때입니다. `target`은 `heart`이고 그 `span`에는 `data-id`가 없어 `e.target.dataset.id`가 `undefined`입니다. `currentTarget`은 리스너를 단 버튼 `like`라서 `e.currentTarget.dataset.id`는 `42`입니다. 둘째 줄 `like 42 42`는 버튼을 직접 눌렀을 때로, 이때는 버튼이 타깃이라 `target`과 `currentTarget`이 같은 노드입니다. 그래서 `target`을 쓰면 아이콘을 누를 때만 틀리고 버튼을 누를 때는 맞아서 버그가 눈에 잘 띄지 않을 수 있습니다.

### 예제 4

`<b>`를 누르면 `target`은 `B`이고, 리스너가 `ul`에 있어도 클릭이 버블 순회로 올라와 실행됩니다. `closest('button')`은 `<b>`의 조상에서 버튼을 찾으므로 `B copy`가 찍힙니다. `구분선`은 조상 중에 버튼이 없어 `closest`가 `null`이고, 그래서 `note 버튼 아님`이 찍힙니다. 마지막 줄 `BUTTON cut`은 나중에 `append`한 버튼을 누른 결과입니다. 리스너는 처음부터 `ul`에 있었고 새 버튼의 클릭도 `ul`까지 올라오기 때문에 새 리스너를 달지 않아도 처리됩니다. 이때 `target`은 버튼 자신이라 `tagName`이 `BUTTON`이고, `closest`는 요소 자신부터 검사하므로 그 버튼을 돌려줍니다.

### 예제 5

첫 줄은 `focus()`를 했을 때 `form`에서 실행된 리스너입니다. `focus` 버블 리스너는 실행되지 않았는데, `focus`가 버블링하지 않는 이벤트라 버블 순회에서 타깃이 아닌 `form` 항목이 건너뛰어졌기 때문입니다. `focus` 캡처 리스너는 캡처 순회에서, `focusin` 버블 리스너는 버블링하는 `focusin` 이벤트에서 실행되어 `["focus 캡처","focusin 버블"]`입니다. 이 순서는 UI Events가 `focus`를 `focusin`보다 먼저 보내도록 정한 것과 맞습니다. 둘째 줄 `false true`는 `new Event('ping')`의 `bubbles`가 `false`이고 `bubbles: true`를 준 쪽이 `true`라는 뜻입니다. 마지막 줄 `["true:3"]`은 `form`이 `bubbles`가 `true`인 이벤트만 받았고 그때 `form`이 타깃이 아니라서 `eventPhase`가 3이었다는 뜻입니다. `bubbles`가 `false`인 이벤트는 캡처 순회에서 `form`을 지나쳤지만, `form`에는 `ping` 캡처 리스너가 없어서 받은 것이 없습니다.

### 예제 6

첫 줄 `true box go`는 일반 함수 리스너의 `this`가 `e.currentTarget`과 같고(`true`), 그 `id`가 `box`이며, 실제로 누른 `e.target`의 `id`는 `go`라는 뜻입니다. 둘째 줄 `true false`는 화살표 함수 리스너의 `this`가 `window`(`true`)이고 `currentTarget`이 아니라는(`false`) 뜻입니다. 화살표 함수는 호출될 때 호스트가 넘기는 `this`를 쓰지 않고 정의된 곳의 `this`를 쓰기 때문입니다. 두 리스너는 모두 `box`의 버블 리스너로, `go`가 타깃이므로 버블 순회에서 등록한 순서대로 실행되어 위의 순서로 출력됩니다.

### 예제 7

첫 줄 `function`은 `onclick` 어트리뷰트로 만들어진 핸들러가 `onclick` 프로퍼티에서 함수로 보인다는 뜻입니다. 둘째 줄은 클릭했을 때의 실행 순서입니다. 어트리뷰트로 활성화된 핸들러가 리스너 목록의 첫 자리에 있고, 프로퍼티를 `프로퍼티A`, `프로퍼티B`로 두 번 대입해도 값만 바뀌어 자리는 그대로입니다. 그래서 마지막 값인 `프로퍼티B`가 가장 먼저 실행되고, 이어서 등록 순서대로 `리스너1`, `리스너2`가 실행됩니다. `프로퍼티A`는 값이 바뀌어 한 번도 실행되지 않았습니다. 셋째 줄 `log.push('어트리뷰트')`는 `getAttribute('onclick')`이 처음 어트리뷰트 문자열을 그대로 돌려준다는 뜻입니다. `onclick` 프로퍼티는 이 어트리뷰트를 반영하는 프로퍼티가 아니라서, 프로퍼티를 바꿔도 어트리뷰트 문자열은 바뀌지 않습니다. 넷째 줄 `["리스너1","리스너2"]`는 `onclick = null` 뒤에 핸들러가 비활성화되어 목록에서 지워져 `addEventListener`로 등록한 두 리스너만 남았다는 뜻입니다. 마지막 줄 `["리스너1","리스너2","프로퍼티C"]`는 비활성화된 핸들러에 다시 함수를 대입하자 새로 활성화되어 그때의 목록 끝, 곧 `리스너2` 뒤에 들어갔다는 뜻입니다.

### 예제 8

첫 줄 `3 card 6`은 리스너 안에서의 값입니다. `card`는 타깃이 아니라 버블 순회의 `eventPhase`가 3이고, `currentTarget`의 `id`는 `card`이며, 경로는 `save`, `card`, `body`, `html`, `document`, `window` 여섯 항목이라 `composedPath().length`가 6입니다. 둘째 줄 `0 null save 0`은 디스패치가 끝난 뒤 같은 이벤트 객체를 읽은 값입니다. `eventPhase`는 0이 되고, `currentTarget`은 `null`이 되었으며 경로가 비워져 `composedPath()`의 길이는 0입니다. `target`은 그림자 트리(Shadow DOM)가 없는 이 예제에서는 지워지지 않아 `saved.target.id`는 그대로 `save`입니다. 이벤트 객체를 나중에 쓰려고 저장하면 안에 든 `currentTarget`을 신뢰할 수 없다는 뜻이므로, 필요한 값은 리스너가 실행되는 동안 꺼내 두어야 합니다.

### 흔한 오해

<Callout type="misconception" title="event.target은 리스너를 단 요소다">

`target`은 이벤트가 향한 가장 안쪽 노드이고, 리스너를 단 요소는 `currentTarget`입니다. 버튼 안의 아이콘을 누르면 버튼 리스너에서도 `target`은 아이콘입니다(예제 1, 3). 두 값이 같은 것은 버튼을 직접 누르는 것처럼 리스너를 단 노드가 곧 타깃일 때뿐입니다.

</Callout>

<Callout type="misconception" title="이벤트는 타깃에서 위로만 올라간다(버블링만 있다)">

이벤트는 경로를 두 번 지납니다. 먼저 `window`에서 타깃 쪽으로 내려가는 캡처 순회가 있고, 그다음에 타깃에서 `window`로 올라가는 버블 순회가 있습니다(예제 1). `addEventListener`의 세 번째 인자를 `true`로 주면 캡처 순회에서 불리는 리스너가 됩니다.

</Callout>

<Callout type="misconception" title="타깃에서는 등록한 순서대로 리스너가 불린다">

타깃은 캡처 순회와 버블 순회에서 한 번씩 방문되고, 캡처 순회에서는 캡처 리스너만, 버블 순회에서는 나머지만 불립니다. 그래서 타깃에서는 버블 리스너를 먼저 등록해도 캡처 리스너가 먼저 실행됩니다(예제 2). 등록 순서가 실행 순서가 되는 것은 같은 방문에서 불리는 리스너끼리, 곧 캡처 리스너들끼리 또는 버블 리스너들끼리입니다.

</Callout>

<Callout type="misconception" title="모든 이벤트는 버블링한다">

`bubbles`가 `false`인 이벤트는 버블 순회에서 타깃이 아닌 노드를 건너뜁니다. `new Event('ping')`은 기본이 `false`이고, `focus`도 버블링하지 않습니다(예제 5). 이런 이벤트도 캡처 순회는 하므로 상위 요소에서 받으려면 캡처 리스너를 쓰거나, `focus` 대신 버블링하는 `focusin`을 써야 합니다. 이벤트마다 버블링 여부가 다르므로 이벤트 위임에 쓰기 전에 그 이벤트가 버블링하는지 확인해야 합니다.

</Callout>

<Callout type="misconception" title="onclick을 여러 번 대입하면 핸들러가 여러 개 등록된다">

`onclick`은 이름마다 값 하나를 갖는 이벤트 핸들러입니다. 다시 대입하면 새 핸들러가 추가되는 것이 아니라 값이 바뀌고, 리스너 목록의 자리는 활성화될 때 정해진 그대로입니다. 다만 `null`로 비활성화한 뒤 다시 대입하면 새로 활성화되어 그때의 목록 끝에 들어갑니다(예제 7). 여러 개를 등록하려면 `addEventListener`를 씁니다. 같은 함수를 중복 등록했을 때의 동작은 [기본 동작과 전파 막기](/concepts/prevent-default-stop-propagation)에서 다룹니다.

</Callout>

<Callout type="misconception" title="화살표 함수 리스너의 this도 currentTarget이다">

호스트가 리스너를 부를 때 `currentTarget`을 `this`로 넘기는 것은 일반 함수에서만 의미가 있습니다. 화살표 함수는 자기 `this`가 없어서 바깥의 `this`를 쓰므로, 이 예제처럼 스크립트 최상위에서 만든 화살표 함수의 `this`는 `window`입니다(예제 6). 화살표 함수 리스너에서 리스너를 단 요소가 필요하면 `e.currentTarget`을 읽습니다.

</Callout>
