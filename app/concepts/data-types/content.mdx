## 동작 원리

숫자를 넣어 둔 변수에 나중에 문자열을 넣어도 오류가 나지 않는 것은, 타입이 변수가 아니라 값에 있기 때문입니다. 이 페이지는 명세가 값마다 정하는 타입 8개, 변수에 타입이 없다는 것의 뜻, 문자열을 만드는 세 가지 따옴표, 값을 할당하지 않은 변수가 갖는 값인 undefined와 객체 값이 의도적으로 없음을 나타내는 null을 알아봅니다.

이 페이지는 클래식 스크립트, 즉 `type` 속성이 없거나 JavaScript MIME 타입인 `<script>`로 실행되는 코드의 맨 바깥에서 `var`로 선언한 변수를 기준으로 설명합니다. `.js` 예제는 Node의 `vm` 모듈에서 ECMAScript 스크립트(Script)로, `.html` 예제는 Chromium에서 실행해 출력을 확인했습니다.

표의 `undefined`는 리터럴이 아니라, 전역 객체의 `undefined` 프로퍼티를 가리키는 식별자입니다. 이 점은 [전역 객체](/concepts/global-object)에서 다룹니다.

### 변수에는 타입이 없다

명세의 개요(4장, 비규범 설명)는 변수에 타입을 선언할 필요가 없다고 적습니다("a variable is not required to have its type declared"). 변수에 어떤 타입의 값이든 넣을 수 있다는 것은 명세 본문에서도 확인할 수 있습니다.

- `var` 선언문의 문법에는 타입을 적는 자리가 없습니다. 선언에 적는 것은 이름과 초기값입니다. 다만 이것만으로는 변수에 타입이 없다고 할 수 없습니다. 타입을 적지 않아도 처음 넣은 값의 타입으로 변수를 고정하는 규칙이 있을 수 있기 때문입니다.
- 결정적인 근거는 바인딩에 값을 넣는 연산(SetMutableBinding)입니다. 이 연산은 값 인수를 "an ECMAScript language value"로 받고, 값의 타입을 검사하는 단계가 없습니다.

그래서 같은 변수에 다른 타입의 값을 차례로 할당할 수 있습니다. 예제 1에서 확인합니다. 이 페이지에서 "변수의 타입"이라고 하면 그 시점에 변수가 가진 값의 타입을 뜻합니다. 예제 1의 출력은 "변수의 타입이 값에 따라 바뀐다"는 해석으로도 같게 나오므로 정의를 증명하지는 못합니다. 정의의 근거는 위의 명세이고, 예제 1이 배제하는 것은 "변수는 처음 넣은 값의 타입으로 고정된다"는 모델입니다.

변수에 타입을 정해 두고 실행 전에 검사하는 방식을 정적 타입이라고 하고, 이렇게 하지 않는 언어를 흔히 동적 타입 언어라고 부릅니다. 이는 명세에 나오지 않는 일반 용어입니다. 이 페이지는 다른 언어의 동작은 다루지 않습니다.

브라우저에서 따라 할 때는 변수 이름에 주의해야 합니다. 브라우저의 전역 객체에는 브라우저가 정의해 둔 접근자 프로퍼티가 있고, `name`이 그중 하나입니다. 맨 바깥 `var` 이름이 이런 프로퍼티와 같으면 `var` 선언은 전역 객체에 새 프로퍼티를 만들지 않습니다. `name`처럼 세터가 있는 프로퍼티라면 할당은 그 세터를 거칩니다. `name`의 세터는 넣으려던 값을 문자열로 바꾸므로, 아래 코드에서 `10`을 넣은 뒤의 `typeof name`은 `'string'`이고 출력은 `string true`입니다. 변수에 타입이 있어서가 아니라 브라우저가 정의한 세터가 값을 바꾸기 때문입니다.

### 문자열을 만드는 세 가지 따옴표

작은따옴표 `'…'`, 큰따옴표 `"…"`, 백틱 `` `…` ``(템플릿 리터럴)은 모두 String 타입의 값을 만듭니다. 만들어진 값의 코드 유닛 나열이 같으면 어느 따옴표로 만들었든 같은 문자열 값입니다. 어떤 따옴표를 썼는지는 값에 남지 않습니다. 예제 2에서 확인합니다. 눈에 같아 보여도 다른 문자열일 수 있다는 점은 [문자열 길이와 UTF-16](/concepts/string-utf16)에서 다룹니다.

템플릿 리터럴은 별도의 타입이 아니라 문자열을 만드는 또 하나의 문법입니다. 만들어지는 값의 타입은 같고, 문법이 다음처럼 다릅니다.

- 작은따옴표·큰따옴표 문자열에는 줄바꿈 문자(LF·CR)를 문자열 내용으로 그대로 쓸 수 없습니다. 쓰면 SyntaxError입니다.
- 다만 `\` 바로 뒤의 줄바꿈은 줄 잇기(LineContinuation)로 허용됩니다. 이 줄바꿈은 값에 아무것도 넣지 않습니다. 예를 들어 작은따옴표 문자열을 `'a\`로 끝내고 다음 줄을 `b'`로 이어 쓰면 값은 `ab`입니다.
- 템플릿 리터럴에는 줄바꿈을 그대로 쓸 수 있습니다. 소스의 LF·CR·CRLF 줄바꿈은 값에서 LF 하나(`\n`)가 되고, 따옴표 문자열과 마찬가지로 `\` 바로 뒤의 줄바꿈은 값에 아무것도 넣지 않습니다. 예제 2의 두 줄 템플릿은 LF 줄바꿈이 값에서 줄바꿈 문자 하나가 되는 것을 보입니다. CR과 CRLF가 LF로 바뀌는 것은 명세가 정한 규칙이고, 예제 파일의 줄바꿈은 LF라서 예제로는 보이지 않습니다.
- `${식}`처럼 `${`와 `}` 사이에 식을 쓰면 그 식의 값이 문자열로 바뀌어 그 자리에 들어갑니다. 심벌처럼 문자열로 바꿀 수 없는 값이면 TypeError입니다. 값을 문자열로 바꾸는 규칙은 [암묵적 타입 변환](/concepts/type-coercion)에서 다룹니다.

### undefined와 null

명세는 Undefined 타입의 값이 `undefined` 하나뿐이라고 정하고, "값을 할당하지 않은 변수는 값 `undefined`를 가진다"고 설명합니다("Any variable that has not been assigned a value has the value undefined"). 이 문장은 한 방향으로만 읽어야 합니다. 값을 할당하지 않았으면 `undefined`이지만, 값이 `undefined`라고 해서 할당하지 않았다는 뜻은 아닙니다. `var x = undefined;`처럼 `undefined`를 직접 할당할 수도 있기 때문입니다.

`let x;`처럼 초기값 없이 선언한 `let` 변수도 선언문이 실행된 뒤에는 `undefined`입니다. 다만 `let`과 `const` 변수는 선언문이 실행되기 전에 읽으면 `undefined`가 아니라 ReferenceError입니다. 기준은 코드의 위치가 아니라 실행 시점이며, [TDZ](/concepts/tdz)에서 다룹니다. `const`는 초기값 없는 선언 자체가 SyntaxError라서 값을 할당하지 않은 `const` 변수는 없습니다. `var`로 선언한 변수가 값을 할당하기 전에 `undefined`인 이유는 [변수 선언과 할당](/concepts/variable-declaration)에서 다룹니다.

Null 타입의 값은 `null` 하나뿐이고, 명세는 이를 객체 값이 의도적으로 없음("intentional absence of any object value")을 나타내는 값이라고 설명합니다. `null`은 객체 값이 없음을 나타내려고 쓰는 값입니다.

둘은 타입이 다른 서로 다른 값이라서 `===`로 비교하면 `false`입니다. 예제 3에서 확인합니다. 그렇다고 둘이 늘 다르게 취급되는 것은 아닙니다. `==`는 둘을 같다고 봅니다([동등 비교](/concepts/equality-operators) 참고). 또 `typeof null`은 `'null'`이 아니라 `'object'`입니다([typeof 연산자](/concepts/typeof-operator) 참고). 구조 분해의 기본값은 값이 `undefined`일 때만 쓰이고 `null`에는 쓰이지 않습니다([스프레드와 디스트럭처링](/concepts/spread-destructuring) 참고).

예제 1에서 `value`에는 숫자 `10`, 문자열 `'ten'`, 불리언 `true`를 차례로 할당합니다. 각 줄의 `typeof value`는 그 시점에 변수가 가진 값의 타입을 알려 주므로 `number`, `string`, `boolean`이 차례로 출력됩니다. 두 번째 할당 뒤 오류 없이 `string`이 출력되었다는 것은 "처음 넣은 값의 타입으로 고정된다"는 모델이 틀렸다는 뜻입니다. 변수에 타입이 없다는 설명의 근거는 앞에서 본 명세의 바인딩 연산입니다.

예제 2의 첫 번째 출력은 `'JS'`, `"JS"`, `` `JS` ``가 모두 같은 문자열 값이라서 두 비교가 모두 `true`입니다. 백틱으로 만든 값도 `typeof`가 `string`이라 별도의 타입이 아닙니다. 세 번째 출력에서 두 줄에 걸쳐 쓴 템플릿 리터럴의 값은 `a`, 줄바꿈 문자 하나, `b`이고 `'a\nb'`와 같으므로 `true`입니다. 마지막 출력은 `${n}`과 `${n + 1}`의 값이 문자열로 바뀌어 들어가 `2 + 1 = 3`이 됩니다.

예제 3에서 `var empty;`는 값을 할당하지 않았으므로 `empty`는 `undefined`입니다. 그래서 `empty === undefined`는 `true`이고 `empty === null`은 `false`입니다. `nothing`에는 `null`을 직접 넣었으므로 `nothing === null`은 `true`이고, `null === undefined`는 타입이 다른 값끼리의 비교라서 `false`입니다.

<Callout type="misconception" title="변수는 처음 넣은 값의 타입으로 정해진다">
  변수에는 타입을 정하는 자리도, 값의 타입을 검사하는 단계도 없습니다. 예제 1에서 숫자를 넣은 변수에
  문자열과 불리언을 차례로 넣을 수 있고, 각 시점의 타입은 그때 변수가 가진 값의 타입입니다.
</Callout>

<Callout type="misconception" title="백틱 문자열은 다른 타입이다">
  백틱으로 만든 값도 String 타입이고 값의 코드 유닛 나열이 같으면 따옴표 문자열과 같은 값입니다(예제
  2). 템플릿 리터럴은 줄바꿈을 그대로 쓸 수 있고 식을 끼워 넣을 수 있는, 문자열을 만드는 다른
  문법입니다.
</Callout>

<Callout type="misconception" title="null과 undefined는 같은 값이다">
  둘은 서로 다른 타입의 서로 다른 값이라서 `===`로 비교하면 `false`입니다(예제 3). 선언만 하고 값을
