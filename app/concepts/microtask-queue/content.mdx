Node.js 같은 다른 호스트는 이 페이지에서 다루지 않습니다. 예제의 출력은 테스트가 Chromium에서 실제로 실행해 얻은 값이며, 두 프로미스 체인 예제만 Node의 `vm`에서 ECMAScript 코드로 실행한 값입니다. 이 페이지는 [이벤트 루프와 태스크 큐](/concepts/event-loop)에서 본 태스크와 스택, [프로미스](/concepts/promise)에서 본 `then`이 Job을 넣는 절차, [타이머](/concepts/timers)에서 본 타이머 콜백을 전제합니다. `async`/`await`와 `try...catch`는 별도 개념(작성 예정)입니다.

## 동작 원리

### 마이크로태스크 큐는 태스크 큐가 아니다

HTML 표준은 이벤트 루프마다 마이크로태스크를 담는 큐가 하나 있다고 정합니다.

> Each event loop has a microtask queue, which is a queue of microtasks, initially empty.

표준의 정의로는 마이크로태스크도 태스크의 한 종류입니다. queue a microtask 알고리즘으로 만든 태스크를 흔히 마이크로태스크라고 부릅니다.

> A microtask is a colloquial way of referring to a task that was created via the queue a microtask algorithm.

하지만 마이크로태스크가 들어가는 큐는 [이벤트 루프와 태스크 큐](/concepts/event-loop)에서 본 태스크 큐와 다른 큐입니다. 표준은 주석(비규범)으로 이 점을 적습니다.

> The microtask queue is not a task queue.

처리 모델의 주석도 같은 점을 짚습니다. 이벤트 루프가 태스크 큐 하나를 골라 태스크를 꺼내는 단계에서 마이크로태스크 큐는 골라지지 않습니다.

> Remember that the microtask queue is not a task queue, so it will not be chosen in this step.

마이크로태스크는 뒤에서 볼 체크포인트에서 따로 실행됩니다. 이 페이지는 태스크 큐에 들어가 이벤트 루프가 하나씩 꺼내는 태스크를 그냥 태스크라고 부르고, 마이크로태스크 큐에 들어가는 것을 마이크로태스크라고 부릅니다.

### 프로미스 Job과 queueMicrotask는 같은 큐로 들어간다

`then` 콜백은 [프로미스](/concepts/promise)에서 본 대로 Job으로 만들어져 호스트의 HostEnqueuePromiseJob에 넘겨집니다. 프로미스가 이미 이행된 상태에서 `then`을 부르면 그 자리에서 Job을 넘기고, pending이면 프로미스가 정해질 때 넘깁니다. 이 Job을 어디에 넣을지는 호스트가 정하는데, HTML 표준은 이렇게 적습니다.

> HTML schedules these operations in the microtask queue.

`queueMicrotask`도 같은 큐를 씁니다. HTML 표준의 `queueMicrotask` 단계(규범)는 이렇습니다.

> The queueMicrotask(callback) method must queue a microtask to invoke callback with « » and "report".

둘 다 마이크로태스크 큐에 마이크로태스크를 넣는 일이므로, `then` 콜백과 `queueMicrotask` 콜백은 하나의 큐에 넣은 순서대로 섞여 실행됩니다. 큐에서 먼저 넣은 것부터 꺼낸다는 것은 뒤에서 볼 체크포인트의 단계가 정하고, 이 순서를 예제 1이 확인합니다.

### 체크포인트는 스택이 빌 때 일어난다

마이크로태스크는 마이크로태스크 체크포인트에서 실행됩니다. 표준에는 체크포인트를 하는 곳이 여럿 있는데, 이 페이지의 예제와 관련된 곳은 두 곳입니다. 하나는 스크립트나 콜백을 실행한 뒤의 정리 단계(clean up after running script)입니다.

> If the JavaScript execution context stack is now empty, perform a microtask checkpoint.

"now empty"라는 한정어가 중요합니다. 스크립트나 콜백이 끝났어도 [실행 컨텍스트](/concepts/execution-context)의 스택에 다른 실행 컨텍스트가 남아 있으면 이 단계에서는 체크포인트를 하지 않습니다. 스택이 비었을 때만 합니다. 이 정리 단계는 Web IDL이 콜백을 부르는 알고리즘의 끝에서도 부릅니다.

> Clean up after running script with relevant settings.

따라서 이벤트 리스너나 타이머 콜백처럼 호스트가 부르는 콜백이 끝날 때마다 스택이 비었는지 확인하고, 비었으면 체크포인트를 합니다. 다른 하나는 이벤트 루프의 처리 모델입니다. 태스크의 단계를 실행한 뒤에 이 단계가 있습니다.

> Perform a microtask checkpoint.

앞의 정리 단계에서 이미 큐를 비웠다면 이 체크포인트에는 실행할 마이크로태스크가 없습니다. 체크포인트에는 마이크로태스크를 실행한 뒤의 다른 단계도 있지만 이 페이지는 다루지 않습니다. 이 페이지의 시뮬레이터는 그런 체크포인트를 따로 그리지 않습니다. HTML 표준의 `queueMicrotask()` 절은 이 메서드로 넣은 콜백이 언제 실행되는지 이렇게 설명합니다.

> This allows their code to run once the JavaScript execution context stack is next empty, which happens once all currently executing synchronous JavaScript has run to completion.

이 설명의 주어는 `queueMicrotask()`이지만, then 콜백의 Job도 같은 마이크로태스크 큐에 들어가 앞의 정리 단계에서 실행되므로 마찬가지로 동기 코드가 모두 끝나 스택이 비는 때 실행됩니다. 그래서 `setTimeout(fn, 0)`을 먼저 등록해도 스크립트가 끝나 스택이 빌 때 체크포인트가 먼저 일어나고, 타이머 콜백은 별도의 태스크로 그다음에 실행됩니다. 이 순서는 예제 1이 보입니다. 이것은 태스크 큐에 대한 마이크로태스크 큐의 순서 규칙이 따로 있어서가 아니라, 체크포인트가 일어나는 시점이 스택이 비는 순간이라서 나오는 결과입니다.

### 체크포인트는 큐가 빌 때까지 계속된다

체크포인트는 큐에 마이크로태스크가 하나 있다고 하나만 실행하고 끝나지 않습니다. 체크포인트의 반복 부분은 이렇습니다.

> While the event loop's microtask queue is not empty:

반복할 때마다 큐에서 마이크로태스크를 하나 꺼냅니다.

> Let oldestMicrotask be the result of dequeuing from the event loop's microtask queue.

큐가 비지 않은 동안 가장 먼저 넣은 마이크로태스크를 꺼내 실행하는 반복입니다. 그래서 마이크로태스크 안에서 새 마이크로태스크를 넣으면 같은 체크포인트 안에서 이어서 실행됩니다. 예제 2에서 `m1`이 `m2`를, `m2`가 `m3`을 넣어도 셋 모두 타이머 콜백보다 먼저 실행됩니다. 마이크로태스크가 새 마이크로태스크를 계속 넣으면 큐가 비지 않으므로 체크포인트가 끝나지 않고, 그동안 다음 태스크(타이머 콜백 등)는 실행되지 못합니다. 예제 3은 이를 1000개로 확인합니다. 이 페이지는 정확한 시간이 아니라 순서만 확인합니다. `queueMicrotask()` 절은 이렇게 덧붙입니다.

> Authors ought to be aware that scheduling a lot of microtasks has the same performance downsides as running a lot of synchronous code.

마이크로태스크를 많이 넣는 것은 동기 코드를 오래 실행하는 것과 같은 단점이 있다는 설명입니다. 큐가 끝없이 채워지면 체크포인트가 끝나지 않으므로 마이크로태스크로 일을 쪼개도 다른 태스크에는 틈이 생기지 않습니다. 이 점이 타이머로 일을 쪼갠 [이벤트 루프와 태스크 큐](/concepts/event-loop)의 방식과 다릅니다.

그런데 마이크로태스크 콜백이 끝날 때도 스택이 비므로 정리 단계가 체크포인트를 부릅니다. 그래도 체크포인트가 겹쳐 실행되지 않는 것은 체크포인트의 첫 단계가 이미 체크포인트를 하는 중이면 바로 돌아가는 재진입 방지 단계이기 때문입니다.

> If the event loop's performing a microtask checkpoint is true, then return.

그래서 바깥 체크포인트의 반복이 그대로 이어집니다.

### 두 체인이 끼어드는 순서는 ECMAScript가 정한다

`then` 체인이 둘 있을 때 콜백이 어떤 순서로 실행되는지는 HTML이 아니라 ECMAScript가 정하는 부분이 있습니다. 먼저 ECMAScript는 Job을 언제 시작할 수 있는지 제약합니다. Job은 실행 중인 실행 컨텍스트가 없고 실행 컨텍스트 스택이 비었을 때 실행됩니다.

> At some future point in time, when there is no running context in the agent for which the job is scheduled and that agent's execution context stack is empty, the implementation must:

그리고 한 번에 하나씩 끝까지 실행됩니다.

> Once evaluation of a Job starts, it must run to completion before evaluation of any other Job starts in an agent.

그래서 then 콜백이 동기 코드가 끝난 뒤에 실행된다는 것 자체는 ECMAScript가 보장합니다. 예제 4에서 `동기 코드 끝`이 `a1`보다 먼저 찍히는 근거가 이 요구입니다. HostEnqueuePromiseJob은 이 제약 안에서 구체적인 시점과 큐를 호스트에 맡기는 호스트 정의 연산이고, ECMAScript는 이 연산으로 넣은 Job의 실행 순서에 대해 이렇게 요구합니다.

> Jobs must run in the same order as the HostEnqueuePromiseJob invocations that scheduled them.

HostEnqueuePromiseJob으로 넣은 Job은 넣은 순서대로 실행되어야 한다는 요구입니다. 모든 Job이 아니라 이 연산으로 넣은 프로미스 Job에 대한 요구입니다. 이 요구와 [프로미스](/concepts/promise)에서 본 절차를 합치면 예제 4의 순서가 나옵니다. 체인 `a`의 첫 `then`과 체인 `b`의 첫 `then`은 프로미스가 이미 이행되어 있어 등록 즉시 Job이 큐에 들어갑니다. `a1`의 Job이 실행되어 콜백이 끝나야 `then`이 돌려준 새 프로미스가 이행되고, 그제야 다음 `then`인 `a2`의 Job이 큐 맨 뒤에 붙습니다. 그때 큐에는 이미 `b1`의 Job이 있으므로 `b1`이 `a2`보다 먼저 실행됩니다. 같은 이유로 `b2`는 `a2` 뒤에, `a3`은 `b2` 뒤에 실행됩니다. 결과는 `a1`, `b1`, `a2`, `b2`, `a3`입니다. 이 설명은 콜백이 프로미스(thenable)가 아닌 값을 반환하는 경우입니다. 콜백이 프로미스를 반환하면 [프로미스](/concepts/promise)에서 본 채택 절차 때문에 다음 Job이 들어가는 때가 달라지므로 이 순서를 그대로 적용할 수 없고, 이 페이지는 그 경우의 순서를 다루지 않습니다. 정리하면 Job은 스택이 비었을 때 하나씩 끝까지 실행된다는 것, then 콜백이 끝나야 다음 Job이 들어가는 절차, 프로미스 Job을 넣은 순서대로 실행하라는 요구는 ECMAScript가 정하고, 스택이 빈 뒤 언제 실행할지(체크포인트)와 `queueMicrotask`·타이머 같은 다른 일과의 상대 순서는 호스트(HTML)가 정합니다. 예제 4는 `then` 체인이 만든 Job 순서만 보려고 타이머·DOM 같은 호스트의 스케줄링 API 없이(출력용 `console.log`만 사용) ECMAScript 코드로 실행합니다.

### 스크립트 요소 사이와 타이머 콜백 사이

체크포인트가 스택이 빌 때 일어난다는 규칙은 태스크 안에서도 똑같이 적용됩니다. 스크립트 요소 두 개가 있으면 첫 스크립트의 실행이 끝나 스택이 비는 순간 정리 단계가 체크포인트를 합니다. 그래서 첫 스크립트가 넣은 마이크로태스크는 둘째 스크립트가 실행되기 전에 실행됩니다. 이 순서는 예제 5가 보입니다. 두 스크립트 요소가 같은 태스크에서 처리되는지는 문서가 어떻게 도착하는지(둘째 스크립트가 외부 파일인지, 응답이 나뉘어 오는지 등)에 따라 달라질 수 있으므로, 예제 5는 다른 태스크(타이머 등)와의 순서에 기대지 않고 마이크로태스크와 둘째 스크립트의 순서만 확인합니다. 타이머 콜백도 마찬가지입니다. 콜백이 부른 `queueMicrotask`의 콜백은 콜백이 끝나 스택이 비는 때 실행되고, 다음 타이머 콜백은 별도의 태스크라서 그다음에 실행됩니다. 예제 6에서 `a`의 마이크로태스크는 그 마이크로태스크보다 먼저(스크립트에서) 등록된 0ms 타이머 `b`보다 앞섭니다. 이 두 경우는 정리 단계의 규칙에 따른 것이고, 출력은 Chromium에서 관찰한 값입니다.

### 리스너 사이

같은 이벤트의 리스너 두 개 사이에서 체크포인트가 일어나는지는 리스너를 누가 불렀는지에 달렸습니다. 표준은 정리 단계(와 그 짝인 준비 단계)가 스크립트 실행 도중에 다시 불릴 수 있음을 주석으로 적습니다.

> These algorithms are not invoked by one script directly calling another, but they can be invoked reentrantly in an indirect manner, e.g. if a script dispatches an event which has event listeners registered.

스크립트가 이벤트를 디스패치하면 등록된 리스너를 부를 때 이 알고리즘들이 스크립트가 아직 실행 중인 상태에서 다시(재진입으로) 불린다는 뜻입니다. `요소.click()`이 그런 경우입니다. 예제 7에서 `click()`을 부른 전역 코드는 리스너가 끝나도 스택에 남아 있습니다. 리스너 1이 끝난 정리 단계에서 스택이 비어 있지 않으므로 체크포인트를 하지 않고, 리스너 2도 마찬가지입니다. 체크포인트는 `click() 뒤`가 찍힌 다음 전역 코드가 끝나 스택이 비었을 때 일어나 `마이크로태스크 1`, `마이크로태스크 2`가 실행됩니다.

반대로 브라우저가 태스크 안에서 리스너를 부르면 그 리스너 밖에는 스택에 아무것도 없습니다. `postMessage`는 표준에 따라 posted message 태스크 소스의 태스크를 큐에 넣습니다.

> Queue a global task on the posted message task source given targetWindow to run the following steps:

예제 8에서는 이 message 태스크가 리스너 1을 부르고, 리스너 1이 끝나면 스택이 비어 정리 단계가 체크포인트를 하므로 `마이크로태스크 1`이 리스너 2보다 먼저 실행됩니다. 리스너 2도 끝나면 같은 일이 일어납니다. 같은 이벤트의 리스너 사이에서 마이크로태스크가 끼어드는지가 `click()`과 message에서 다른 이유는 이렇게 스택에 전역 코드가 남아 있는지의 차이입니다.

실제 사용자 클릭은 표준이 이렇게 정합니다.

> Events sent in response to user input (e.g., click events) must be fired using tasks queued with the user interaction task source.

사용자 입력에 대한 이벤트는 사용자 상호작용 태스크 소스의 태스크로 디스패치됩니다. 그러면 message와 같은 방식으로 리스너마다 스택이 비어 체크포인트가 일어난다고 이 표준 서술에서 이끌어 낼 수 있습니다. 다만 이것은 표준 서술에서 이끌어 낸 설명이며, 이 페이지의 테스트는 브라우저의 입력 경로를 거치는 클릭을 만들지 않아 실행으로 확인하지 않았습니다. 이 페이지의 테스트가 확인한 것은 코드가 부른 `click()`의 결과뿐입니다.

### 이 페이지가 다루지 않는 것

체크포인트 안에서 일어나는 처리되지 않은 거부 알림, IndexedDB 트랜잭션 정리 같은 단계는 다루지 않습니다. HTML 파서가 script 종료 태그를 처리할 때처럼 정리 단계와 처리 모델 말고도 체크포인트를 하는 곳이 있지만, 이 페이지의 예제는 두 곳으로 설명할 수 있어 나머지는 다루지 않습니다. 렌더링 갱신과 `requestAnimationFrame`, `MutationObserver`도 다루지 않습니다. `async`/`await`와 `try...catch`는 별도 개념(작성 예정)이고, Node.js의 큐는 다루지 않습니다.

### 흔한 오해

<Callout type="misconception" title="마이크로태스크는 지금 태스크가 끝나야만 실행된다">

체크포인트는 태스크가 끝난 뒤에만 일어나는 것이 아닙니다. 태스크 안에서도 스크립트나 콜백이 끝나 스택이 비면 정리 단계가 체크포인트를 합니다. 예제 8에서는 같은 message 태스크 안인 리스너 1과 리스너 2 사이에서 `마이크로태스크 1`이 실행되었습니다. 반대로 예제 7처럼 스택에 전역 코드가 남아 있으면 리스너가 끝나도 체크포인트가 일어나지 않습니다.

</Callout>

<Callout type="misconception" title="Promise 콜백은 우선순위가 높아 언제든 먼저 실행된다">

ECMAScript 명세의 주석(비규범)은 웹 브라우저와 Node.js가 프로미스 Job을 다른 일보다 높은 우선순위로 다룬다고 적습니다.

> For example, web browsers and Node.js treat Promise-handling Jobs as a higher priority than other work; future features may add Jobs that are not treated at such a high priority.

하지만 HTML 표준에서 이것은 언제든 먼저 실행된다는 뜻이 아니라, 스택이 비는 때의 체크포인트에서 실행된다는 시점으로 나타납니다. 타이머 콜백은 별도의 태스크라서 지금 태스크와 그 안의 체크포인트가 끝난 다음에 꺼내지므로, 예제 1과 예제 3에서 `타이머 0ms`가 마지막에 나왔습니다. 반대로 예제 7에서는 마이크로태스크가 이미 큐에 있어도 스택에 전역 코드가 남아 있는 동안에는 실행되지 않고 `click() 뒤`가 먼저 찍혔습니다.

</Callout>

<Callout type="misconception" title="click()으로 확인한 순서가 실제 클릭에도 그대로 적용된다">

`click()`은 스크립트 실행 도중에 이벤트를 그 자리에서 디스패치하므로 리스너가 끝나도 전역 코드가 스택에 남습니다. 그래서 예제 7에서 마이크로태스크는 `click() 뒤` 다음에 실행되었습니다. 실제 사용자 클릭은 표준에 따라 사용자 상호작용 태스크 소스의 태스크로 디스패치되므로 message와 같은 방식으로 리스너마다 체크포인트가 일어난다고 표준 서술에서 이끌어 낼 수 있습니다. 다만 이 페이지의 테스트는 입력 이벤트를 만들지 않아 실제 클릭을 확인하지 않았습니다.

</Callout>

<Callout type="misconception" title="체인 하나의 then은 다 끝난 뒤 다음 체인으로 넘어간다">

한 체인의 `then` 콜백이 모두 끝난 뒤에 다른 체인이 시작되지 않습니다. 앞 콜백이 끝나야 다음 `then`의 Job이 큐 맨 뒤에 붙으므로 두 체인이 번갈아 실행됩니다. 예제 4의 출력은 `a1`, `b1`, `a2`, `b2`, `a3`입니다. 이 순서는 then의 절차와 프로미스 Job을 넣은 순서대로 실행하라는 ECMAScript의 요구에서 나오며, 호스트(HTML)는 그 Job을 마이크로태스크 큐에 넣어 체크포인트에서 실행합니다.

</Callout>
