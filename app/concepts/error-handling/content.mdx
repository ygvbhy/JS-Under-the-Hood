`finally` 블록의 `return`은 왜 `try` 블록의 `return`을 덮어쓸까요? `try`에서 `return`했는데도 `finally`는 실행되고, `finally`가 `return`하면 앞선 `return`은 사라집니다. 반대로 `finally`에서 변수를 바꿔도 이미 `return`한 값은 그대로입니다. 이 페이지는 이 질문에서 출발해 `try` 문이 끝날 때 결과가 정해지는 규칙, 에러가 호출 스택을 따라 전파되는 방식, async 함수의 `try`에서 `return p`와 `return await p`가 다른 이유, 그리고 `try`가 잡지 못하는 에러와 거부(타이머 콜백의 `throw`와 처리되지 않은 거부)가 어디로 가는지를 예제 열세 개로 차례로 확인합니다. `try`, `catch`, `finally`, `throw`는 ECMAScript 언어의 동작이고, `error`·`unhandledrejection`·`rejectionhandled` 이벤트와 타이머는 브라우저가 제공하며 WHATWG HTML 표준이 정하고, `console`은 호스트가 제공하는 API입니다. 언어 예제 아홉 개의 출력은 Node.js의 `vm`에서, 브라우저 예제 네 개의 출력은 Chromium에서 실제로 실행한 값입니다. 이 페이지는 [실행 컨텍스트](/concepts/execution-context), [프로미스](/concepts/promise), [마이크로태스크 큐](/concepts/microtask-queue), [타이머](/concepts/timers), [async/await](/concepts/async-await)를 전제합니다.

## 동작 원리

### finally는 앞선 완료를 잠시 두고 실행된다

명세는 문장을 평가한 결과를 완료(Completion Record)라는 값으로 설명합니다. 문장이 순서대로 끝나면 정상(normal) 완료이고, `return`은 값을 담은 return 완료를, `throw`는 던진 값을 담은 throw 완료를 만듭니다. `return`·`throw`처럼 `break`와 `continue`도 각각 정상이 아닌 완료(abrupt completion)를 만듭니다. 블록은 정상이 아닌 완료를 만난 문장 뒤의 문장을 평가하지 않고 그 완료를 자기 완료로 삼습니다. 완료는 명세가 동작을 설명하려고 쓰는 장치이고, 엔진이 이런 레코드를 실제로 만든다는 뜻이 아닙니다.

`try` 문은 이 완료를 써서 `finally`를 실행합니다. `try` 블록의 평가가 끝나면 그 완료가 어떤 것이든 `finally` 블록을 평가합니다. 예제 1에서 `work()` 안의 `return`은 함수를 그 자리에서 끝내지 않고 return 완료를 만들어 `try` 블록의 결과로 삼습니다. 그다음 `finally` 블록이 평가되어 `finally`가 찍히고, `finally`가 정상 완료하므로 앞서 만든 return 완료가 `try` 문의 결과가 되어 `work`가 그 값을 돌려줍니다. `console.log(work())`는 `work`가 값을 돌려준 뒤에 실행되므로 `try`, `finally`가 찍힌 다음에야 `return 값`이 찍힙니다.

`finally`는 `try` 문을 평가하는 도중에 실행되는 블록입니다. `try` 문에 이르기 전에 함수가 끝났다면(앞선 `return`이나 예외) 실행되지 않습니다. `try` 블록의 평가가 끝나지 않아도 실행되지 않습니다. 예를 들어 `try` 블록 안에서 멈춘 제너레이터가 재개되지 않으면 `finally`는 실행되지 않습니다.

### finally가 try 문의 결과를 정하는 규칙

`try` 문의 결과는 명세의 TryStatement 평가 단계가 정합니다. 판마다 단계의 문장과 변수 이름이 다르므로 인용하지 않고, 두 판에 공통인 흐름을 풀어 씁니다.

1. `try` 블록을 평가해 완료를 얻습니다.
2. `catch`가 있고 그 완료가 throw 완료이면, 던진 값을 `catch`의 매개변수에 담아 `catch` 블록을 평가합니다. 이때부터 앞선 완료로 취급되는 것은 `catch` 블록의 완료입니다. `catch`가 없거나 throw 완료가 아니면 `try` 블록의 완료가 그대로 남습니다.
3. `finally`가 있으면 `finally` 블록을 평가합니다.
4. `finally`의 완료가 정상이면 앞선 완료(`try` 또는 `catch`의 완료)가 `try` 문의 결과입니다. 정상이 아니면 `finally`의 완료가 결과이고, 앞선 완료는 버려집니다. `finally`가 없으면 앞선 완료가 곧 결과입니다.

예제 2에서 `finally`의 `return 'finally'`는 return 완료이므로 정상이 아닙니다. 그래서 `try` 블록이 만든 return 완료는 버려지고 `pick()`은 `finally`를 돌려줍니다.

예제 5는 이 규칙을 세 가지로 보입니다. 첫째, `hide()`의 `try` 블록은 throw 완료로 끝나지만 `finally`가 return 완료를 만들므로 예외는 버려지고 `삼킴`이 반환됩니다. 둘째, `leave()`의 `finally`에 있는 `break`도 정상이 아닌 break 완료를 만듭니다. 이 완료가 `try` 문의 결과가 되어 앞선 return 완료를 버리고, `while` 문이 break 완료를 받아 반복을 끝내므로 그 뒤의 `return '루프 뒤'`가 실행됩니다. 셋째, `replace()`는 `try`의 예외 뒤에 `finally`가 새 예외를 던집니다. `finally`의 throw 완료가 결과가 되므로 바깥의 `catch`는 `finally의 예외`를 받습니다.

### return 값은 이미 정해져 있다

`return`이 만드는 return 완료의 값은 `return`을 평가하는 시점에 정해집니다. ReturnStatement의 평가는 `return` 뒤의 식을 평가해 값을 얻고

> Let exprValue be ? GetValue(exprRef).

그 값을 담은 return 완료를 돌려줍니다.

> Return ReturnCompletion(exprValue).

예제 3의 `return x`는 식 `x`를 평가한 값 `1`이 return 완료에 담깁니다. 이어서 `finally`의 `x = 2`는 변수 `x`의 바인딩만 바꾸고 return 완료에 이미 담긴 값은 건드리지 않습니다. `finally`는 정상 완료하므로 앞선 return 완료가 결과가 되어 `keep()`은 `1`을 돌려줍니다. `finally x = 2`는 `keep()` 안에서 찍히고 반환값 `1`은 `keep()`이 끝난 뒤 바깥의 `console.log`가 찍으므로, 출력은 `finally x = 2`, `1` 순서입니다.

값이 객체이면 return 완료에 담기는 것이 그 객체입니다. 예제 4의 `reassign`에서 `finally`의 `o = { v: 2 }`는 변수 `o`에 새 객체를 대입할 뿐 return 완료에 담긴 객체는 그대로이므로, 반환된 객체의 `v`는 `1`입니다. `mutate`에서는 `finally`의 `o.v = 2`가 return 완료에 담긴 바로 그 객체의 프로퍼티를 바꿉니다. 반환된 것과 `finally`가 변경한 것이 같은 객체이므로 호출한 쪽이 받은 객체에서 변경이 보여 `2`입니다. 재할당은 변수만 바꾸고 변경은 객체 자체를 바꾼다는 점이 두 결과를 가릅니다.

### 에러는 호출 스택을 따라 전파된다

`throw`는 던진 값을 담은 throw 완료를 만듭니다(`throw` 문의 평가 단계는 판마다 문장이 달라 인용하지 않습니다). 던질 수 있는 값은 `Error` 객체로 한정되지 않습니다. 예제 7의 첫 `try`는 문자열을 던지고 `catch`의 매개변수 `e`는 그 문자열이어서 `typeof e`가 `string`입니다. 언어 동작이 던지는 에러도 같은 throw 완료입니다. `null.x`처럼 `null`의 프로퍼티를 읽으면 TypeError가 던져지고, `e.name`은 `TypeError`입니다. TypeError 인스턴스의 프로토타입 체인에는 `TypeError.prototype`과, `TypeError.prototype`이 상속하는 `Error.prototype`이 있으므로 `e instanceof TypeError`와 `e instanceof Error`가 모두 `true`입니다. 던진 값을 쓰지 않으면 `catch (e)` 대신 바인딩 없는 `catch { ... }`를 쓸 수 있고, 마지막 `try`가 그 경우입니다.

throw 완료는 정상이 아닌 완료이므로, 함수 안에서 던져지면 그 문장 뒤의 문장은 평가되지 않고 함수 호출 식도 같은 throw 완료로 끝납니다. 그 완료는 호출한 쪽의 문장으로 올라가고, 바깥 함수의 문장도 같은 완료로 끝나며, `finally`가 다른 완료로 바꾸지 않는 한 `catch`가 있는 `try` 문에 닿을 때까지 이어집니다. 예제 6에서 `inner`가 던진 에러는 `middle`의 `try` 블록에서 `inner()` 호출 뒤의 `console.log`를 건너뜁니다. `middle`의 `try`에는 `catch`가 없으므로 앞서 본 규칙의 4단계가 적용됩니다. `finally`가 `middle finally`를 찍고 정상 완료하므로 앞선 throw 완료가 그대로 결과가 되어 에러는 `middle` 밖으로 나갑니다. `outer`의 `console.log`도 건너뛰고, 바깥의 `try...catch`가 `잡음: 전파`를 찍은 뒤 `이어서 실행`이 찍힙니다. 이 과정에서 `inner`, `middle`, `outer`의 [실행 컨텍스트](/concepts/execution-context)는 차례로 스택에서 빠집니다.

### async 함수의 try와 return await

[async/await](/concepts/async-await)에서 본 대로 async 함수의 `return`은 호출이 돌려준 프로미스를 `return`한 값으로 resolve합니다. 예제 8의 `noAwait`에서 `return Promise.reject(...)`는 프로미스를 기다리지 않습니다. ReturnStatement에서 `return`한 값을 `await`하는 단계는 async 제너레이터에만 적용되고 async 함수에는 적용되지 않기 때문입니다. 그래서 `try` 블록은 거부된 프로미스를 값으로 담은 return 완료로 곧바로 끝나고, `catch`는 실행되지 않습니다. 함수 본문이 끝난 뒤에야 AsyncBlockStart가 `[[Resolve]]`를 부르고 호출이 돌려준 프로미스가 `return`한 프로미스를 따라가며 거부되므로, 이 거부는 `try` 문 바깥에서 일어납니다.

`withAwait`의 `return await Promise.reject(...)`는 다릅니다. `await`는 함수를 멈추고, 거부된 프로미스의 반응이 실행될 때 멈춘 지점에서 예외가 던져진 것처럼 이어집니다. 그 지점이 `try` 블록 안이므로 `catch`가 잡고 `catch가 잡음`을 `return`하며, 호출이 돌려준 프로미스는 이행됩니다. 출력에서 `withAwait`가 먼저 나오는 것은, `noAwait`의 거부가 프로미스를 resolve하는 경로(async/await 페이지 예제 5)를 거쳐 Job이 더 필요하기 때문입니다. 이 순서는 이 예제의 Job 순서이며 일반 규칙이 아닙니다.

같은 차이가 `finally`에도 그대로 나타납니다. `return p`는 `p`를 기다리지 않고 `try` 블록을 곧바로 끝내므로, `p`가 아직 대기 중이어도 `finally`가 실행됩니다. `return await p`는 `p`의 결과가 정해져 재개된 뒤에 `finally`가 실행됩니다. `finally`에서 정리하는 코드가 `p`의 작업이 끝난 뒤에 실행되어야 한다면 이 차이가 결과를 바꿉니다. 예제 9가 이 순서를 보입니다.

### try 밖에서 난 에러: 타이머와 error 이벤트

여기서부터는 ECMAScript가 아니라 호스트(브라우저)의 동작이며 주로 WHATWG HTML 표준이 정합니다. `setTimeout`은 콜백을 나중에 실행할 태스크로 예약할 뿐입니다([타이머](/concepts/timers), [이벤트 루프](/concepts/event-loop)). 예제 10에서 `try` 블록은 타이머를 예약하고 `try 끝`을 찍은 뒤 끝나고, 스크립트도 `스크립트 끝`을 찍고 끝납니다. 콜백은 그 뒤의 태스크에서 실행되므로 콜백이 던질 때 바깥 `try` 문은 이미 끝나 있습니다. 그래서 `catch`가 실행될 수 없고 `catch: ...`는 찍히지 않습니다.

타이머의 콜백은 HTML 표준의 타이머 초기화 단계가 이 문장대로 호출합니다.

> invoke handler given arguments and "report", and with callback this value set to thisArg.

HTML이 넘긴 `"report"`는 Web IDL의 콜백 호출(invoke) 단계에서, 콜백이 던진 예외를 HTML 표준의 "report an exception" 단계로 넘기라는 뜻입니다. 이 단계는 전역 객체에 `error` 이벤트를 발화하는데, 이벤트의 cancelable 속성이 `true`입니다. 리스너가 `event.preventDefault()`를 부르면 이벤트가 취소되어 처리된 것으로 칩니다. 취소되지 않으면 표준은 사용자 에이전트가 예외를 개발자 콘솔에 보고할 수 있다(may)고 정합니다. 이 사이트의 실행기는 보고된 에러를 실패로 처리하므로 모든 전역 에러 예제의 리스너는 `preventDefault()`를 부르고, 취소하지 않는 경우는 표준의 서술일 뿐 예제로 실행해 보이지 않습니다. 예제 10의 출력에서 `error 이벤트: 타이머 안`이 찍힌 뒤에도 `다음 타이머`가 찍히는 것은, 한 콜백의 예외가 다른 타이머의 실행을 막지 않기 때문입니다. 같은 지연으로 먼저 예약한 타이머가 먼저 실행되는 순서도 표준이 정하므로, 두 타이머는 등록 순서대로 실행됩니다.

### 처리되지 않은 거부: unhandledrejection과 rejectionhandled

`Promise.reject(...)`는 예외를 던지지 않고 거부된 프로미스를 돌려줄 뿐입니다. 예제 11의 `try` 블록은 예외 없이 `try 끝`까지 실행되고 `catch`는 실행되지 않습니다. 반응이 등록된 적 없는(`[[PromiseIsHandled]]`가 false인) 프로미스가 거부되면 ECMAScript는 호스트에 알리는 HostPromiseRejectionTracker를 "reject" 동작과 함께 부르고, 브라우저는 그 프로미스를 about-to-be-notified 목록에 넣습니다. `then`·`catch`·`finally` 호출과 `await`는 모두 PerformPromiseThen을 거치며 이 표시를 true로 바꿉니다. 거부 핸들러 없이 `p.then(f)`만 불러도 `p`는 처리된 것으로 표시되고, 대신 `then`이 돌려준 프로미스가 거부되어 알림 대상이 됩니다. 스크립트가 끝난 뒤 마이크로태스크 체크포인트에서 [마이크로태스크 큐](/concepts/microtask-queue)가 비면, 표준의 "notify about rejected promises" 단계가 이 목록으로 일을 합니다. 이 단계는 목록을 복제해 두고 원본을 비운 뒤 전역 태스크를 큐에 넣습니다.

> Queue a global task on the DOM manipulation task source given global to run the following step:

그 태스크는 복제한 목록의 프로미스를 하나씩 보면서 이미 처리된 프로미스를 건너뜁니다.

> If p.[[PromiseIsHandled]] is true, then continue.

처리되지 않은 프로미스에는 전역 객체에 `unhandledrejection` 이벤트(cancelable)를 발화합니다. 그래서 예제 11에서는 `스크립트 끝` 뒤에 `unhandledrejection: 거부`가 찍힙니다. 스크립트가 끝난 뒤의 태스크에서 일어나므로 `try` 문과는 아무 관련이 없습니다.

예제 12는 이 목록에서 빠지는 경우입니다. 거부된 프로미스 `p`는 목록에 들어가지만, `Promise.resolve().then(...)`의 콜백이 마이크로태스크 체크포인트 안에서 `p.catch`를 부릅니다. `p.catch`가 `then`을 거쳐 PerformPromiseThen에 이르면 호스트에는 "handle" 동작이 전달되고, 프로미스가 아직 about-to-be-notified 목록에 있으면 목록에서 빠집니다. 큐를 비운 뒤의 알림 단계에는 알릴 프로미스가 없으므로 `unhandledrejection`은 발화하지 않고 `마이크로태스크에서 잡음`만 찍힙니다.

예제 13은 이벤트가 이미 발화한 뒤에 잡는 경우입니다. 알림 단계는 이벤트를 발화한 뒤에도 프로미스가 여전히 처리되지 않았다면 그 프로미스를 전역의 outstanding rejected promises 집합에 넣어 둡니다. 예제의 `unhandledrejection` 리스너는 `preventDefault()`를 부르고 타이머로 `p.catch`를 예약합니다. 그 타이머 콜백이 `p.catch`를 부르면 "handle" 동작이 프로미스가 집합에 있는 것을 보고 집합에서 빼면서 `rejectionhandled` 이벤트를 발화할 전역 태스크를 큐에 넣습니다. `catch` 콜백은 타이머 콜백 직후의 마이크로태스크 체크포인트에서 실행되어 `뒤늦게 잡음`을 찍고, `rejectionhandled`는 이미 큐에 들어간 별도의 태스크이므로 현재 태스크와 그 체크포인트가 끝난 뒤에 실행됩니다. 그래서 `unhandledrejection`, `뒤늦게 잡음`, `rejectionhandled` 순서입니다. 이 순서는 이벤트 리스너 안에서 예약한 타이머와 마이크로태스크 체크포인트로 구성한 것이며, 서로 다른 태스크 소스 사이의 순서를 일반 규칙으로 주장하지 않습니다.

### 이 페이지가 다루지 않는 것

`Error`의 `cause`, `AggregateError`, `stack`(ECMAScript 표준이 아님), 사용자 정의 에러 클래스는 다루지 않습니다. 스크립트 최상위에서 잡히지 않은 예외와 `onerror` 핸들러 속성, 다른 출처 스크립트의 `Script error.`, 워커의 에러, Node.js의 `process` 이벤트도 다루지 않습니다. 최상위 `await`는 [ES 모듈](/concepts/es-modules)에서 다룹니다. 시뮬레이터는 `catch`가 없는 `try...finally`만 단계별로 보이고, `catch`를 거치는 경우는 위 규칙과 예제로 설명했습니다. 완료는 명세의 설명 장치이며, 명세 링크는 현재 초안을 가리키고 인용은 ES2026판과 현재 초안에 똑같이 있는 문장만 씁니다.

## 결과와 이유

예제 1~13의 출력은 두 가지 규칙으로 읽을 수 있습니다. 언어 쪽 규칙은 `try` 문이 `try`(또는 `catch`)의 완료를 얻은 뒤 `finally`를 평가하고, `finally`가 정상 완료하면 앞선 완료가, 정상이 아니면 `finally`의 완료가 결과가 된다는 것입니다. `return`의 값은 평가하는 시점에 완료에 담기고, `throw`는 `finally`가 다른 완료로 바꾸지 않는 한 호출 스택을 따라 `catch`에 닿을 때까지 전파되며, async 함수의 `return p`는 `p`를 기다리지 않으므로 호출이 돌려준 프로미스의 거부가 `try` 밖에서 일어납니다. 호스트 쪽 규칙은 콜백에서 잡히지 않은 예외는 report an exception을 거쳐 `error` 이벤트로, 처리되지 않은 채 남은 거부는 `unhandledrejection`으로 알려지고, 뒤늦게 처리되면 `rejectionhandled`가 발화한다는 것입니다. 어느 쪽도 `try` 문의 `catch`로 가지 않습니다. 다음 표는 예제마다 결과와 근거를 정리한 것입니다. 결과 열은 meta의 출력과 같고, 그 출력은 테스트가 실제 실행과 대조합니다. 근거 열은 이 페이지에서 설명한 명세의 연산과 실행 결과(예제 1~9는 Node.js의 `vm`, 예제 10~13은 Chromium)를 뜻합니다.

<Callout type="misconception" title="finally는 return이 끝난 뒤에 실행되므로 결과를 못 바꾼다">

`finally`가 있는 `try` 문에서 `try` 블록의 `return`은 return 완료를 만들 뿐이고, 함수가 돌아가기 전에 `finally`가 평가됩니다. `finally`가 정상 완료하면 앞선 완료가 결과로 남지만, `finally`가 `return`, `break`, `continue`, `throw`로 정상이 아닌 완료를 만들면 그 완료가 결과가 되어 앞선 `return`이나 예외는 버려집니다. 예제 2에서 `pick()`은 `finally`를 돌려주었고, 예제 5에서는 `finally`의 `return`이 예외를 삼키고 `break`가 `return`을 버렸습니다.

</Callout>

<Callout type="misconception" title="return x 뒤 x를 바꾸면 반환값도 바뀐다">

`return x`는 식 `x`를 평가한 값을 return 완료에 담습니다. 이후 `finally`에서 `x`에 재할당해도 변수만 바뀝니다. 예제 3에서 `finally x = 2`가 찍혔지만 `keep()`은 `1`을 돌려주었습니다. 다만 값이 객체이면 `finally`가 그 객체를 변경한 것이 반환된 객체에서 보입니다. 예제 4의 `mutate`가 `2`를 돌려준 것은 반환된 것과 변경된 것이 같은 객체이기 때문이고, 같은 상황에서 변수에 새 객체를 대입한 `reassign`은 `1`을 돌려주었습니다.

</Callout>

<Callout type="misconception" title="try로 감싸면 안에서 예약한 콜백의 에러도 잡힌다">

`try` 문이 다루는 것은 그 문이 평가되는 동안의 완료뿐입니다. 예제 10에서 `setTimeout`의 콜백은 `try` 문이 끝난 뒤의 태스크에서 실행되므로 `catch`가 아니라 전역 `error` 이벤트로 보고되었습니다. 예제 11에서 `Promise.reject`는 예외를 던지지 않고 거부된 프로미스를 돌려줄 뿐이어서 `catch`가 실행되지 않았고, 처리되지 않은 거부는 `unhandledrejection` 이벤트로 알려졌습니다.

</Callout>

<Callout type="misconception" title="async 함수의 try는 return한 프로미스의 거부도 잡는다">

async 함수의 `return p`는 `p`를 기다리지 않습니다. `try` 블록은 return 완료로 끝나고 `p`의 거부는 `try` 문이 끝난 뒤 함수의 프로미스에 반영되므로 `catch`가 잡지 못합니다. 예제 8에서 `noAwait`의 프로미스는 거부되었고, `return await p`를 쓴 `withAwait`는 `await` 자리에서 예외가 던져져 `catch`가 잡았습니다.

</Callout>
