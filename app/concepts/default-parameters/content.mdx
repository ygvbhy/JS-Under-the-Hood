## 동작 원리

`var x = 'outer'`가 있는 스크립트에서 `function read(get = function () { return x; }) { var x = 'body'; … }`를 부르면, 기본값으로 만들어진 `get` 안의 `x`는 본문의 `var x`가 아니라 바깥의 `x`를 읽습니다. 본문에 같은 이름의 `var`가 있는데 왜 보이지 않을까요? 이 질문에 답하려면 기본값 식이 언제, 어떤 순서로, 어느 환경에서 평가되는지를 알아야 합니다. 이 페이지는 호출 때 평가되는 기본값 식, 인수·기본값·본문의 순서, 왼쪽부터 평가와 초기화 전 상태, 함수의 `length`, 매개변수 스코프와 같은 이름의 `var`, `arguments`와의 연결, 함수 안의 `'use strict'` 제약, 필수 인수 패턴을 예제 열두 개로 살펴보고, 마지막에 이 규칙들을 가르는 두 조건을 표로 정리합니다. 함수 호출은 [함수 호출](/concepts/function-calls), 초기화 전 상태는 [TDZ](/concepts/tdz), 함수가 만들어진 환경을 기억하는 방식은 [클로저](/concepts/closure), `arguments`와 rest 파라미터는 [화살표 함수](/concepts/arrow-functions)에서 본 것을 전제합니다.

### 기본값 식은 호출할 때 평가된다

기본값 식은 함수를 만들 때 평가되지 않습니다. 매개변수에 대응하는 값이 `undefined`일 때, 그 호출에서 매개변수를 초기화하는 단계에 평가됩니다(명세: SingleNameBinding은 초기화식이 있고 값이 `undefined`일 때만 초기화식을 평가합니다). 그래서 기본값이 필요한 호출마다 식이 다시 평가되고, 식이 객체 리터럴이면 호출마다 새 객체가 만들어집니다(예제 1). 인수가 `undefined`가 아니면 식은 평가되지 않습니다(예제 2). 무엇이 `undefined`로 취급되는지는 [함수 호출](/concepts/function-calls)에서 본 규칙 그대로입니다.

### 인수, 기본값, 본문의 순서

호출식은 먼저 인수를 왼쪽부터 평가합니다. 그 값으로 함수가 호출되면 FunctionDeclarationInstantiation이 매개변수 바인딩을 만들고 왼쪽부터 초기화하는데, 기본값 식은 이 초기화 안에서 평가됩니다. 본문 문장은 그 단계가 모두 끝난 뒤에 실행됩니다(예제 3). 기본값 식이 예외를 던지면 본문은 시작하지 않습니다(예제 12).

### 왼쪽부터, 매개변수도 초기화 전이 있다

매개변수는 왼쪽부터 차례로 초기화됩니다. 오른쪽 매개변수의 기본값 식은 이미 초기화된 왼쪽 매개변수를 읽을 수 있습니다(예제 4의 `height = width`). 반대로 아직 초기화되지 않은 오른쪽 매개변수나 자기 자신을 읽으면 ReferenceError입니다(예제 5). 바깥에 같은 이름이 있어도 매개변수 바인딩이 먼저 만들어져 가리므로 바깥 값을 읽지 않습니다. `function f(x = x)`로 바깥 `x`를 기대하는 실수가 이 경우입니다. 기본값 안의 함수는 호출될 때 이름을 읽으므로, 뒤 매개변수가 초기화된 뒤에 호출하면 오류가 나지 않습니다. 명세에서 매개변수 바인딩은 CreateMutableBinding으로 먼저 만들어지고, 초기화는 왼쪽부터 InitializeBinding으로 이루어집니다. 그 사이의 바인딩은 [TDZ](/concepts/tdz)에서 본 초기화 전 상태라서 읽으면 ReferenceError입니다. 중복된 이름이 있을 때만 `undefined`로 미리 초기화되는데, 단순하지 않은 매개변수 목록에서 이름이 중복되면 조기 오류이고 식이 있는 목록은 항상 단순하지 않으므로 이 경우에는 해당하지 않습니다.

### 함수의 length

함수의 `length`는 ExpectedArgumentCount가 정합니다. rest 파라미터 또는 초기화식이 있는 첫 매개변수 왼쪽에 있는 매개변수의 개수입니다. 그 뒤에 기본값이 없는 매개변수가 있어도 세지 않습니다. `(a, b = 1, c)`의 `length`는 `1`입니다(예제 6).

### 매개변수 스코프

'매개변수 스코프'는 명세 용어가 아니라 이 현상을 가리키는 관용 표현입니다. 명세가 정하는 것은 함수를 호출할 때 어떤 조건에서 환경 레코드가 몇 개 만들어지느냐입니다. 함수 환경 레코드는 호출을 준비할 때, 나머지는 FunctionDeclarationInstantiation에서 만듭니다. 이 페이지는 매개변수 바인딩이 들어 있는 레코드를 매개변수 레코드, 본문의 `var`가 들어 있는 레코드를 본문 var 레코드라고 부릅니다.

두 레코드가 나뉘는 조건은 매개변수 목록에 식이 있는가(명세의 ContainsExpression)입니다. 식이 없으면 본문의 `var`는 매개변수와 같은 레코드를 쓰고, 이미 있는 이름은 새 바인딩을 만들지 않습니다. 식이 있으면 본문 var 레코드를 따로 만들고, 매개변수 레코드가 그 바깥이 됩니다. 명세 NOTE가 적은 취지는 매개변수 목록의 식이 만든 클로저가 함수 본문의 선언을 보지 못하게 하려는 것입니다. 이 조건은 식이 무엇인지를 따지지 않아서, 기본값이 리터럴 `1`이어도 본문 var 레코드는 따로 만들어집니다. 초기화식이 없어도 패턴의 계산된 키가 있으면 식이 있는 것으로 치지만, 패턴은 [스프레드와 디스트럭처링](/concepts/spread-destructuring)에서 다루므로 이 페이지는 다루지 않습니다.

기본값 안의 익명 함수 식과 화살표 함수는 평가될 때의 LexicalEnvironment를 `[[Environment]]`로 가집니다([클로저](/concepts/closure)). 기본값은 매개변수를 초기화하는 동안 평가되므로 그때의 LexicalEnvironment는 매개변수 레코드이고, 이 함수는 자기 호출의 환경에 없는 이름을 매개변수 레코드부터 바깥으로 찾습니다. 본문 var 레코드는 매개변수 레코드의 안쪽이라 이 경로에 없습니다. 예제 7의 `get`이 본문의 `x`가 아니라 바깥의 `x`를 읽는 까닭입니다. 기본값이 화살표 함수나 메서드 축약의 매개변수에 있어도 결과는 같습니다. 본문의 함수 선언은 본문 var 레코드에, `let`·`const`·클래스 선언은 그 안쪽 렉시컬 레코드(strict mode에서는 본문 var 레코드)에 있으므로 기본값 안의 함수에서 마찬가지로 보이지 않습니다.

시뮬레이터의 그림은 이 구조를 단순화합니다. 명세는 sloppy mode 함수에서 매개변수 목록에 식이 있으면 레코드를 네 개 만듭니다. 이름 바인딩이 없는 함수 환경 레코드, 매개변수 레코드, 본문 var 레코드, 그리고 본문의 let·const·클래스 선언을 담는 렉시컬 레코드입니다. 명세 NOTE를 보면 매개변수 레코드와 렉시컬 레코드를 따로 두는 것은 둘 다 직접 eval을 처리하기 위해서입니다. strict mode 함수는 함수 환경 레코드가 매개변수를 맡고, 본문 var 레코드가 let·const까지 맡아 레코드가 두 개입니다. 시뮬레이터는 매개변수 레코드, 본문 var 레코드, 전역 레코드만 그리므로, 본문을 실행하는 동안의 LexicalEnvironment도 렉시컬 레코드 대신 본문 var 레코드로 표시합니다.

### 매개변수와 같은 이름의 var

매개변수 목록에 식이 있으면, 본문 var 레코드를 만들 때 var 이름마다 바인딩을 만들고 그 이름이 매개변수와 같으면 그 매개변수의 값으로 초기화합니다. 그래서 `var x;`만 있어도 `x`는 `undefined`가 아니라 인수로 받은 값을 보여 줍니다(예제 8의 3번 줄). 하지만 두 바인딩은 서로 다른 레코드에 있는 별개의 바인딩이므로, 이후의 재할당은 본문 var 레코드의 `x`만 바꾸고 매개변수 레코드의 `x`는 그대로입니다. 매개변수 레코드를 보는 `get`은 처음 값을 읽습니다.

본문에 `var x`가 없으면 본문의 `x`는 매개변수 레코드의 바인딩 자체이므로, 재할당이 `get`에게도 보입니다(예제 9). 매개변수 목록에 식이 없는 함수에서는 처음부터 같은 바인딩이라 이 차이가 없습니다. 매개변수 목록에 식이 있든 없든 같은 이름을 `let`으로 선언하면 SyntaxError입니다(`function f(a = 1) { let a; }`).

### arguments와의 연결

화살표 함수가 아닌 함수가 sloppy mode이고 매개변수 목록이 단순하면, 매핑된 `arguments`를 만들어 넘긴 인수에 대응하는 매개변수의 재할당이 `arguments[i]`에 보입니다. 기본값, rest 파라미터, 패턴이 하나라도 있어 목록이 단순하지 않거나(명세의 IsSimpleParameterList가 `false`) strict mode이면 매핑되지 않은 `arguments`가 만들어져 둘이 끊깁니다. 예제 10에서 기본값이 없는 `plain(0)`은 `arguments[0]`이 `2`가 되고, 기본값이 있는 `withDefault(0)`은 `0` 그대로입니다. 예제 파일에는 `'use strict'`가 없어 sloppy mode이고, strict mode에서는 `plain(0)`도 `0`입니다. `arguments.length`는 넘긴 인수의 개수이며 기본값은 영향을 주지 않습니다. 자세한 `arguments`의 성질은 [화살표 함수](/concepts/arrow-functions)의 `arguments` 설명을 보세요.

### 함수 안의 'use strict'는 금지

매개변수 목록이 단순하지 않은데(기본값, rest 파라미터, 패턴) 그 함수의 본문에 `'use strict'` 지시어가 있으면 SyntaxError입니다. 파일 첫 줄의 `'use strict'`는 괜찮습니다. 예제 11은 이 오류를 잡으려고 `new Function`으로 코드를 컴파일해 봅니다. 함수 선언에 직접 쓰면 스크립트 전체가 실행되기 전에 SyntaxError가 나서 다른 줄도 실행되지 않기 때문입니다.

### 필수 인수 패턴

기본값 식은 필요할 때만 평가되므로, 오류를 던지는 함수의 호출식을 기본값 식으로 두면 값이 `undefined`인 호출, 곧 인수를 빠뜨렸거나 `undefined`를 넘긴 호출만 잡을 수 있습니다(예제 12). `undefined`가 아닌 인수를 넘기면 그 함수는 호출되지 않습니다. `null`은 `undefined`가 아니므로 기본값이 쓰이지 않고 그대로 통과합니다.

### 두 조건 비교표

앞에서 본 규칙은 두 조건으로 갈립니다. 매개변수 목록에 식이 있는지는 본문 var 레코드를 따로 만드는지를 정하고, 매개변수 목록이 단순한지는 `arguments` 연결과 함수 안의 `'use strict'` 허용을 정합니다. 기본값은 식이 있고 단순하지도 않은 사례일 뿐이고, 두 조건은 서로 다릅니다. `...이름` 형태의 rest 파라미터만 있는 목록은 식이 없지만 단순하지도 않습니다.

## 결과와 이유

### 예제 1

5번 줄과 6번 줄은 인수 없이 `makeBox`를 부르므로 `box`가 `undefined`이고, 호출마다 1번 줄의 기본값 식 `{ count: 0 }`이 새로 평가되어 서로 다른 객체가 만들어집니다. 각각 `count`가 `1`이 되어 7번 줄은 `1 1 false`를 출력합니다. 9번 줄과 10번 줄은 `undefined`가 아닌 `shared`를 넘기므로 기본값 식이 평가되지 않고, 같은 객체의 `count`가 두 번 늘어 11번 줄은 `2`를 출력합니다.

### 예제 2

6번 줄 `tag`의 `id`가 `undefined`인 호출은 9번 줄의 첫째, 둘째, 마지막 `tag()`입니다. 이 세 번만 `nextId()`가 평가되어 `1`, `2`, `3`을 돌려줍니다. `tag(100)`과 `tag(null)`은 `undefined`가 아니라서 식이 평가되지 않고 `100`과 `null`이 그대로 나옵니다. 그래서 9번 줄은 `1 2 100 null 3`이고, `nextId()`가 세 번 불렸으므로 10번 줄은 `3`입니다.

### 예제 3

8번 줄 `run(note('인수 a'))`에서 호출 전에 인수 `note('인수 a')`가 평가되어 `인수 a`가 출력되고, `a`가 이 값으로 초기화됩니다. 5번 줄의 `b`와 `c`는 인수가 없어 `undefined`이므로 매개변수 초기화 중에 왼쪽부터 기본값 식이 평가되어 `b 기본값`, `c 기본값`이 출력됩니다. 그 뒤에 본문 6번 줄이 실행되어 `본문 시작`이 마지막에 나옵니다.

### 예제 4

1번 줄 `box(width, height = width, area = width * height)`에서 `height`의 기본값 식은 이미 초기화된 `width`를 읽습니다. `box(3)`은 `height`가 `3`, `area`가 `9`이고, `box(3, 4)`는 `height`가 `4`라 `area`만 기본값으로 `12`가 됩니다. `box(3, undefined, 0)`의 둘째 인수 `undefined`는 기본값 판단에서 인수가 없을 때와 같아 `height`는 `3`이 되고, 셋째 인수 `0`은 `undefined`가 아니라 `area`의 기본값 식은 평가되지 않아 `0`이 됩니다. 출력은 `3 3 9`, `3 4 12`, `3 3 0`입니다.

### 예제 5

3번 줄 `late(a = b, b = 1)`을 인수 없이 부르면 `a`의 기본값 식이 `b`를 읽는 시점에 `b`는 아직 초기화 전이라 ReferenceError입니다. 1~2번 줄의 바깥 `a`, `b`가 있어도 매개변수 바인딩이 먼저 만들어져 가리므로 바깥 값 `'outer'`를 읽지 않습니다. 6번 줄 `self(a = a)`에서 기본값 식이 읽는 `a`는 초기화 중인 자기 자신이라 역시 초기화 전이고 ReferenceError입니다. 19번 줄 `late(5)`는 `a`에 값이 있어 `b`를 읽지 않고 `b`만 `1`로 초기화되어 `5`를, `self(6)`은 `6`을 돌려줘서 `5 6`이 출력됩니다.

### 예제 6

`none(a, b)`는 기본값이 없어 `length`가 `2`이고, `last(a, b = 1)`은 `b`에서 세기를 멈춰 `1`, `first(a = 1, b)`는 첫 매개변수부터 기본값이라 `0`입니다. 7번 줄이 출력하는 `middle(a, b = 1, c)`는 `b`에서 세기를 멈추고 뒤의 `c`는 기본값이 없어도 세지 않으므로 `1`이고, `rest(a, ...others)`는 rest 파라미터 왼쪽의 `a`만 세어 `1`입니다.

### 예제 7

2번 줄 `read`의 매개변수 목록에는 식이 있으므로 3번 줄의 `var x`는 매개변수 레코드와 다른 본문 var 레코드에 만들어집니다. `read()`를 인수 없이 부르면 `get`이 `undefined`라서 기본값의 함수 식이 평가되는데, 이때의 LexicalEnvironment가 매개변수 레코드라서 이 함수의 `[[Environment]]`는 매개변수 레코드입니다. 4번 줄 `get()` 안의 `x`는 매개변수 레코드(`get`과 `arguments`만 있음)에서 찾지 못하고 바깥 전역의 `x`인 `outer`에 닿습니다. 본문의 `x`는 3번 줄에서 재할당한 본문 var 레코드의 `body`입니다. 그래서 6번 줄은 `outer body`를 출력합니다.

### 예제 8

1번 줄의 매개변수 `x`는 `'arg'`입니다. 2번 줄에 `var x` 선언이 있으므로, 본문을 실행하기 전에 본문 var 레코드에 `x`가 만들어져 매개변수 값 `arg`로 초기화됩니다. 그래서 3번 줄은 `undefined`가 아니라 `arg`를 출력합니다. 4번 줄의 재할당은 본문 var 레코드의 `x`만 `body`로 바꿉니다. 5번 줄의 `x`는 `body`이지만 `get()`은 매개변수 레코드의 `x`를 읽으므로 `arg`이고, 출력은 `body arg`입니다.

### 예제 9

예제 8에서 `var x;`를 뺀 코드입니다. 매개변수 목록에 식이 있어 본문 var 레코드는 만들어지지만 `x` 바인딩은 그 안에 없습니다. 2번 줄의 `x = 'body'`는 매개변수 레코드의 바인딩을 재할당하고, 3번 줄의 `x`도 `get()` 안의 `x`도 같은 바인딩을 읽어 `body body`가 출력됩니다.

### 예제 10

1번 줄 `plain(a)`는 sloppy mode이고 목록이 단순해서 매핑된 `arguments`를 가지며, 2번 줄의 `a = 2`가 `arguments[0]`에 보여 `2`를 돌려줍니다. 5번 줄 `withDefault(a = 1)`은 목록이 단순하지 않아 매핑되지 않은 `arguments`를 가지므로, 같은 재할당 뒤에도 `arguments[0]`은 넘긴 인수 `0` 그대로입니다. 9번 줄은 `2 0`입니다. 13번 줄은 `arguments.length`를 돌려주는 `count`를 인수 없이, 인수 하나로, `undefined` 두 개로 불러 `0 1 2`를 출력합니다. 기본값이 있어도 `arguments.length`는 넘긴 인수의 개수입니다.

### 예제 11

`new Function(params, body)`로 매개변수 목록과 본문을 컴파일해 봅니다. 9번 줄은 목록이 단순한 `a`이고 본문에 지시어가 있어도 허용되므로 `ok`입니다. 10번 줄은 목록이 단순하지 않은 `a = 1`에 지시어가 있어 SyntaxError이고, 11번 줄은 같은 목록이어도 본문에 지시어가 없어 `ok`입니다.

### 예제 12

8번 줄의 `greet()`은 `name`이 `undefined`라서 4번 줄의 기본값 식 `required('name')`이 평가되고, `required`가 TypeError를 던져 본문은 시작하지 않습니다. `catch`에서 `TypeError name 인수가 필요합니다`가 출력됩니다. `greet('kim')`은 기본값 식이 평가되지 않아 `hi kim`입니다. `greet(null)`의 `null`은 `undefined`가 아니라서 기본값을 쓰지 않고 `hi null`이 됩니다.

### 흔한 오해

<Callout type="misconception" title="기본값은 함수를 만들 때 한 번만 평가된다">

기본값 식은 기본값이 필요한 호출마다 평가됩니다. 예제 1의 `makeBox()`는 호출마다 새 객체를 만들었고, 예제 2의 `nextId()`는 `undefined`인 호출 세 번에서만 불렸습니다.

</Callout>

<Callout type="misconception" title="null을 넘겨도 기본값이 쓰인다">

기본값은 값이 `undefined`일 때만 쓰입니다. 예제 2의 `tag(null)`은 `null`을, 예제 12의 `greet(null)`은 `hi null`을 돌려주었습니다.

</Callout>

<Callout type="misconception" title="기본값이 있어도 본문의 var x는 매개변수 x와 같은 변수다">

매개변수 목록에 식이 없으면 실제로 같은 바인딩이라 본문의 `var x = …`가 매개변수 값을 덮어씁니다. 하지만 식이 있으면 본문의 `var`는 별도 바인딩입니다. 같은 이름이면 매개변수의 값으로 시작하지만(예제 8의 3번 줄), 이후의 재할당은 매개변수 레코드를 바꾸지 않습니다(`get()`이 `arg`를 읽은 5번 줄). 본문에 `var`가 없으면 재할당이 매개변수 바인딩을 바꾸므로 `get()`도 바뀐 값을 읽습니다(예제 9).

</Callout>
