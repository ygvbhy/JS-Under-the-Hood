## 동작 원리

`'abc'.length`는 3이니 `length`는 글자 수처럼 보입니다. 그런데 이모지 하나인 `'😀'`의 `length`는 2입니다. 자바스크립트 문자열은 글자를 담는 것이 아니라 16비트 값을 나열한 것이고, `length`는 그 값의 개수이기 때문입니다. 이 페이지는 세 가지 단위를 구분합니다. 문자열을 이루는 16비트 값인 **코드 유닛**, 유니코드가 문자마다 붙인 번호인 **코드 포인트**, 그리고 사람이 화면에서 한 글자로 보는 단위입니다. 셋은 같을 때도 있지만 다를 때가 많고, 문자열 메서드가 어느 단위로 동작하는지 알면 결과를 예측할 수 있습니다.

### 문자열은 코드 유닛의 나열이다

명세는 문자열 타입을 0개 이상의 16비트 부호 없는 정수(요소)를 순서대로 나열한 것으로 정의하고, `length`는 이 요소의 개수입니다. 문자열의 내용을 해석하는 연산은 각 요소를 UTF-16 코드 유닛으로 봅니다. 엔진이 문자열을 메모리에 어떻게 저장하는지는 명세가 정하지 않으므로, 이 페이지는 언어가 보여 주는 단위인 코드 유닛만 이야기합니다.

유니코드 코드 포인트는 U+0000부터 U+10FFFF까지라서 16비트 하나에 다 들어가지 않습니다. U+FFFF 이하의 코드 포인트는 코드 유닛 하나로, 그보다 큰 코드 포인트는 코드 유닛 두 개로 나타냅니다. 이 두 개를 서로게이트 쌍이라 하고, 앞의 것(0xD800~0xDBFF)을 상위 서로게이트, 뒤의 것(0xDC00~0xDFFF)을 하위 서로게이트라고 부릅니다. 명세는 이 둘을 선행(leading) 서로게이트와 후행(trailing) 서로게이트라고 부르고, '상위'라는 이름과 달리 값은 상위 서로게이트 쪽이 더 작습니다. 😀은 U+1F600이라 상위 서로게이트 0xD83D와 하위 서로게이트 0xDE00의 쌍입니다. 완성형 한글 음절(U+AC00~U+D7A3)은 U+FFFF 이하라서 음절 하나가 코드 유닛 하나입니다. 같은 음절을 초성·중성·종성 자모로 풀어 쓰면 코드 유닛이 늘어납니다(예제 4).

예제 1의 2번 줄은 `'😀'`이 2, `'a😀b'`가 4, `'가나'`가 2입니다. 3번 줄의 `charCodeAt`은 그 위치의 코드 유닛 값을 돌려주므로 `d83d`와 `de00`입니다. 4번 줄의 `codePointAt`은 그 위치에서 시작하는 코드 포인트를 돌려줍니다. 0번 위치는 쌍의 앞이라 둘을 합친 `1f600`이고, 1번 위치는 쌍의 뒤라 합칠 상대 없이 그 코드 유닛 값 `de00`입니다. 5번 줄의 `String.fromCodePoint(0x1f600)`과 `'\u{1F600}'`은 코드 포인트로 문자열을 만들며, 둘 다 같은 두 코드 유닛이 되어 `smile`과 같습니다.

### 인덱스, slice, split은 코드 유닛 단위다

`text[1]`, `charAt`, `slice`, `split('')`, `indexOf`가 쓰는 위치는 모두 코드 유닛의 인덱스입니다. 그래서 서로게이트 쌍의 가운데를 자르면 쌍이 쪼개져 짝 없는 서로게이트가 남습니다. 짝 없는 서로게이트는 그것만으로 어떤 문자도 나타내지 않으므로 화면에 그리는 방법이 호스트마다 다릅니다. 이 페이지는 그런 값을 `JSON.stringify`로 출력합니다. `JSON.stringify`는 짝 없는 서로게이트를 `\ud83d`처럼 `\u`와 16진수 네 자리로 쓰도록 ES2019부터 명세가 정해 두었습니다.

예제 2의 2번 줄에서 `text[1]`과 `text.charAt(2)`는 😀의 두 코드 유닛을 하나씩 꺼내 `"\ud83d"`와 `"\ude00"`입니다. 3번 줄의 `slice(0, 2)`는 0번과 1번 코드 유닛을 잘라 `"a\ud83d"`이고, `'b'`의 위치는 코드 유닛으로 세어 `3`입니다. 4번 줄의 `split('')`은 빈 문자열을 구분자로 받으면 코드 유닛 하나씩 나누므로 이모지가 두 조각이 됩니다. 5번 줄처럼 그 배열을 뒤집어 다시 이으면 쌍의 순서까지 뒤집혀, 하위 서로게이트가 앞에 오는 깨진 문자열 `"b\ude00\ud83da"`이 됩니다.

### 문자열은 바뀌지 않는다

문자열은 원시 값이라 바꿀 수 없습니다([원시 값과 객체](/concepts/primitives-and-objects)). `word[0] = 'b'`처럼 인덱스에 대입해도 문자열의 첫 코드 유닛은 바뀌지 않습니다. 원시 값의 프로퍼티에 대입하면 명세는 그 문자열에 대응하는 String 객체를 만들어 대입을 시도하는데, String 객체의 인덱스 프로퍼티는 쓰기 불가(`writable: false`)이고 설정 불가(`configurable: false`)로 정의되어 있어 대입이 실패합니다. sloppy mode에서는 실패가 조용히 무시되고, strict mode에서는 TypeError가 납니다. `length`도 쓰기 불가라 대입이 실패하고, `toUpperCase` 같은 메서드는 원래 문자열을 바꾸지 않고 새 문자열을 돌려줍니다([원시 값의 메서드](/concepts/primitive-methods)).

예제 3의 2번 줄은 sloppy mode라 오류 없이 지나가고, 3번 줄의 `word`와 `word[0]`은 그대로 `cat`과 `c`입니다. 4번 줄은 `Object.getOwnPropertyDescriptor`로 인덱스 `0` 프로퍼티의 어트리뷰트를 보여 줍니다([프로퍼티 어트리뷰트와 접근자](/concepts/property-attributes)). 값은 `"c"`이고 `writable`과 `configurable`이 `false`입니다. 6번 줄에서 `word`는 여전히 `cat`이고 `toUpperCase`가 돌려준 새 문자열만 `CAT`입니다. 문자열을 "바꾸고" 싶다면 새 문자열을 만들어 변수에 다시 대입합니다.

### 같아 보여도 다른 문자열: 결합 문자와 normalize

유니코드에는 é처럼 미리 합쳐 둔 코드 포인트(U+00E9)도 있고, 기본 글자 e(U+0065) 뒤에 결합 양음 부호(U+0301)를 붙여 같은 모양을 만드는 방법도 있습니다. 화면에서는 똑같이 보이지만 코드 유닛이 다르므로 `length`도 다르고 `===`로 비교하면 `false`입니다. 명세의 어떤 연산도 문자열을 암묵적으로 정규화하지 않습니다. 유일한 예외는 내부에서 정규화한 뒤 비교하는 `localeCompare`인데, 결과가 로캘에 따라 달라 이 페이지에서는 다루지 않습니다. 같은 문자열로 다루려면 `normalize`를 직접 불러 정규화한 뒤 비교합니다. `normalize()`의 기본 형식 NFC는 합칠 수 있는 것을 합치고, `'NFD'`는 분해합니다. 한글도 마찬가지입니다. 완성형 음절 `'한'`을 NFD로 분해하면 초성 ㅎ, 중성 ㅏ, 종성 ㄴ의 자모 코드 포인트 세 개가 되어 코드 유닛도 세 개입니다. 다른 시스템에서 분해형 한글이 들어올 수 있는 곳에서는 비교하기 전에 정규화합니다.

예제 4는 보이지 않는 차이를 드러내려고 `\u` 이스케이프로 두 문자열을 씁니다. 3번 줄은 `1 2 false`입니다. 4번 줄에서 `decomposed.normalize()`는 e와 결합 부호를 합쳐 `composed`와 같아지고, `composed.normalize('NFD')`는 e와 결합 부호로 분해되어 길이가 2입니다. 5번 줄의 `'한'`은 완성형 음절 하나라 길이 1이고, NFD로 분해하면 자모 세 개라 3입니다.

### 이모지 조합: 사람이 보는 한 글자

가족 이모지 👨‍👩‍👧처럼 여러 이모지를 ZWJ(Zero Width Joiner, U+200D)라는 보이지 않는 코드 포인트로 이어 한 그림으로 보이게 하는 경우가 있습니다. 화면에서는 한 글자지만 문자열로는 이모지 세 개와 ZWJ 두 개, 곧 코드 포인트 다섯 개입니다. 이모지는 각각 서로게이트 쌍이라 코드 유닛은 6개, ZWJ는 U+FFFF 이하라 2개, 모두 8개입니다. 사람이 한 글자로 보는 단위(자소 클러스터)로 나누는 것은 ECMAScript 언어가 정하지 않습니다. 그 일을 하는 `Intl.Segmenter`는 국제화 API 명세(ECMA-402)에 있는 별도 기능입니다.

예제 5의 1번 줄은 이모지와 ZWJ를 이스케이프로 써서 무엇이 들어 있는지 보이게 했습니다. 2번 줄의 `length`는 `8`입니다. 3번 줄에서 2번 위치는 첫 이모지(0~1번)의 다음인 ZWJ라 `200d`입니다. 4번 줄의 `slice(0, 2)`는 첫 사람 이모지 하나만 잘라 `"👨"`이고, ZWJ로 나누면 이모지 세 조각이라 `3`입니다.

### 대소문자를 바꾸면 길이가 바뀔 수 있다

`toUpperCase`와 `toLowerCase`는 유니코드 문자 데이터베이스의 로캘에 상관없는 대소문자 매핑을 쓰도록 명세가 정합니다. 이 매핑에는 코드 포인트 하나가 여러 코드 포인트로 바뀌는 경우가 있어서, 결과 문자열의 길이가 원래와 다를 수 있습니다. 독일어 ß(U+00DF)의 대문자는 S 두 개, 곧 코드 포인트 둘(코드 유닛 둘)입니다. 바꾼 결과를 다시 소문자로 바꿔도 원래 문자열로 돌아온다는 보장도 없습니다. 언어별 규칙을 따르는 `toLocaleUpperCase`는 호스트와 로캘에 따라 결과가 달라질 수 있어 이 페이지에서 다루지 않습니다.

예제 6의 3번 줄은 `straße`가 6, 대문자 `STRASSE`가 7입니다. 4번 줄에서 `STRASSE`를 소문자로 바꾸면 `strasse`가 되어 원래의 `straße`와 같지 않습니다.

### 짝 없는 서로게이트 검사: isWellFormed

쌍을 쪼개면 짝 없는 서로게이트가 생기는데, 이런 문자열을 UTF-8 같은 다른 인코딩으로 바꾸거나 다른 시스템에 보내면 문제가 생길 수 있습니다. `isWellFormed`는 문자열에 짝 없는 서로게이트가 있으면 `false`, 없으면 `true`를 돌려줍니다. `toWellFormed`는 짝 없는 서로게이트를 대체 문자 U+FFFD(�)로 바꾼 새 문자열을 돌려줍니다. 두 메서드는 ES2024에 추가되었고 『모던 자바스크립트 Deep Dive』 출간 이후의 기능입니다.

예제 7의 2번 줄에서 `half`는 😀의 상위 서로게이트 하나만 잘라 낸 문자열입니다. 3번 줄은 `true false`입니다. 4번 줄의 `toWellFormed()`는 그 서로게이트를 U+FFFD 하나로 바꿔 `"�"`, 길이 `1`이고, 5번 줄에서 그 코드 포인트는 `fffd`입니다.

## 결과와 이유

### 예제 1

2번 줄은 `2 4 2`입니다. 😀(U+1F600)은 서로게이트 쌍이라 코드 유닛 두 개이고, `'a😀b'`는 a와 b를 더해 4개, 완성형 한글 음절 두 개인 `'가나'`는 2개입니다. 3번 줄은 `d83d de00`입니다. `charCodeAt`은 각 위치의 코드 유닛 값을 그대로 돌려줍니다. 4번 줄은 `1f600 de00`입니다. `codePointAt(0)`은 상위 서로게이트 다음에 하위 서로게이트가 있어 둘을 합친 코드 포인트를, `codePointAt(1)`은 하위 서로게이트에서 시작하므로 그 값을 돌려줍니다. 5번 줄은 `true true`입니다. 코드 포인트로 만든 두 문자열 모두 `smile`과 같은 코드 유닛 두 개입니다.

### 예제 2

2번 줄은 `"\ud83d" "\ude00"`입니다. 1번과 2번 코드 유닛은 😀의 상위·하위 서로게이트이고, 하나씩 꺼내면 짝이 없어 `JSON.stringify`가 이스케이프로 씁니다. 3번 줄은 `"a\ud83d" 3`입니다. `slice(0, 2)`는 0번과 1번 코드 유닛이고, `'b'`는 3번 코드 유닛입니다. 4번 줄은 `["a","\ud83d","\ude00","b"]`입니다. `split('')`은 코드 유닛 하나씩 나눕니다. 5번 줄은 `"b\ude00\ud83da"`입니다. 뒤집은 배열에서는 하위 서로게이트가 상위 서로게이트보다 앞에 있어 쌍을 이루지 못합니다.

### 예제 3

3번 줄은 `cat c`입니다. 2번 줄의 대입은 인덱스 프로퍼티가 쓰기 불가라 실패했고, sloppy mode라 오류 없이 무시되었습니다. 4번 줄은 `{"value":"c","writable":false,"enumerable":true,"configurable":false}`입니다. 문자열의 인덱스 프로퍼티는 이렇게 정의되어 있습니다. 6번 줄은 `cat CAT`입니다. `toUpperCase`는 새 문자열을 만들어 `upper`에 담았고 `word`는 바뀌지 않았습니다.

### 예제 4

3번 줄은 `1 2 false`입니다. `composed`는 U+00E9 코드 유닛 하나, `decomposed`는 e와 U+0301 코드 유닛 두 개이고, 코드 유닛이 다르니 같은 문자열이 아닙니다. 4번 줄은 `true 2`입니다. `normalize()`의 NFC는 e와 결합 부호를 U+00E9 하나로 합치고, NFD는 U+00E9를 e와 결합 부호로 나눕니다. 5번 줄은 `1 3`입니다. 완성형 음절 한(U+D55C)은 코드 유닛 하나이고, NFD는 이를 초성 ㅎ(U+1112), 중성 ㅏ(U+1161), 종성 ㄴ(U+11AB)으로 나눕니다.

### 예제 5

2번 줄은 `8`입니다. 이모지 세 개가 각각 코드 유닛 두 개라 6개, ZWJ 두 개가 2개입니다. 3번 줄은 `200d`입니다. 0번과 1번이 첫 이모지의 쌍이고 2번이 ZWJ입니다. 4번 줄은 `"👨" 3`입니다. 처음 두 코드 유닛은 첫 이모지의 온전한 쌍이라 `JSON.stringify`가 이모지 그대로 쓰고, ZWJ 두 개로 나누면 세 조각입니다.

### 예제 6

3번 줄은 `6 STRASSE 7`입니다. 로캘에 상관없는 대문자 매핑에서 ß는 SS가 되므로 한 코드 유닛이 두 코드 유닛으로 늘었습니다. 4번 줄은 `strasse false`입니다. S의 소문자는 s이므로 SS는 ß로 돌아가지 않습니다.

### 예제 7

3번 줄은 `true false`입니다. `smile`은 서로게이트 쌍이 온전하고, `half`는 상위 서로게이트만 남아 짝이 없습니다. 4번 줄은 `"�" 1`입니다. `toWellFormed`는 짝 없는 서로게이트를 U+FFFD 하나로 바꾼 새 문자열을 돌려줍니다. 5번 줄은 `fffd`입니다. `half`는 바뀌지 않고, 새 문자열의 코드 포인트가 U+FFFD입니다.

### 흔한 오해

<Callout type="misconception" title="length는 글자 수다">

`length`는 코드 유닛의 개수입니다. U+FFFF보다 큰 코드 포인트(대부분의 이모지)는 코드 유닛 두 개라서 `'😀'.length`는 2이고(예제 1), 여러 코드 포인트를 이은 이모지는 한 그림으로 보여도 8이 될 수 있습니다(예제 5). 코드 포인트 단위로 문자열을 도는 `for...of`와 스프레드는 이터레이션을 다루는 [이터러블과 for...of](/concepts/iterable-for-of)에서 다룹니다.

</Callout>

<Callout type="misconception" title="인덱스로 문자열의 한 글자를 바꿀 수 있다">

문자열은 원시 값이라 바뀌지 않고, 인덱스 프로퍼티는 쓰기 불가로 정의되어 있습니다(예제 3). sloppy mode에서는 대입이 조용히 무시되어 바뀐 줄 착각하기 쉽고, strict mode에서는 TypeError가 납니다. 바꾼 문자열이 필요하면 `slice`와 연결로 새 문자열을 만들어 다시 대입합니다.

</Callout>

<Callout type="misconception" title="보기에 같은 문자열은 ===로 같다">

`===`는 코드 유닛을 하나씩 비교합니다. 미리 합친 é와 e + 결합 부호처럼 화면에서 같아 보이는 문자열도 코드 유닛이 다르면 같지 않습니다(예제 4). 사용자 입력처럼 출처가 다른 문자열을 비교할 때는 `normalize`로 같은 형식으로 맞춘 뒤 비교합니다.

</Callout>

<Callout type="misconception" title="toUpperCase는 길이를 바꾸지 않는다">

대소문자 매핑에는 코드 포인트 하나가 여러 코드 포인트가 되는 경우가 있어 결과의 `length`가 달라질 수 있고, 다시 바꿔도 원래로 돌아오지 않을 수 있습니다(예제 6). 대소문자를 무시하고 비교하려고 한쪽만 바꿔 길이나 위치를 계산하면 어긋날 수 있습니다.

</Callout>
