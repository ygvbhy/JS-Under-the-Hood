지연이 이미 끝난 타이머 콜백이 있어도, 지금 실행 중인 코드가 끝나기 전에는 왜 실행되지 않을까요? 이 페이지는 이 질문에서 출발해 브라우저의 이벤트 루프가 태스크를 하나씩 꺼내 끝까지 실행하는 규칙을 확인합니다. 동기 코드가 길면 콜백이 늦어지는 이유, 콜백 안에서 예약한 타이머의 순서, 긴 작업을 쪼개는 방법, 큐를 거치지 않고 그 자리에서 실행되는 `click()`, 그리고 태스크 소스가 다르면 순서가 보장되지 않는 경우를 차례로 살펴봅니다. 이벤트 루프는 ECMAScript가 아니라 WHATWG HTML 표준이 정하는 호스트(브라우저)의 동작입니다. Node.js 같은 다른 호스트는 자기 나름의 이벤트 루프를 가지며 이 페이지의 규칙이 그대로 적용된다고 볼 수 없고, 이 페이지는 Node.js를 다루지 않습니다. 예제의 출력은 모두 테스트가 Chromium에서 실제로 실행해 얻은 값입니다. 이 페이지는 [실행 컨텍스트](/concepts/execution-context)에서 본 콜 스택과 [타이머](/concepts/timers)에서 본 타이머 콜백이 태스크로 예약된다는 설명을 전제합니다.

## 동작 원리

### 이벤트 루프는 태스크를 하나씩 꺼내 끝까지 실행한다

HTML 표준은 이벤트 루프가 태스크를 담는 큐를 가진다고 정합니다.

> An event loop has one or more task queues.

이벤트 루프의 처리 모델은 반복마다 큐 하나를 고르고 그 큐에서 실행할 수 있는(runnable) 첫 태스크를 꺼내 실행합니다. 어느 큐를 고를지는 구현이 정합니다.

> Let taskQueue be one such task queue, chosen in an implementation-defined manner.

고른 큐에서 태스크를 꺼내는 단계는 이렇습니다.

> Set oldestTask to the first runnable task in taskQueue, and remove it from taskQueue.

그리고 꺼낸 태스크의 단계를 실행합니다.

> Perform oldestTask's steps.

이 단계가 모두 끝나야 처리 모델의 다음 단계로 넘어가고, 다음 태스크는 그다음 반복에서 고릅니다. 그래서 태스크 하나가 실행되는 동안에는 다른 태스크가 끼어들 수 없습니다. 이 페이지는 이 성질을 '한 번에 태스크 하나, 끝까지 실행'이라고 부릅니다. 다른 자료에서 보는 '매크로태스크'는 표준 용어가 아니며, 표준은 이것을 그냥 태스크(task)라고 부릅니다.

스크립트 실행도 이 태스크 안에서 일어납니다. 표준은 HTML 파서의 일을 태스크의 예로 듭니다.

> The HTML parser tokenizing one or more bytes, and then processing any resulting tokens, is typically a task.

콜백을 부르는 일은 흔히 별도의 태스크로 이루어집니다.

> Calling a callback is often done by a dedicated task.

다만 원문도 '흔히(often)'라고 쓰듯 항상 그런 것은 아닙니다. 예제 5의 `click()` 리스너처럼 지금 실행 중인 태스크 안에서 바로 호출되는 콜백도 있습니다.

콜 스택은 ECMAScript에서 실행 컨텍스트 스택이라고 부르는 것입니다. 명세는 이 스택의 역할을 이렇게 적습니다. 자세한 내용은 [실행 컨텍스트](/concepts/execution-context)에서 다룹니다.

> The execution context stack is used to track execution contexts.

정리하면 이벤트 루프와 태스크 큐는 ECMAScript 언어가 아니라 HTML 표준이 정한 호스트의 구조이고, 스택은 그 태스크가 실행되는 동안 쌓이고 비워지는 실행 컨텍스트의 더미입니다. 이 페이지는 스택을 이름으로만 그리고, `setTimeout`이나 `console.log` 같은 호스트 함수의 프레임은 그리지 않습니다.

### 동기 코드가 끝나야 콜백이 실행된다

타이머는 지연이 끝나면 콜백을 실행하는 일을 타이머 태스크 소스의 태스크로 큐에 넣습니다. [타이머](/concepts/timers)에서 본 표준의 단계는 이렇습니다.

> Let completionStep be an algorithm step which queues a global task on the timer task source given global to run task.

지금 실행 중인 스크립트도 태스크 하나입니다. 이 태스크가 끝나기 전에는 큐에 들어온 콜백 태스크가 꺼내질 수 없으므로, 스크립트가 오래 걸리면 지연이 이미 끝난 콜백도 그만큼 기다립니다. 예제 1은 0ms 타이머 `a`와 10ms 타이머 `b`를 등록한 뒤 `while` 문으로 50ms 동안 스크립트를 붙잡습니다. 출력은 `스크립트 시작`, `스크립트 끝`, `a 0ms`, `b 10ms` 순서입니다. 두 타이머 모두 스크립트가 끝난 뒤에 실행됩니다.

`a 0ms`가 `b 10ms`보다 먼저 나오는 것은 [타이머](/concepts/timers)에서 본 순서 규칙, 즉 먼저 등록했고 지연이 같거나 짧은 타이머가 먼저 실행된다는 규칙이 보장합니다. 이 페이지는 50ms라는 정확한 값이 아니라 '붙잡은 동안에는 실행되지 못한다'는 순서만 확인합니다.

### 한 번에 태스크 하나: 준비된 콜백도 기다린다

콜백 태스크도 스크립트 태스크와 같습니다. 예제 2는 0ms 타이머 `a`와 `b`를 등록하고, `a`의 콜백 안에서 `while` 문으로 50ms 동안 붙잡습니다. `b`는 `a`와 같은 0ms라서 이미 실행될 수 있는 상태이지만, `a`의 태스크가 끝나기 전에는 꺼내지지 않습니다. 출력은 `a 끝`, `b, a가 50ms 이상 붙잡음 true`입니다. `b`는 `a`가 시작한 시각부터 50ms 이상 지난 뒤에 실행되었습니다.

여기서도 `a`가 `b`보다 먼저인 것은 타이머의 순서 규칙(먼저 등록했고 지연이 같으면 먼저)이 보장합니다. 이 페이지가 확인하는 것은 밀리초 값이 아니라 하한(50ms 이상)과 순서입니다. 콜백이 서로 다른 스레드에서 병렬로 실행되는 것이 아니라, 하나의 태스크가 끝나야 다음 태스크가 시작됩니다.

### 콜백 안의 예약과 작업 쪼개기

콜백 안에서 새 타이머를 등록하면 그 콜백도 지연이 끝난 뒤 새 태스크로 큐에 들어갑니다. 등록은 지금 일어나므로, 먼저 등록되었고 지연이 같거나 더 짧은 타이머보다 앞설 수 없습니다. 반대로 먼저 등록되었더라도 지연이 더 긴 타이머(예를 들어 먼저 등록한 100ms 타이머)보다는 앞설 수 있습니다. 예제 3은 0ms 타이머 `a`와 `b`를 등록한 뒤 `스크립트 끝`을 찍고, `a`의 콜백 안에서 0ms 타이머 `c`를 또 등록합니다. 출력은 `스크립트 끝`, `a 시작`, `a 끝`, `b`, `c`입니다. `c`는 `a`가 실행되는 동안 등록되었으므로 이미 기다리던 `b`보다 뒤에 실행됩니다. `b`가 `c`보다 먼저 등록되었고 지연이 같으므로 이 순서도 타이머의 순서 규칙이 보장합니다.

이 성질을 이용하면 긴 작업을 쪼갤 수 있습니다. 예제 4의 `work(i)`는 `조각 i`를 찍고, 3보다 작으면 다음 조각을 0ms 타이머로 예약합니다. 같은 0ms 타이머로 `다른 타이머`를 등록해 두면 출력은 `조각 1`, `다른 타이머`, `조각 2`, `조각 3`입니다. 조각 사이에 이미 큐에 있던 다른 태스크가 실행됩니다. `조각 2`의 타이머는 `다른 타이머`보다 나중에 등록되었고 지연이 같으므로 순서 규칙이 이 순서를 보장합니다. 다음 조각을 타이머로 예약해 일을 나누는 방식은 HTML 표준의 타이머 절에도 예시가 실려 있는데, 그 예시는 일을 시작하기 전에 다음 타이머를 먼저 등록하고 일이 끝났으면 `clearTimeout`으로 지우는 형태라서 예제 4와 순서가 다릅니다. 이 페이지는 그 코드를 인용하지 않습니다. 조각을 아주 많이 이어 예약하면 중첩 단계가 5를 넘은 뒤로는 4ms보다 짧은 지연이 4ms로 올라가는 규칙도 만나게 되는데, 이는 [타이머](/concepts/timers#setinterval과-clear는-같은-맵을-쓴다)에서 다룹니다. 예제 4는 중첩이 세 단계라 이 규칙에 걸리지 않습니다.

### click()은 큐를 거치지 않는다

`요소.click()`은 클릭 이벤트를 큐에 넣는 것이 아니라 그 자리에서 디스패치합니다. 표준의 `click()` 단계는 이렇습니다.

> Fire a synthetic pointer event named click at this element, with the not trusted flag set.

이벤트가 모두 태스크 큐를 거치는 것은 아닙니다. 표준은 이렇게 적습니다.

> Not all events are dispatched using the task queue; many are dispatched during other tasks.

그래서 예제 5에서 `save.click()`을 부르면 리스너가 `click() 뒤`를 찍는 다음 줄보다 먼저 실행되고, 0ms 타이머보다도 먼저 실행됩니다. 출력은 `click() 전`, `click 리스너`, `click() 뒤`, `타이머 0ms`입니다. 타이머 콜백은 스크립트 태스크가 끝난 뒤에 실행됩니다.

실제 사용자의 클릭은 다릅니다. 표준은 사용자 입력에 대한 이벤트를 이렇게 정합니다.

> Events sent in response to user input (e.g., click events) must be fired using tasks queued with the user interaction task source.

이 문장은 표준의 서술입니다. 이 페이지는 실제 사용자 입력을 만들 수 없으므로 실행으로 확인하지 않았고, 코드로 호출하는 `click()`의 결과만 확인합니다.

### 태스크 소스가 다르면 순서 보장이 없다

태스크마다 태스크 소스가 있습니다. 타이머는 타이머 태스크 소스를 쓰고, `window.postMessage`는 다른 소스를 씁니다. 표준의 `postMessage` 단계는 이렇습니다.

> Queue a global task on the posted message task source given targetWindow to run the following steps:

태스크 소스와 큐의 관계는 이렇게 정해집니다.

> For each event loop, every task source must be associated with a specific task queue.

소스마다 큐가 다를 수 있고, 어느 큐에서 꺼낼지는 앞서 본 대로 구현이 정합니다. 그래서 서로 다른 소스의 태스크 사이에는 표준이 보장하는 순서가 없습니다. 같은 소스 안에서는 순서가 지켜집니다.

> Note that in this setup, the processing model still enforces that the user agent would never process events from any one task source out of order.

예제 6은 `타이머 1`, `postMessage`, `타이머 2`를 차례로 등록합니다. 표준이 보장하는 것은 같은 타이머 태스크 소스의 `타이머 1`이 `타이머 2`보다 먼저라는 것뿐입니다. Chromium에서 관찰한 출력은 `타이머 1`, `message m`, `타이머 2`이지만, `message m`이 둘 사이에 나오는 것은 표준이 보장하는 순서가 아니라 이 페이지가 Chromium에서 본 결과입니다.

### 이 페이지가 다루지 않는 것

처리 모델은 태스크 하나를 실행한 뒤 이 단계를 거칩니다.

> Perform a microtask checkpoint.

마이크로태스크와 Promise는 이 페이지에서 다루지 않고, 마이크로태스크를 다루는 별도 개념(작성 예정)으로 남겨 둡니다. 창의 이벤트 루프에는 렌더링 갱신 기회도 있지만 이 페이지에서는 다루지 않습니다.

## 결과와 이유

예제 1~6의 출력은 모두 하나의 규칙으로 읽을 수 있습니다. 이벤트 루프는 태스크를 하나 고르고 그 단계를 모두 실행한 뒤에야 다음 태스크를 고릅니다. 스크립트와 타이머 콜백은 각각 태스크이고, 콜백 안에서 등록한 타이머는 먼저 등록되었고 지연이 같거나 더 짧은 타이머 뒤에 실행됩니다. `click()`은 태스크를 만들지 않고 그 자리에서 이벤트를 디스패치합니다. 서로 다른 태스크 소스의 순서는 표준이 보장하지 않고, 같은 소스 안의 순서만 보장됩니다.

### 흔한 오해

<Callout type="misconception" title="0ms 콜백은 동기 코드 중간에라도 끼어든다">

태스크는 한 번에 하나씩 끝까지 실행되므로 실행 중인 스크립트 중간에 콜백이 끼어들 수 없습니다. 예제 1에서 `a 0ms`는 50ms 동안 붙잡던 `스크립트 끝` 뒤에 나왔습니다.

</Callout>

<Callout type="misconception" title="콜백이 오래 걸려도 다른 준비된 콜백은 병렬로 실행된다">

타이머 콜백도 태스크로 실행되므로 하나가 끝나야 다음 태스크를 고릅니다. 예제 2에서 `b`는 `a`가 50ms 동안 붙잡는 동안 실행되지 못했고, `b, a가 50ms 이상 붙잡음 true`를 찍었습니다.

</Callout>

<Callout type="misconception" title="콜백 안에서 등록한 0ms 타이머는 바로 다음에 실행된다">

콜백 안에서 등록한 타이머는 그 순간에 등록되므로, 먼저 등록되었고 지연이 같거나 더 짧은 타이머가 먼저 실행됩니다([타이머](/concepts/timers)의 순서 규칙). 먼저 등록되었더라도 지연이 더 긴 타이머보다는 먼저 실행될 수 있습니다. 예제 3에서 `c`는 `a` 안에서 등록되었지만 `b` 뒤에 나왔고, 예제 4에서도 `조각 2`는 `다른 타이머` 뒤에 나왔습니다.

</Callout>

<Callout type="misconception" title="click()도 이벤트 루프를 거친다">

`click()`은 클릭 이벤트를 큐에 넣지 않고 그 자리에서 디스패치합니다. 예제 5에서 `click 리스너`는 `click() 뒤`보다 먼저, `타이머 0ms`보다도 먼저 나왔습니다. 실제 사용자 클릭은 표준이 사용자 상호작용 태스크 소스의 태스크로 정하지만, 이 페이지는 실제 입력을 만들 수 없어 실행으로 확인하지 않았습니다.

</Callout>

<Callout type="misconception" title="모든 비동기 콜백은 하나의 큐에서 등록 순서대로 실행된다">

태스크 소스마다 태스크 큐가 다를 수 있고 어느 큐에서 꺼낼지는 구현이 정합니다. 같은 소스 안의 순서만 보장되므로 예제 6에서 `타이머 1`이 `타이머 2`보다 먼저인 것만 보장되고, 그 사이의 `message m`은 Chromium에서 관찰한 결과일 뿐입니다.

</Callout>

<Callout type="misconception" title="이벤트 루프는 자바스크립트 언어의 일부다">

이벤트 루프와 태스크 큐는 ECMAScript가 아니라 WHATWG HTML 표준이 정하는 호스트의 동작입니다. 콜 스택에 해당하는 실행 컨텍스트 스택은 ECMAScript가 정하지만, 어떤 태스크를 언제 꺼내 실행할지는 호스트의 이벤트 루프가 정합니다. `setTimeout`, `console`, `postMessage`도 호스트 API입니다.

</Callout>
