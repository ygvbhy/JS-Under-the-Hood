import { Simulator } from './Simulator'
import { scenarios } from './scenarios'

`import`한 변수는 왜 저절로 바뀔까요? `count`를 `import`해 둔 모듈은 `count`에 대입한 적이 없는데도, `inc()`를 부르고 나면 `count`의 값이 바뀌어 있습니다. 반대로 그 모듈에서 `count = 5`를 쓰면 에러가 납니다. 이 페이지는 이 질문에서 출발해, `import`한 이름이 값이 아니라 다른 모듈의 바인딩(binding)을 가리킨다는 규칙을 모듈 환경과 간접 바인딩으로 설명하고, 모듈의 로드·링크·평가 순서, 순환 `import`, `default`와 네임스페이스, 동적 `import()`와 최상위 `await`, 브라우저가 맡는 로딩까지 예제 열여덟 개로 차례로 확인합니다. 바인딩, 모듈 환경, 링크 오류, 평가 순서, 네임스페이스, `import()` 구문, 최상위 `await`는 ECMAScript 언어의 동작이고, URL 해석, 모듈 맵, 지연 실행, `import.meta.url`의 값은 브라우저가 따르는 WHATWG HTML 표준이 정하며, `console`은 호스트가 제공하는 API입니다. 예제 열여덟 개의 출력은 모두 Chromium에서 실제로 실행한 값이고 다른 브라우저는 확인하지 않았습니다. 이 페이지는 [TDZ](/concepts/tdz), [스코프 체인](/concepts/scope-chain), [실행 컨텍스트](/concepts/execution-context), [script의 async와 defer](/concepts/script-async-defer), [프로미스](/concepts/promise), [async/await](/concepts/async-await)를 전제합니다.

## 동작 원리

### 모듈은 자기 환경을 가진다

ECMAScript 명세에서 모듈 코드는 모듈 환경 레코드(Module Environment Record)라는 환경에서 실행됩니다. 모듈마다 환경이 하나씩 있고, 그 바깥 환경은 전역 환경입니다. 모듈 코드가 클래식 스크립트와 다른 점을 세 가지로 나눠 봅니다.

첫째, 모듈 최상위의 `var`와 `let`은 그 모듈의 환경에 선언되는 바인딩입니다. 클래식 스크립트의 최상위 `var`가 전역 객체(`window`)의 프로퍼티가 되는 것과 달리 모듈의 최상위 `var`는 전역 객체의 프로퍼티가 되지 않고, 다른 모듈은 `export`하지 않은 이름을 볼 수 없습니다. 바깥 환경이 전역 환경이므로 클래식 스크립트가 선언한 전역 이름은 모듈 안에서도 보입니다. 클래식 스크립트의 최상위 `let`도 전역 객체의 프로퍼티는 아니므로, `let`에서 달라지는 것은 `window`가 아니라 다른 스크립트에서 보이는지입니다. 클래식 스크립트의 최상위 `let`은 뒤의 스크립트에서 보이지만([전역 객체](/concepts/global-object) 참고) 모듈의 최상위 `let`은 보이지 않습니다. 예제 6이 모듈 쪽을 확인합니다.

둘째, 모듈 환경 레코드는 항상 `this` 바인딩을 제공하고, 명세가 모듈의 `this`를 `undefined`로 정하므로 모듈 최상위의 `this`는 `undefined`입니다.

> Module Environment Records always provide a this binding.

셋째, 모듈 코드는 `'use strict';` 지시어가 없어도 항상 strict mode입니다.

> Module code is always strict mode code.

그래서 선언하지 않은 변수에 대입하면 ReferenceError가 나고, 일반 호출한 함수 안의 `this`도 `undefined`입니다. 예제 7이 이를 확인합니다.

### import는 값이 아니라 바인딩을 가리킨다

`import { count } from './counter.js'`가 만드는 `count`는 값을 담은 변수가 아닙니다. 명세는 모듈 환경 레코드가 변경할 수 없는 import 바인딩(immutable import binding)을 가진다고 설명합니다.

> immutable import bindings which are bindings that provide indirect access to a target binding

이런 바인딩을 만드는 연산 CreateImportBinding은 간접 접근을 이렇게 서술합니다.

> Accesses to the value of the new binding will indirectly access the bound value of the target binding.

이 페이지는 `import`한 쪽의 이름을 간접 바인딩(indirect binding), 그것이 가리키는 `export`한 모듈 안의 바인딩을 대상 바인딩(target binding)이라고 부릅니다. `count`를 읽으면 그 시점에 대상 바인딩의 값을 읽습니다. 그래서 `export`한 모듈 안에서 `count += 1`이 대상 바인딩의 값을 바꾸면, `import`한 쪽에서 `count`를 다시 읽을 때 바뀐 값이 보입니다. 이 동작을 흔히 라이브 바인딩(live binding)이라고 부르고, 예제 1이 보입니다. 간접 바인딩은 명세가 이 동작을 설명하려고 쓰는 장치이고, 엔진이 이런 구조를 실제로 만든다는 뜻이 아닙니다.

간접 바인딩은 변경할 수 없는 바인딩이고 모듈 코드는 strict mode이므로, `import`한 이름에 대입하면 TypeError입니다. 대상 바인딩이 변경할 수 있는 바인딩이어도 값을 바꾸는 대입은 그 바인딩이 있는 모듈 안의 코드에서만 할 수 있습니다. 예제 2가 이를 확인합니다. 여기서 구분할 것은 바인딩의 불변과 값의 변경입니다. 바인딩이 변경할 수 없다는 것은 그 이름에 다른 값을 대입할 수 없다는 뜻이고, 이름이 가리키는 객체의 프로퍼티를 바꾸는 것은 별개의 동작입니다. `const`로 `export`한 객체여도 `import`한 쪽이든 다른 모듈이든 그 객체의 프로퍼티는 바꿀 수 있고, 바꾼 결과는 같은 객체를 쓰는 모든 모듈에서 보입니다. 예제 3이 이를 보입니다. 객체의 변경은 [원시 값과 객체](/concepts/primitives-and-objects)에서 본 재할당과 변경의 구분과 같은 것입니다.

### 로드, 링크, 평가

모듈은 코드를 실행하기 전에 의존 모듈까지 준비하는 과정을 거칩니다. 명세는 모듈 레코드의 LoadRequestedModules, Link, Evaluate 메서드로 이 과정을 서술하고, 이 페이지는 그것을 로드, 링크, 평가라는 교육용 이름으로 부릅니다.

- 로드: `import` 선언과 `export … from` 선언의 모듈 지정자(specifier)를 요청으로 보고, 의존 모듈을 찾아 모듈로 만듭니다. 이 과정에서 모듈 코드는 실행되지 않습니다. 지정자를 URL로 해석하고 같은 URL의 모듈을 찾는 일은 ECMAScript가 아니라 호스트인 HTML이 맡습니다.
- 링크: 모듈 환경을 만들고, 이 선언들이 요구한 이름을 `export`한 모듈의 바인딩과 연결합니다. 요구한 이름을 찾지 못하거나 모호하면 이 단계에서 SyntaxError가 나고, 평가 단계로 넘어가지 않습니다. 함수 선언은 링크 단계에서 함수 값으로, `var`는 `undefined`로 초기화되고, `let`·`const`·`class` 바인딩은 만들어지기만 하고 초기화되기 전입니다.
- 평가: 모듈의 코드를 실행합니다. 평가는 깊이 우선(depth-first)이어서, 모듈은 자기 본문보다 먼저 자신이 `import`한 의존 모듈을 평가합니다(이미 평가 중인 모듈로 되돌아오는 순환은 아래에서 따로 봅니다). 선언이 파일 안의 어느 줄에 있는지는 본문과의 순서에 영향을 주지 않습니다. 의존 모듈은 선언이 쓰인 순서대로 평가를 시작합니다.

예제 8은 `import` 선언이 본문 중간에 있어도 의존 모듈이 먼저 평가되는 것을, 예제 9는 없는 이름을 `import`하면 링크에서 SyntaxError가 나고 의존 모듈조차 평가되지 않는 것을 보입니다.

같은 모듈이 한 번만 평가되는 이유는 두 층으로 나뉩니다. ECMAScript는 한 모듈 안에서 같은 지정자를 두 번 쓰면 하나의 요청으로 합치고, 같은 (참조하는 모듈, 요청) 쌍의 로드가 성공했다면 호스트가 그 뒤로도 같은 결과를 돌려주도록 요구합니다. 서로 다른 모듈이 같은 파일을 요청해도 같은 모듈을 얻는 것은 ECMAScript가 아니라 HTML의 모듈 맵이 URL로 모듈을 찾기 때문입니다. 평가를 마친 모듈 레코드는 다시 실행되지 않으므로 여러 모듈이 같은 의존 모듈을 `import`해도 그 모듈은 한 번 평가됩니다. 예제 4가 보입니다. 평가 중에 에러가 던져져 평가가 실패해도 모듈은 다시 실행되지 않습니다. 명세는 실패한 평가의 에러를 모듈에 기록해 두고, 이후의 요청에는 같은 에러를 돌려줍니다. 예제 5가 이를 보입니다.

### 순환 import와 TDZ

모듈 A가 B를 `import`하고 B가 다시 A를 `import`하는 순환(cycle)이어도 링크는 평가보다 먼저 끝나므로 모든 간접 바인딩이 연결됩니다. 평가에서는 깊이 우선으로 의존 모듈을 먼저 평가하되, 이미 평가가 진행 중인 모듈로 되돌아오면 다시 평가하지 않습니다. 그래서 A를 평가하다 B로 가고, B가 A의 이름을 쓰는 시점에 A의 본문은 아직 실행되지 않았습니다.

이때 A의 바인딩이 어떻게 보이는지는 선언 종류에 달려 있습니다. 함수 선언은 링크 단계에서 함수로 초기화되어 있으므로 B가 호출할 수 있습니다. `var`는 링크 단계에서 `undefined`로 초기화되어 있으므로 에러 없이 `undefined`로 읽힙니다. `let`과 `const`, `class`는 선언이 평가되기 전까지 초기화되지 않은 바인딩이므로 읽으면 ReferenceError입니다. 이것이 [TDZ](/concepts/tdz)입니다. 예제 10이 보입니다. 이 페이지는 TDZ를 모듈에 적용한 결과만 확인하고, TDZ 자체의 규칙은 TDZ 개념에서 다룹니다.

### default와 네임스페이스

`default`라는 이름으로 내보내는 대표적인 형태는 다음과 같고, 형태에 따라 그 이름이 가리키는 바인딩이 다릅니다.

- `export default 식`: 식의 값을 담는 바인딩이 만들어집니다. 명세는 이 바인딩의 이름을 합성 이름 `*default*`로 서술하고, 이 이름은 ECMAScript 코드나 링크 알고리즘에서 접근할 수 없는 명세 서술용 이름입니다. 식을 평가한 값이 이 바인딩에 담깁니다. 식이 `n`이라는 변수여도 `*default*`에 담기는 것은 그 시점의 `n`의 값이고, 이후에 `n`을 바꿔도 이 바인딩은 `n`을 따라가지 않습니다.
- `export { n as default }`: `n` 바인딩을 `default`라는 이름으로 내보냅니다. 새 바인딩이 아니라 `n`을 가리키므로 `n`이 바뀌면 `import`한 쪽에서도 바뀐 값이 보입니다.
- `export default function f() {}`처럼 이름 있는 함수 선언: 그 이름 `f`의 바인딩이 `default`로 내보내집니다. 모듈 안에서 `f`에 재할당하면 `import`한 쪽에도 보입니다. 이름 있는 클래스 선언도 그 이름의 바인딩입니다.
- `export default function () {}`처럼 이름 없는 함수·클래스 선언: `*default*` 바인딩을 쓰지만 식이 아니라 선언입니다. 그래서 이름 없는 함수는 링크 단계에서 함수로 초기화되고, 클래스는 평가될 때 초기화됩니다.

그래서 `default`가 라이브인지 아닌지는 `default`라는 이름이 아니라 어떤 바인딩을 가리키는지에 달려 있습니다. 예제 11이 앞의 세 경우를 비교합니다.

`import * as ns from ...`가 만드는 `ns`는 간접 바인딩이 아니라 모듈 네임스페이스 객체(module namespace exotic object)로 초기화된 변경할 수 없는 바인딩입니다. 라이브인 것은 이 객체의 프로퍼티입니다. 문자열 키는 내보낸 이름이고 코드 유닛 순으로 정렬되며, `default`로 내보낸 이름도 키에 들어갑니다. 프로토타입은 `null`이고 `Symbol.toStringTag`는 `'Module'`입니다. 각 프로퍼티의 값은 그 이름의 바인딩을 읽으므로 라이브입니다. 네임스페이스 객체의 `[[Set]]`은 항상 `false`를 돌려주므로 strict mode 코드의 대입은 TypeError입니다. 이미 있는 이름에 대입해도, 새 이름을 만들어도 마찬가지입니다. 예제 12가 보입니다.

`export * from './m.js'`는 `m.js`가 내보낸 이름을 다시 내보내되 `default`는 뺍니다. 두 `export *`가 같은 이름을 서로 다른 바인딩으로 내보내면 모호해져서 그 이름은 네임스페이스 객체의 키에서 빠지고, 그 이름을 지정해 `import`하면 SyntaxError입니다. 같은 바인딩으로 풀리면 모호하지 않고, 모듈이 직접 내보낸 이름은 `export *`의 이름보다 우선합니다. `export { x } from './m.js'`처럼 이름을 직접 적어 다시 내보낼 수도 있습니다. 다시 내보내는 모듈의 환경에는 `x` 바인딩이 생기지 않고, 그 모듈에서 `import`한 이름의 대상 바인딩은 링크 단계에서 `m.js`의 `x`로 풀립니다. 그래서 다시 내보낸 이름도 라이브입니다. 예제 13이 보입니다.

### 동적 import와 최상위 await

`import` 선언은 모듈 목표(Module)의 문법입니다. 클래식 스크립트(Script)에서 `import { x } from './m.js'`를 쓰면 SyntaxError입니다. 반면 `import('./m.js')`는 문장이 아니라 프로미스를 돌려주는 식이므로 클래식 스크립트에서도 쓸 수 있습니다. 이 프로미스는 모듈의 로드, 링크, 평가가 끝나면 모듈 네임스페이스 객체로 이행되고, 그 과정이 실패하면 거부됩니다. 예제 14에서 `eval`로 `import` 선언을 평가하면 SyntaxError가 나고, `import()`의 `then` 콜백은 클래식 스크립트가 끝난 뒤에 실행됩니다. 이 콜백이 스크립트의 동기 코드 뒤에 실행되는 것은 [프로미스](/concepts/promise)의 `then` 콜백이 항상 나중에 실행되는 규칙입니다.

최상위 `await`(top-level await)는 모듈의 최상위에서 쓰는 `await`이고 모듈에서만 쓸 수 있습니다. 최상위에 `await`가 있는 모듈의 평가는 [async/await](/concepts/async-await)의 `await`처럼 그 자리에서 멈췄다가 프로미스가 정해지면 이어집니다. 이 모듈을 `import`한 모듈은 그 평가가 끝날 때까지 자신의 본문을 실행하지 않고 기다립니다. 하지만 그 모듈과 의존 관계가 없는 형제 모듈은 기다리지 않고 평가됩니다. 멈추는 것은 최상위 `await`가 있는 그 모듈의 평가이고, 호출 스택이나 이벤트 루프가 아닙니다. 예제 15가 이를 보입니다. 두 가지 예외가 있습니다. 기다린 프로미스의 거부를 그 모듈 안에서 잡지 않으면 그 모듈의 평가가 실패하고 그 모듈을 `import`한 모듈의 본문은 실행되지 않습니다. 또 같은 순환 안에서는 이미 평가 중인 모듈로 되돌아온 쪽이 이 대기를 하지 않으므로, 최상위 `await`가 있는 모듈을 `import`했어도 먼저 실행될 수 있습니다.

### 브라우저가 맡는 부분

여기서부터는 ECMAScript가 아니라 호스트(브라우저)의 동작이며 WHATWG HTML 표준이 정합니다.

HTML 문서에 쓴 `<script type="module">`은 `async` 속성이 없으면 [script의 async와 defer](/concepts/script-async-defer)에서 본 `defer` 스크립트처럼 파싱이 끝난 뒤 실행됩니다. 표준은 파서가 넣은 모듈 스크립트에 `async`가 없으면 외부 클래식 스크립트의 `defer`와 같은 목록, 즉 문서 파싱이 끝났을 때 실행할 스크립트 목록에 넣는다고 정하며, 모듈 스크립트에 대해서는 이렇게 덧붙입니다.

> (The defer attribute has no effect on module scripts.)

그래서 `defer` 속성을 따로 붙이지 않아도 이런 모듈 스크립트는 이미 지연 실행이고, `defer` 속성은 모듈에 효과가 없습니다. 예제 16이 이를 보입니다. 이 페이지는 `async` 속성을 준 모듈 스크립트와 스크립트 코드로 문서에 넣은 모듈 스크립트는 다루지 않습니다.

모듈 맵(module map)은 문서나 워커마다 있는, 이미 가져온 모듈 스크립트를 보관하는 표준의 자료 구조입니다.

> A module map is a map keyed by tuples consisting of a URL record and a string.

키는 URL과 모듈 유형을 묶은 쌍입니다. 키에 URL이 들어가므로 같은 파일이라도 URL이 다르면 다른 모듈이고, URL의 조각(`#` 뒤)도 URL의 일부입니다. 그래서 예제의 문서처럼 `http://example.test/`에 있는 문서에서는 `./map-log.js`와 `/map-log.js`가 지정자 문자열이 달라도 같은 URL로 해석되어 모듈 맵이 같은 모듈을 돌려주므로 한 번 평가되지만, `./map-log.js#again`은 다른 URL이므로 따로 평가됩니다. 예제 17이 이를 보입니다.

모듈 지정자는 HTML의 규칙으로 URL로 해석됩니다. `./`, `../`, `/`로 시작하거나 URL로 해석되는 지정자는 URL이 됩니다. 이름만 쓴 `'counter.js'` 같은 지정자(bare specifier)는 import map으로 대응 URL이 지정되지 않았다면 해석 규칙이 TypeError를 던집니다. `import.meta`는 모듈 안에서 쓰는 ECMAScript 구문이고, 거기에 어떤 프로퍼티와 값이 들어가는지는 호스트가 정합니다. HTML은 `url` 프로퍼티를 정하고, 그 값은 모듈 스크립트의 base URL입니다. 외부 파일이면 그 파일의 응답 URL이고(리다이렉트가 없으면 요청한 주소입니다), 인라인 모듈은 자기 파일이 없으므로 문서의 base URL이며 예제에서는 문서 주소 `http://example.test/`입니다. 예제 18이 이를 보입니다.

### 이 페이지가 다루지 않는 것

Node.js의 모듈 동작과 CommonJS 호환, import map, import attributes와 JSON·CSS 모듈, 번들러, `export * as ns from`, `async` 속성을 준 모듈 스크립트와 스크립트 코드로 넣은 모듈 스크립트, `nomodule`, 다른 출처 모듈의 CORS, 워커 모듈, `import.meta.resolve`는 다루지 않습니다. 정적 `import`가 실패했을 때 `script` 요소의 `error` 이벤트나 전역 `error`로 어떻게 보고되는지도 다루지 않으며, 링크 실패와 평가 실패는 `import()`의 `catch`로 잡아 보입니다. 시뮬레이터는 모듈 환경의 바인딩 이름과 값, `import`의 대상만 그립니다. 명세 링크는 현재 초안을 가리키고 인용은 ES2026판과 현재 초안에 똑같이 있는 문장만 씁니다.

## 결과와 이유

예제 1~18의 출력은 두 갈래의 규칙으로 읽을 수 있습니다. 언어 쪽 규칙은 이름을 지정해 `import`한 이름이 값이 아니라 `export`한 모듈의 대상 바인딩에 대한 간접 바인딩이고 변경할 수 없다는 것입니다. 그래서 대상 바인딩이 바뀌면 `import`한 쪽에서도 바뀐 값이 보이고, 이름에 대입하면 TypeError입니다. 모듈은 자기 환경을 가지며 `this`는 `undefined`이고 항상 strict mode입니다. 링크가 평가보다 먼저 끝나므로 없는 이름은 평가 전에 SyntaxError이고, 순환에서는 함수 선언이 초기화되어 있는 반면 `let`·`const`는 초기화 전입니다. 평가는 깊이 우선으로 의존 모듈이 먼저이고, 평가를 마쳤거나 실패한 모듈은 다시 실행되지 않으며, 최상위 `await`는 그 모듈의 평가를 멈추고 그 모듈을 `import`한 모듈은 끝날 때까지 기다립니다. 호스트 쪽 규칙은 모듈 스크립트가 파싱이 끝난 뒤 실행되고, 모듈 맵이 URL과 모듈 유형의 쌍을 키로 모듈을 찾으며, 이름만 쓴 지정자와 `import.meta.url`의 값을 HTML이 정한다는 것입니다. 다음 표는 예제마다 결과와 근거를 정리한 것입니다. 결과 열은 Chromium에서 실행한 출력입니다. 근거 열은 이 페이지에서 설명한 명세의 연산과 표준의 절을 뜻합니다.

### 흔한 오해

<Callout type="misconception" title="import는 export한 값을 복사해 온다">

이름을 지정해 `import`한 이름은 값을 담은 변수가 아닙니다. 명세는 그 이름을 `export`한 모듈의 대상 바인딩에 대한 간접 바인딩으로 서술하고, 그 이름을 읽으면 대상 바인딩의 값을 읽습니다. 값을 복사해 온 것이라면 예제 1의 두 번째 출력이 `0`이어야 하지만 `1`이었습니다. 반대로 간접 바인딩은 변경할 수 없으므로, 예제 2에서 보았듯 `import`한 쪽에서 대입하면 TypeError입니다. 바꿀 수 있는 쪽은 바인딩이 있는 모듈 안의 코드뿐입니다. 간접 바인딩은 명세의 설명 장치이며 엔진 구조를 서술한 것이 아닙니다.

</Callout>

<Callout type="misconception" title="const로 export하면 객체의 내용도 바꿀 수 없다">

`const`와 `import`가 막는 것은 이름에 다른 값을 대입하는 것, 즉 바인딩의 변경입니다. 이름이 가리키는 객체의 프로퍼티를 바꾸는 것은 막지 않습니다. 예제 3에서 `settings.size = 2`는 성공했고 다른 모듈 `read-settings.js`도 바뀐 `2`를 읽었으며, `settings = {}`만 TypeError였습니다.

</Callout>

<Callout type="misconception" title="export default는 언제나 라이브 바인딩이다">

`default`가 라이브인지는 `default`라는 이름이 아니라 그 이름이 가리키는 바인딩에 달려 있습니다. 예제 11에서 `export default n`은 식 `n`을 평가한 값을 담은 바인딩이라 `n`이 바뀌어도 `0`이었고, `export { n as default }`는 `n` 바인딩 자체를 내보내므로 `1`이었으며, 이름 있는 함수 선언은 그 이름의 바인딩이라 재할당이 보여 `g`였습니다. 그렇다고 `default`가 라이브가 아니라고 말할 수도 없습니다.

</Callout>

<Callout type="misconception" title="최상위 await는 페이지 전체를 멈춘다">

최상위 `await`가 멈추는 것은 그 모듈의 평가이고, 그 모듈을 `import`한 모듈은 끝날 때까지 기다립니다. 의존 관계가 없는 형제 모듈은 기다리지 않습니다. 예제 15에서 `tla-slow.js`가 멈춘 동안 `tla-fast.js`는 평가되어 `fast`가 찍혔고, `main`은 `tla-slow.js`가 끝난 뒤에야 실행되었습니다. 최상위 `await`는 [async/await](/concepts/async-await)의 `await`처럼 프로미스가 정해지면 이어서 실행하도록 평가를 멈추는 것이므로 호출 스택을 붙잡아 이벤트 루프를 막는 것이 아닙니다.

</Callout>

<Callout type="misconception" title="같은 파일이면 어떤 URL로 불러도 한 번만 평가된다">

한 번만 평가되는 단위는 파일이 아니라 모듈 맵이 찾아낸 모듈이고, 모듈 맵의 키는 URL과 모듈 유형의 쌍입니다. 같은 URL로 해석되는 요청은 지정자 문자열이 달라도 한 번 평가되지만(예제 4와 예제 17의 처음 두 `import`), URL이 다르면 같은 파일을 가리켜도 다른 모듈로 취급되어 따로 평가됩니다. 예제 17에서 `./map-log.js#again`은 조각만 다른 URL이어서 한 번 더 평가되었습니다. 이 결과는 Chromium에서 실행한 값이고, 다른 URL이 다른 모듈이 되는 근거는 모듈 맵의 키가 URL이라는 표준의 서술입니다.

</Callout>
