## 동작 원리

클래스는 새로운 종류의 값일까요, 아니면 함수일까요? `class`라는 키워드가 따로 있으니 함수와는 다른 무언가처럼 보이지만, `typeof`로 확인하면 답이 나옵니다. 이 페이지는 클래스가 함수 객체를 만든다는 같은 점을 먼저 확인하고, 그 함수가 생성자 함수와 어떻게 다른지를 예제 아홉 개로 하나씩 살펴봅니다. 선언 전에 쓰는 경우, `new` 없이 부르는 경우, 항상 strict mode인 점, 메서드의 열거 여부, 클래스 이름 바인딩, 필드와 static, private 필드, 메서드를 `new`하는 경우, `prototype` 프로퍼티를 다루고, 마지막에 비교표로 정리합니다. `new`의 단계는 [new 연산자](/concepts/new-operator), 프로토타입 체인은 [프로토타입 체인](/concepts/prototype-chain), TDZ는 [TDZ](/concepts/tdz), 열거 가능 여부와 writable은 [프로퍼티 어트리뷰트와 접근자](/concepts/property-attributes)에서 본 것을 전제합니다. 상속(`extends`)은 별도 개념이라 여기서 다루지 않습니다.

### 클래스는 함수 객체

예제 1의 5번 줄에서 `typeof Point`는 `'function'`입니다. 클래스 정의를 평가하면 생성자 역할을 하는 함수 객체가 만들어지고, 클래스 이름은 그 함수 객체를 가리킵니다. 이 함수 객체에도 `[[Call]]` 내부 메서드가 있어서, 명세의 `typeof`는 다른 함수와 똑같이 `'function'`을 돌려줍니다(그 `[[Call]]`이 실제로 하는 일은 아래 "new 없이 부르면"에서 봅니다). 6번 줄의 `Point.prototype.constructor === Point`가 `true`인 것도 생성자 함수와 같은 모양입니다. `Point.prototype`의 `constructor` 프로퍼티가 다시 `Point`를 가리킵니다. 7번 줄에서 `new Point(3)`으로 만든 객체의 `[[Prototype]]`은 8번 줄에서 확인하듯 `Point.prototype`이고, 메서드 `getX`는 그 객체에 없고 프로토타입 체인으로 찾아 쓰는 것입니다([프로토타입 체인](/concepts/prototype-chain)).

여기까지는 생성자 함수와 구조가 같습니다. 하지만 클래스가 만든 함수는 일반 함수와 내부 슬롯, 프로퍼티 어트리뷰트, strict mode 여부가 다릅니다. 이어지는 절들이 그 차이를 하나씩 보입니다.

### 호이스팅과 TDZ

예제 2의 2번 줄은 6번 줄의 클래스 선언 앞에서 `new Animal()`을 부르고 `ReferenceError`가 납니다. 클래스 선언의 바인딩은 `let`처럼 블록(또는 스크립트)이 시작될 때 이미 만들어지지만, 선언이 평가되기 전에는 초기화되지 않은 상태입니다([TDZ](/concepts/tdz)). 선언을 평가한 뒤인 7번 줄에서는 `typeof new Animal()`이 `'object'`입니다.

바인딩이 처음부터 있다는 증거는 8~16번 줄입니다. 바깥에 `let Shape = 'outer'`가 있는데도, 블록 안 11번 줄의 `Shape`를 읽으면 `'outer'`가 아니라 `ReferenceError`가 납니다. 같은 블록의 15번 줄 `class Shape`가 만든 바인딩이 블록 시작부터 바깥 이름을 가리고 있고, 아직 초기화되지 않았기 때문입니다. 반대로 함수 선언은 선언 처리 단계에서 바인딩을 만들 때 함수 객체로 초기화까지 끝내므로 선언 앞에서도 부를 수 있습니다([호이스팅](/concepts/hoisting)). 그래서 "클래스는 호이스팅되지 않는다"가 아니라 "호이스팅되지만 초기화되기 전에는 쓸 수 없다"가 정확합니다.

### new 없이 부르면

예제 3의 1번 줄 함수 선언 `Person`은 3번 줄처럼 그냥 호출하면 그대로 실행되어 `'called'`를 돌려줍니다. 클래스는 다릅니다. 클래스가 만든 생성자 함수는 내부 슬롯 `[[IsClassConstructor]]`가 `true`이고, 명세는 이런 함수의 `[[Call]]`이 TypeError를 만들어 던진다고 정합니다. 그래서 4번 줄의 `Member()`도, `[[Call]]`을 거치는 5번 줄의 `Member.call({})`도 모두 `TypeError`입니다. 클래스는 `new`로 부를 때만 생성자로 동작합니다([new 연산자](/concepts/new-operator)).

### 항상 strict

명세는 ClassDeclaration과 ClassExpression의 모든 부분이 strict mode 코드라고 정합니다. `'use strict'`를 쓰지 않아도 클래스 본문은 strict mode입니다. 예제 4의 4번 줄과 5번 줄은 각각 sloppy mode 함수와 클래스의 메서드를 객체에서 꺼내 변수에 담습니다. 6번 줄에서 그냥 호출하면 sloppy mode 함수의 `this`는 전역 환경의 global this value(`globalThis`의 값)라서 `a() === globalThis`가 `true`이고, 클래스 메서드의 `this`는 `undefined`입니다([this](/concepts/this-binding)). 이 차이는 함수냐 클래스냐가 아니라 sloppy mode냐 strict mode냐에서 옵니다. 첫 줄에 `'use strict';`를 쓴 스크립트라면 생성자 함수의 메서드를 꺼내 불러도 `this`가 `undefined`입니다. 클래스는 지시어 없이도 본문이 항상 strict mode라는 점이 다릅니다.

또 하나는 선언 없는 대입입니다. 7번 줄의 `start` 메서드 안 `total = 0`은 선언한 적 없는 이름에 대한 대입이라 strict mode에서 `ReferenceError`입니다. 8번 줄이 `ReferenceError`와 `typeof total`의 결과 `'undefined'`를 함께 출력하므로, 전역에 `total`이 암묵적으로 만들어지지도 않았습니다. sloppy mode의 함수라면 같은 대입이 전역 객체의 프로퍼티를 만들었을 것입니다([블록 스코프](/concepts/block-scope)).

### 메서드는 열거되지 않는다

예제 5의 2번 줄은 생성자 함수의 `prototype`에 메서드를 대입합니다. 보통의 대입으로 만든 프로퍼티는 열거 가능(enumerable)이 `true`이므로 `for...in`에 나옵니다. `for...in`은 자기 프로퍼티뿐 아니라 프로토타입 체인에 있는 열거 가능한 문자열 키도 훑기 때문에, 5번 줄의 `keys1`에는 `own`과 `hello`가 모두 담깁니다. 3번 줄 클래스의 `hello`는 다릅니다. 클래스 요소를 평가할 때 명세(ClassElementEvaluation)가 메서드의 enumerable에 `false`를 넘겨서, 메서드는 `Modern.prototype`에 열거 불가 프로퍼티로 정의됩니다. 그래서 7번 줄의 `keys2`에는 `own`만 담기고, 9번 줄의 디스크립터에서도 `enumerable`이 `false`입니다([프로퍼티 어트리뷰트와 접근자](/concepts/property-attributes)). 같은 메서드 정의 문법이라도 객체 리터럴 <code>{"{ hello() {} }"}</code>의 메서드는 열거 가능이라 `Object.keys`에 나옵니다. 열거 불가는 클래스가 메서드를 정의할 때 정하는 클래스 고유의 차이입니다.

### 클래스 이름 바인딩

클래스 안에서 쓰는 클래스 이름은 변경할 수 없는(immutable) 바인딩입니다. 예제 6의 2번 줄에서 `static reset` 메서드가 `Config = null`을 하려고 하면, 4번 줄이 보이듯 `TypeError`가 납니다. 명세(ClassDefinitionEvaluation)는 클래스 안쪽 이름을 클래스만을 위한 환경 레코드에 strict 바인딩인 변경할 수 없는 바인딩(`CreateImmutableBinding`의 두 번째 인수가 `true`)으로 만듭니다. strict 바인딩에 대입하면 대입하는 코드의 모드와 관계없이 항상 TypeError입니다. 이름 있는 함수 식의 이름도 변경할 수 없는 바인딩이지만 strict 바인딩이 아니어서, sloppy mode 함수 안에서 대입하면 오류 없이 무시됩니다([즉시 실행 함수와 모듈 패턴](/concepts/iife-module-pattern)). 반면 바깥의 클래스 선언이 만든 바인딩은 `let`처럼 다시 대입할 수 있어서, 5번 줄의 `Config = 'replaced'`는 오류 없이 6번 줄에서 `'replaced'`를 출력합니다. 안쪽 이름과 바깥 이름은 서로 다른 바인딩이므로, 바깥 `Config`에 다른 값을 대입한 뒤에도 클래스 안의 `Config`는 여전히 원래 클래스를 가리킵니다.

클래스 식의 이름은 클래스 안에서만 보입니다. 7번 줄의 `class Inner`에서 `Inner`는 메서드 안에서는 `typeof Inner`가 `'function'`이지만, 8번 줄의 바깥에서 `typeof Inner`는 `'undefined'`입니다. 한편 같은 스코프에 `let A;`가 있는데 `class A {}`를 또 선언하면 문법 오류(SyntaxError)입니다. 문법 오류는 코드가 실행되기 전에 걸러지므로 그런 줄이 하나라도 있으면 스크립트 전체가 한 줄도 실행되지 않습니다. 그래서 예제로 출력을 보일 수 없고, 이 페이지의 테스트가 확인합니다.

### 인스턴스 필드와 static

예제 7의 2번 줄 필드 `count = 0`은 인스턴스를 만들 때 그 인스턴스에 자기 프로퍼티로 생깁니다. 6번 줄의 `a`와 7번 줄의 `b`가 각자 `count`를 가지므로, 8번 줄에서 `a.add()`를 두 번, `b.add()`를 한 번 부르면 9번 줄에서 `a.count`는 `2`, `b.count`는 `1`입니다. 이 프로퍼티는 열거 가능해서 10번 줄의 `Object.keys(a)`는 `["count"]`입니다. 반면 메서드 `add`는 인스턴스마다 생기지 않고 `Item.prototype`에 하나만 있습니다. 그래서 `a.hasOwnProperty('add')`는 `false`입니다.

3번 줄의 `static total = 0`은 인스턴스가 아니라 클래스, 곧 함수 객체 `Item` 자신의 프로퍼티입니다. 4번 줄의 `Item.total++`은 모든 인스턴스가 함께 쓰는 하나의 값을 올리므로 9번 줄의 `Item.total`이 `3`입니다. 인스턴스에서는 `typeof a.total`이 `'undefined'`입니다.

### private 필드

예제 8의 `#balance`는 프로퍼티가 아닙니다. 프로퍼티 키(문자열이나 심볼)로 관리되는 것이 아니라, 명세가 Private Name으로 구분하는 별도의 private 요소입니다. 그래서 클래스 안의 3번 줄 `this.#balance`로는 읽고 쓸 수 있어서 `w.spend(30)`이 `70`을 돌려주지만(6번 줄), 프로퍼티 목록에는 나타나지 않습니다. 7번 줄에서 `Object.keys(w)`는 `[]`, `JSON.stringify(w)`는 `{}`이고 `w.balance`는 `undefined`입니다.

8번 줄의 `w['#balance'] = 0`은 private 필드를 건드리는 것이 아닙니다. 이름이 `'#balance'`라는 문자열인 보통의 프로퍼티를 새로 만들 뿐입니다. 그래서 9번 줄의 `w.spend(10)`은 private 필드 `70`에서 `10`을 뺀 `60`을 돌려주고, 보통 프로퍼티 `w['#balance']`는 `0`입니다. 한편 클래스 밖에서 `w.#balance`라고 쓰면 문법 오류(SyntaxError)입니다. 이것도 실행 전에 걸러지는 오류라서 스크립트 전체가 실행되지 않으므로 예제로 보이지 않고 테스트가 확인합니다.

상태를 숨기는 다른 방법인 클로저([클로저](/concepts/closure), [모듈 패턴](/concepts/iife-module-pattern))와는 숨기는 위치가 다릅니다. 클로저는 변수 바인딩을 함수가 만든 환경 레코드에 두어 바깥에서 닿지 못하게 하고, private 필드는 숨은 상태를 인스턴스마다 붙여 둡니다. 클로저는 클래스의 `constructor` 안에서도 그대로 쓸 수 있으므로 "생성자 함수는 클로저, 클래스는 private 필드"처럼 나뉘는 것은 아닙니다. 차이는 private 필드를 클래스 본문 안에서만 쓸 수 있다는 것입니다. private 이름은 그것을 선언한 클래스 본문 안에서만 유효해서(명세의 AllPrivateIdentifiersValid 검사), 클래스 본문 밖의 생성자 함수에서 `this.#secret = 1`처럼 쓰면 SyntaxError입니다. 반대로 클래스 본문 안에 들어 있는 함수라면 `function` 키워드로 만든 함수에서도 그 클래스의 private 이름을 쓸 수 있습니다. 기준은 함수의 종류가 아니라 코드가 어느 클래스 본문 안에 있느냐입니다.

### 메서드는 생성자가 아니다

예제 9의 2번 줄은 `function` 식을 메서드로 대입했습니다. 이 함수는 생성자로 쓸 수 있어서, 4번 줄의 `new Legacy.prototype.make()`는 객체를 만들고 `typeof`가 `'object'`입니다. 3번 줄 클래스 안의 메서드 `make`는 생성자가 아니라서, 5번 줄의 `new Modern.prototype.make()`는 `TypeError`입니다. 이 차이는 `class`가 아니라 메서드 정의 문법(`make() {}`)에서 옵니다. 객체 리터럴의 <code>{"{ make() {} }"}</code>에서 꺼낸 `make`를 `new`해도 같은 TypeError입니다. 클래스는 메서드를 이 문법으로만 쓰게 할 뿐입니다. 메서드 정의 문법과 화살표 함수 전반은 별도 개념에서 다룹니다.

6번 줄은 `prototype` 프로퍼티의 `writable`을 비교합니다. 명세는 ClassDefinitionEvaluation에서 `MakeConstructor`를 부를 때 `prototype`을 쓸 수 없게(`writableProto`가 `false`) 하라고 정합니다. 그래서 클래스의 `prototype`은 `writable`이 `false`이고, 일반 함수의 `prototype`은 `true`입니다.

## 결과와 이유

### 예제 1

5번 줄의 `typeof Point`가 `function`인 것은 클래스 정의를 평가하면 생성자 역할을 하는 함수 객체가 만들어지기 때문입니다. 6번 줄의 `Point.prototype.constructor === Point`는 `true`이고, 8번 줄은 `new Point(3)`이 만든 객체의 `[[Prototype]]`이 `Point.prototype`이라서 `true`, `getX()`의 결과로 `3`을 출력합니다.

### 예제 2

2번 줄은 6번 줄의 클래스 선언이 평가되기 전이라 바인딩이 초기화되지 않았고 `ReferenceError`입니다. 7번 줄은 선언을 평가한 뒤라 `typeof new Animal()`이 `object`입니다. 11번 줄이 `outer`를 출력하지 않고 `ReferenceError`인 것은, 15번 줄의 `class Shape`가 만든 바인딩이 9~16번 줄 블록 시작부터 있어서 8번 줄의 바깥 `Shape`를 가리고, 15번 줄을 평가하기 전까지 초기화되지 않기 때문입니다.

### 예제 3

1번 줄의 함수 선언 `Person`은 3번 줄의 호출에서 `called`를 돌려줍니다. 2번 줄의 클래스 `Member`는 `[[IsClassConstructor]]`가 `true`라서, 4번 줄의 `Member()`와 5번 줄의 `Member.call({})` 모두 `[[Call]]`이 TypeError를 던지고 catch가 `TypeError`를 출력합니다.

### 예제 4

4번 줄의 `a`는 sloppy mode 함수라서 6번 줄에서 그냥 호출하면 `this`가 `globalThis`의 값이고 `a() === globalThis`는 `true`입니다. 5번 줄의 `b`는 클래스 메서드라서 같은 방식으로 호출해도 `this`가 `undefined`이고 `b()`는 `undefined`입니다. 7번 줄의 `start` 안 `total = 0`은 strict mode 코드의 선언 없는 대입이라 `ReferenceError`이고, 전역에 `total`이 생기지 않아 8번 줄의 `typeof total`은 `undefined`입니다.

### 예제 5

2번 줄은 `Legacy.prototype`에 `hello`를 대입했으므로 열거 가능한 프로퍼티입니다. 5번 줄의 `for...in`은 자기 프로퍼티 `own`과 프로토타입 체인의 `hello`를 모두 훑어 `keys1`이 `["own","hello"]`입니다. 3번 줄 클래스의 `hello`는 `enumerable`이 `false`로 정의되어 7번 줄의 `keys2`는 `["own"]`이고, 9번 줄의 디스크립터는 `false`를 출력합니다.

### 예제 6

2번 줄의 `Config = null`은 클래스 안의 이름, 곧 변경할 수 없는 바인딩에 대입하는 것이라 `TypeError`이고 4번 줄이 그 오류의 이름을 출력합니다. 5번 줄은 바깥의 클래스 선언 바인딩에 대입하는 것이므로 `let`처럼 허용되어 6번 줄이 `replaced`를 출력합니다. 7번 줄의 클래스 식 이름 `Inner`는 클래스 안에서만 보여 메서드 안의 `typeof Inner`는 `function`이고, 8번 줄의 바깥 `typeof Inner`는 `undefined`입니다.

### 예제 7

2번 줄의 필드 `count`는 6번 줄의 `a`와 7번 줄의 `b`가 각자 자기 프로퍼티로 가지므로 8번 줄의 호출 뒤 `a.count`는 `2`, `b.count`는 `1`입니다. 3번 줄의 `static total`은 `Item` 함수 객체 자신의 프로퍼티이고 4번 줄의 `Item.total++`이 세 번 불려 `Item.total`은 `3`입니다. 10번 줄의 `Object.keys(a)`는 열거 가능한 자기 프로퍼티인 `count`만 담고, 메서드 `add`는 `Item.prototype`에 하나만 있어서 `a.hasOwnProperty('add')`는 `false`입니다. `static total`은 인스턴스에 없으므로 `typeof a.total`은 `undefined`입니다.

### 예제 8

2번 줄의 `#balance`는 프로퍼티가 아니라 private 요소라서 3번 줄의 `this.#balance`로만 읽고 쓸 수 있습니다. 6번 줄의 `w.spend(30)`이 `70`을 돌려주고, 7번 줄의 `Object.keys(w)`는 `[]`, `JSON.stringify(w)`는 `{}`, `w.balance`는 `undefined`입니다. 8번 줄의 `w['#balance'] = 0`은 이름이 `'#balance'`인 보통 프로퍼티를 만들 뿐 private 필드와 관계가 없어서, 9번 줄의 `w.spend(10)`은 `70 - 10`인 `60`이고 `w['#balance']`는 `0`입니다.

### 예제 9

2번 줄에서 대입한 `function` 식은 생성자로 쓸 수 있어서 4번 줄의 `new Legacy.prototype.make()`가 객체를 만들고 `typeof`가 `object`입니다. 3번 줄 클래스의 메서드 `make`는 메서드 정의 문법으로 만든 함수라 생성자가 아니어서 5번 줄의 `new Modern.prototype.make()`는 `TypeError`입니다. 6번 줄에서 클래스 `Modern`의 `prototype` 프로퍼티는 `writable`이 `false`이고, 생성자 함수 `Legacy`의 `prototype`은 `true`입니다.

### 흔한 오해

<Callout type="misconception" title="클래스는 문법 설탕일 뿐이라 생성자 함수와 똑같다">

클래스는 함수 객체를 만들고 `prototype`·`constructor` 연결도 같은 모양이라 닮았지만(예제 1), 똑같지는 않습니다. `new` 없이 부르면 TypeError(예제 3), 본문이 항상 strict mode(예제 4), 메서드가 열거되지 않음(예제 5), `prototype`이 `writable: false`임(예제 9), private 필드를 쓸 수 있음(예제 8)이 생성자 함수와 다릅니다. 클래스 메서드를 `new`할 수 없는 것(예제 9)은 클래스가 아니라 메서드 정의 문법 때문이라 객체 리터럴의 메서드 정의도 같습니다. 반대로 "클래스는 함수가 아니다"도 틀립니다. `typeof`가 `'function'`입니다.

</Callout>

<Callout type="misconception" title="클래스는 호이스팅되지 않는다">

선언 전에 쓰면 오류가 나서 호이스팅되지 않는 것처럼 보이지만, 바인딩은 블록이 시작될 때 이미 있습니다. 예제 2의 11번 줄이 바깥의 `'outer'`가 아니라 `ReferenceError`를 내는 것이 그 증거입니다. 다만 선언이 평가되기 전에는 초기화되지 않은 상태(TDZ)입니다.

</Callout>

<Callout type="misconception" title="private 필드는 이름이 #으로 시작하는 프로퍼티다">

`#balance`는 프로퍼티가 아니라 Private Name으로 관리되는 private 요소입니다. 그래서 `Object.keys`와 `JSON.stringify`에 나타나지 않습니다. `w['#balance']`는 이름이 `'#balance'`인 문자열 키의 보통 프로퍼티이고 private 필드와 별개입니다(예제 8).

</Callout>

<Callout type="misconception" title="static으로 만든 것도 인스턴스에서 쓸 수 있다">

static 필드와 static 메서드는 인스턴스가 아니라 클래스, 곧 함수 객체 자신의 프로퍼티이고 인스턴스의 프로토타입 체인에도 없습니다. 예제 7에서 `static total`은 `Item.total`로 읽고, 인스턴스에서는 `typeof a.total`이 `'undefined'`입니다.

</Callout>
