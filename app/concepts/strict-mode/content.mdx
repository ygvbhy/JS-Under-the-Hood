## 동작 원리

'use strict'를 코드 중간에 쓰면 왜 아무 일도 일어나지 않을까요? strict mode는 코드마다 정해지는 성질이고, 명세는 스크립트와 함수의 경우 그 코드가 use strict 지시어가 든 지시어 프롤로그로 시작하는지로 판정합니다(함수는 strict 코드 안에 쓰여도 strict이고, 모듈과 클래스는 지시어 없이 항상 strict입니다). 지시어 프롤로그는 코드 맨 앞의 문자열 식 문들로만 이루어지므로, 지시어는 그 안, 곧 맨 앞에 써야 효과가 있습니다. 프롤로그 밖에 쓴 'use strict'는 평가만 되는 평범한 문자열 식 문입니다. 판정된 함수는 지시어보다 앞에 쓰인 매개변수까지 통째로 strict입니다.

이 페이지의 예제는 Node의 `vm` 모듈에서 모듈이 아닌 스크립트(Script)로 실행한 결과입니다. 브라우저라면 `type` 속성이 없거나 빈 문자열이거나 JavaScript MIME 타입인 `<script>`로 실행되는 클래식 스크립트에 해당합니다. 모듈은 항상 strict라서 지시어가 없는 코드의 결과가 달라집니다. 모듈은 [ES 모듈](/concepts/es-modules)에서 다룹니다.

### strict mode란

ECMAScript 명세는 언어의 strict variant(엄격한 변형)를 정의합니다. 명세의 개요(4장, 비규범 설명)는 이 변형이 일부 기능을 빼고, 일부 의미를 바꾸고, 오류가 되는 조건을 더한다고 설명합니다. 그래서 strict mode를 "제한"으로만 이해하면 부족합니다. 기능을 빼는 일도 하지만, 같은 코드가 다른 결과를 내도록 의미를 바꾸기도 합니다(일반 함수 호출의 `this`가 그렇습니다).

strict가 아닌 코드를 흔히 sloppy mode라고 부르지만 명세 용어는 아닙니다. 명세는 non-strict code라고 부릅니다. 이 페이지는 다른 페이지와 같이 sloppy mode라고 씁니다.

### 지시어 프롤로그

Script, 함수 본문, 모듈 본문의 맨 앞에서 문자열 리터럴 하나와 세미콜론만으로 된 식 문(expression statement)이 이어지는 가장 긴 구간을 지시어 프롤로그(directive prologue)라고 합니다. 프롤로그 안에서 글자가 정확히 `'use strict'` 또는 `"use strict"`인 문이 use strict 지시어입니다. 이 페이지에서 '지시어'는 use strict 지시어를 줄여 부르는 말입니다. 세미콜론 자동 삽입의 세부는 다루지 않습니다.

이 정의에서 다음이 따라 나옵니다.

- 문자열 리터럴 식 문이 아닌 문(예: `var` 문) 뒤에 쓴 `'use strict'`는 프롤로그 밖이라 지시어가 아니라 평범한 문자열 식 문입니다. 평가될 뿐 strict mode를 켜지 않습니다(예제 1의 `second`).
- 앞에 문자열 식 문만 있으면 모두 프롤로그 안입니다. `'note'; 'use strict';`에서는 둘 다 프롤로그 안이라서 지시어가 효과를 냅니다(예제 1의 `third`).
- 주석은 문이 아니므로 지시어 앞에 있어도 됩니다.
- 이스케이프 시퀀스나 줄 잇기가 든 것은 지시어가 아닙니다. `\u0020`은 공백 문자를 뜻하는 이스케이프 시퀀스인데, `'use\u0020strict'`는 값이 'use strict'와 같은 문자열이어도 소스 글자가 달라서 지시어가 아닙니다. 다만 문자열 리터럴 식 문이므로 프롤로그는 거기서 끊기지 않고, 그 뒤에 쓴 `'use strict';`는 효과를 냅니다.
- 괄호로 감싼 `('use strict');`는 문자열 리터럴 하나와 세미콜론만으로 된 식 문이 아니라서 지시어가 아닙니다.

### 적용 단위

명세는 strict mode를 개별 소스 텍스트 단위 수준에서 고르며, strict mode 소스 텍스트 단위 안에 쓰인 코드를 실제로 실행할 때만 적용된다고 설명합니다(같은 개요). 명세 본문은 코드를 전역 코드(Script), eval 코드, 함수 코드, 모듈 코드의 네 종류로 나누고, 어떤 코드가 strict인지를 다음 경우로 정합니다. 이 페이지는 eval 코드를 다루지 않습니다.

- 전역 코드: 프롤로그에 지시어가 있으면 strict입니다.
- 함수 코드: strict 코드 안에 쓰였거나 자기 본문의 프롤로그에 지시어가 있으면 strict입니다. 함수 코드는 본문뿐 아니라 매개변수 목록도 포함하는 소스 텍스트입니다.
- 모듈 코드는 항상 strict입니다. 지시어가 없는 모듈에서 선언 없는 대입이 ReferenceError가 되는 예제는 [ES 모듈](/concepts/es-modules)에 있습니다.
- 클래스: 코드 종류와 별개로, 클래스 선언·식의 모든 부분은 strict라는 규칙이 따로 있습니다. 클래스는 [클래스](/concepts/class-basics)에서 다룹니다.
- Function 생성자로 만든 함수: 본문(마지막 인수)의 지시어 프롤로그에 use strict 지시어가 있을 때만 strict입니다. 아래에서 따로 설명합니다.

함수의 판정 기준은 코드가 쓰인 위치입니다. strict 함수 안에 쓴 함수는 strict입니다. 반대로 strict 함수가 호출하더라도, strict 코드 밖에 쓰였고 자기 본문에 지시어도 없는 함수는 sloppy입니다. 함수를 호출한 쪽은 기준이 아닙니다(예제 2). 함수 안의 지시어는 바깥 코드로 퍼지지 않습니다. 그 함수와 그 안에 쓴 함수만 strict로 만들 뿐이라서, 같은 Script에서 그 뒤에 쓴 함수도 지시어가 없으면 sloppy입니다(예제 1의 `first` 뒤에 쓴 `second`).

판정된 함수 코드는 통째로 strict입니다. 본문의 지시어 프롤로그에 지시어가 있으면 그보다 앞에 쓰인 매개변수 목록도 strict 규칙을 따르고, 함수 이름도 마찬가지입니다(strict mode에서는 `eval`과 `arguments`를 바인딩 이름으로 쓸 수 없어서 `function eval() { 'use strict'; }`도 SyntaxError입니다). 예를 들어 `function f(a, a) { 'use strict'; }`는 SyntaxError이고, 예제 3의 `duplicate-params` 줄이 이를 보입니다. 매개변수 목록이 단순하지 않은 함수의 본문에 지시어를 쓰는 것은 따로 SyntaxError인데, 이는 [매개변수 기본값](/concepts/default-parameters)에서 다룹니다.

Function 생성자(`new Function`)는 코드를 문자열로 받아 함수를 만드는 기능입니다. 이 페이지에서는 문자열을 코드로 컴파일해 보는 문법 검사 도구로만 씁니다. 함수 선언에 직접 쓰면 스크립트 전체가 실행되기 전에 SyntaxError가 나서 다른 줄도 실행되지 않기 때문입니다. Function 생성자는 인수로 받은 문자열을 호출한 쪽 코드와 따로 파싱해서 함수를 만듭니다. 그래서 만들어진 함수는 호출한 쪽 코드 안에 쓰인 것이 아니고, 본문의 지시어 프롤로그에 지시어가 있을 때만 strict입니다. strict 코드에서 `new Function`을 불러도 본문에 지시어가 없으면 sloppy입니다. 예제 3의 결과가 예제 파일에 지시어가 있는지와 무관한 것은 이 때문입니다.

2행과 5행의 결과는 호출되는 함수가 strict인지로 정해집니다. 표의 코드는 맨 앞에 지시어를 붙였으므로 호출하는 쪽과 호출되는 함수가 함께 strict입니다. strict 코드가 sloppy 함수를 부르면 그 함수 안의 `this`와 `arguments`는 sloppy mode 결과대로이고, 반대로 sloppy 코드가 strict 함수를 부르면 strict mode 결과대로입니다(예제 2와 같은 원리).

strict mode에서는 어떤 문법이 SyntaxError가 됩니다. 식별자에 `delete`를 쓰는 것, `with` 문, 매개변수 이름 중복, `010` 같은 옛 8진수 리터럴, `eval`과 `arguments`에 대입하는 것이 그 예이고, 예제 3에서 sloppy 본문과 strict 본문을 나란히 컴파일해 봅니다. 매개변수 이름 중복이 sloppy mode에서 허용되는 것은 매개변수 목록이 단순한 `function` 함수뿐입니다. 화살표 함수, 메서드, 매개변수 목록이 단순하지 않은 함수에서는 sloppy mode에서도 SyntaxError이며, 이 조건은 [화살표 함수와 메서드 축약](/concepts/arrow-functions)에서 다룹니다.

strict mode 코드에서는 `implements`, `interface`, `let`, `package`, `private`, `protected`, `public`, `static`, `yield`를 변수·함수·매개변수 이름이나 레이블로 쓸 수 없습니다(명세 부록 C가 모아 둔 목록). 프로퍼티 이름으로는 strict mode에서도 쓸 수 있어서 `{ let: 1 }`이나 `o.public`은 문제가 없습니다. `let`이 그중 하나라는 점은 [변수 선언과 할당](/concepts/variable-declaration)과 이어집니다.

명세 부록 C(비규범)가 strict mode의 차이를 모아 둔 곳입니다. 이 페이지는 그중 일부만 다룹니다.

예제 1에서 `first`는 본문의 첫 문이 `'use strict'`라서 프롤로그 안에 있고, 함수 코드 전체가 strict입니다. 그래서 선언 없는 대입이 ReferenceError입니다. `second`의 `'use strict'`는 `var x = 1;` 뒤에 있어 프롤로그 밖입니다. 평범한 문자열 식 문이라서 평가될 뿐이고, 함수는 sloppy라서 대입이 오류 없이 끝납니다. `third`는 `'note';`와 `'use strict';`가 모두 문자열 식 문이라 둘 다 프롤로그 안입니다. 그래서 지시어가 효과를 냅니다. 세 함수는 같은 Script 안에 있지만 각자 판정되어, `first`와 `third`의 지시어는 `second`에 영향을 주지 않습니다.

예제 2에서 `outer`의 프롤로그에 지시어가 있으므로 `outer`는 strict입니다. `inner`는 `outer` 안에 쓰였으므로 strict이고 대입이 ReferenceError입니다. `helper`는 `outer`가 불렀지만 strict 코드 밖에 쓰였습니다. 지시어도 없고 strict 코드 안에 들어 있지도 않으므로 sloppy라서 오류 없이 끝납니다. strict 여부를 정하는 것은 코드가 쓰인 위치이고, 누가 불렀는지는 상관이 없습니다. 탐침은 [블록 스코프](/concepts/block-scope)에서 본 선언 없는 대입입니다.

예제 3의 각 줄은 `<이름> <sloppy 본문 결과> <strict 본문 결과>`입니다. sloppy 본문은 8항목 모두 컴파일되어 `ok`이고, 같은 본문 앞에 `'use strict'; `를 붙이면 모두 SyntaxError입니다. 항목은 식별자에 `delete`를 쓰는 것, `with` 문, 매개변수 이름 중복, 옛 8진수 `010`, `eval`에 대입, `arguments`에 대입, `let`을 변수 이름으로 쓰는 것, `implements`를 변수 이름으로 쓰는 것입니다. 이 가운데 `duplicate-params` 줄이 strict mode가 지시어 이후만이 아니라 함수 코드 전체의 성질임을 보입니다. 지시어는 본문 맨 앞에 있고 `a, a`는 그보다 앞의 매개변수 목록인데도 SyntaxError입니다. "지시어 이후만 strict"라면 이 줄은 `ok ok`였을 것입니다.

`new Function`으로 만든 함수는 본문 문자열을 따로 파싱하고, 본문의 지시어 프롤로그에 지시어가 없으면 호출한 쪽이 strict여도 sloppy입니다. 그래서 예제 3의 결과는 예제 파일의 맨 앞에 `'use strict';`를 붙여도 같습니다.

<Callout type="misconception" title="'use strict'는 파일 어디에 써도 그 뒤가 strict다">
  지시어는 프롤로그 안에 있을 때만 지시어입니다. 문자열 리터럴 식 문이 아닌 문 뒤에 쓴{' '}
  <code>{"'use strict'"}</code>는 평범한 문자열 식 문이라 아무 효과가 없고(예제 1의 `second`),
  지시어가 있으면 그 이후가 아니라 그 함수 코드 전체가 strict입니다(예제 3의 `duplicate-params`).
</Callout>

<Callout type="misconception" title="strict 함수가 부르는 함수도 strict가 된다">
  strict 여부는 코드가 쓰인 위치로 정해지고 호출한 쪽과는 무관합니다. strict 함수가 불러도 strict
  코드 밖에 쓰인 함수는 sloppy입니다(예제 2의 `helper`). 반대로 strict 함수 안에 쓴 함수는
  strict입니다(예제 2의 `inner`).
</Callout>

<Callout type="misconception" title="strict mode는 기능을 빼기만 한다">
  strict mode는 기능을 빼고 오류 조건을 더하지만 일부 의미를 바꾸기도 합니다. 일반 함수 호출의
  `this`와 `arguments`가 그렇습니다. 같은 코드가 오류 없이 다른 값을 낼 수 있습니다(변화 표의 2행과
  5행).
</Callout>
