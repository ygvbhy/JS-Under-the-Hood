## 동작 원리

서버가 404 응답을 보냈는데도 `fetch(...).catch(...)`의 catch 콜백은 왜 실행되지 않을까요? 이 페이지는 이 질문에서 출발해 `fetch`가 돌려주는 프로미스가 이행되는 조건과 거부되는 조건, `response.ok`가 true인 범위, 응답 본문을 읽는 `json()`이 파싱된 값이 아니라 그 값으로 이행될 프로미스를 돌려주는 이유, 본문이 있는 Response를 한 번만 읽을 수 있는 이유를 Fetch 표준의 단계와 실제 실행 결과로 확인합니다. 먼저 동작 원리를 여덟 가지로 나누어 보고, 결과표로 정리한 뒤, 예제 여덟 개를 예측해 보고, 출력의 이유를 줄 번호와 함께 설명합니다. `then`과 `catch`, 프로미스의 상태, 콜백이 던지면 `then`이 돌려준 프로미스가 거부되는 규칙은 [프로미스](/concepts/promise), 응답 본문의 JSON 문법과 `JSON.parse`의 SyntaxError는 [JSON](/concepts/json)에서 본 것을 전제합니다. 요청 옵션(`method`·`headers`·`body`), CORS의 작동 방식, 요청 중단(`AbortController`), 본문 스트림, [async/await](/concepts/async-await)와 [try/catch/finally](/concepts/error-handling)로 다시 쓰는 방법, XMLHttpRequest는 이 페이지에서 다루지 않습니다.

`fetch`와 `Response`는 ECMAScript 언어가 아니라 WHATWG Fetch 표준이 정의한 호스트 API입니다(이 페이지에서는 브라우저). 반면 `fetch`가 돌려준 프로미스에 `then`과 `catch`를 붙였을 때 콜백이 어떻게 불리는지는 ECMAScript가 정한 프로미스의 규칙입니다. 아래에서는 이 둘을 구분해서 씁니다. HTTP 상태 코드는 서버가 응답에 담아 보내는 세 자리 숫자라는 정도로만 다루고, 각 코드의 의미는 다루지 않습니다.

### ① fetch는 프로미스를 돌려준다

`fetch(url)`을 부르면 Fetch 표준의 `fetch()` 메서드 단계가 프로미스 `p`를 만들어 바로 돌려줍니다. 응답을 받아 `p`를 정하는 단계(processResponse)는 표준이 태스크로 넣어 실행하므로, 응답에 따른 이행·거부는 지금 실행 중인 스크립트가 끝난 뒤에 일어납니다. 게다가 `then` 콜백은 프로미스가 이미 정해져 있어도 나중에 불립니다. 그래서 `fetch(...)` 다음에 오는 동기 코드가 콜백보다 먼저 실행됩니다. 예제 1에서는 `then`을 붙인 코드가 `fetch` 호출 바로 아래에 있지만, 마지막 줄의 `console.log('sync end')`가 가장 먼저 출력됩니다. 이 순서는 `then` 콜백이 나중에 불린다는 프로미스의 규칙만으로도 나오므로, processResponse가 태스크로 들어간다는 것의 증거는 아닙니다. 그 차이는 ③의 예제 4와 8에서 봅니다.

```js file=./examples/ok-response.js

```

`then` 콜백이 Job으로 나중에 불리는 것은 프로미스의 규칙입니다([프로미스](/concepts/promise)). `fetch`가 프로미스를 정하는 시점과 그 조건은 Fetch 표준이 정합니다. 다음 절부터 그 조건을 봅니다.

### ② 이행 조건: network error가 아니면 상태와 상관없이 Response로 이행한다

표준의 `fetch()` 메서드는 응답을 받는 단계(processResponse)에서 요청이 중단됐는지와 결과가 network error인지를 검사합니다. network error는 type이 "error"이고 status가 0이며 body가 null인 응답을 가리키는 표준의 용어입니다. 결과가 network error이면 `p`를 TypeError로 거부하고, 아니면 Response 객체를 만들어 `p`를 그 객체로 이행시킵니다. 이 단계에는 상태 코드를 검사하는 부분이 없습니다. 그래서 404나 500처럼 서버가 오류를 뜻하는 상태 코드를 보내도 결과가 network error가 아니면 `p`는 Response로 이행하고, `then` 콜백이 불립니다. 다만 이 단계 앞에서 상태 코드가 결과를 network error로 바꾸는 경우도 있습니다. 예를 들어 리다이렉트 모드를 `"error"`로 준 요청이 리다이렉트 상태를 받으면 HTTP fetch 단계가 결과를 network error로 만듭니다. 이 페이지의 예제는 모두 기본 옵션으로 요청합니다.

```js file=./examples/not-found.js

```

예제 2의 서버는 404를 보내지만(아래 "가짜 서버 경로" 표), `then` 콜백이 불리고 `response.status`는 `404`입니다. `catch`는 불리지 않습니다. 200, 201, 404, 500을 주는 네 경로에 한꺼번에 요청해 보면 네 프로미스가 모두 이행됩니다.

### ③ 거부 조건: network error, Request 생성자 예외, 중단

표준의 `fetch()` 단계 안에서 `p`가 거부되는 경우는 세 가지입니다.

- 결과가 network error일 때. 표준은 이렇게 적습니다: "If response is a network error, then reject p with a TypeError". 예제 4가 이 경우입니다.
- 내부에서 부른 Request 생성자가 예외를 던질 때. 이 예외로 `p`를 거부합니다. 잘못된 URL이 한 예이고, 예제 8이 이 경우입니다. `fetch`가 동기적으로 예외를 던지는 것이 아니라, 요청을 보내기 전에 그 자리에서 `p`를 거부하고 돌려줍니다.
- 요청이 중단(abort)될 때. `p`가 아직 이행되지 않았으면 중단 사유(abort reason)로 거부하고, 이미 이행됐으면 `p`는 그대로 두고 본문을 오류 상태로 만듭니다. 이 페이지에는 중단 예제가 없습니다.

이 단계에 들어가기 전, 인수를 IDL 값으로 바꾸다 생긴 예외(예: 인수 없이 `fetch()`를 부름)도 Web IDL 규칙에 따라 거부된 프로미스로 바뀝니다.

이 페이지가 실행으로 보이는 거부는 network error(예제 4)와 잘못된 URL(예제 8)입니다. 두 예제는 `fetch`가 돌려준 프로미스 `p`에 거부 처리 함수를 직접 붙이고(예제 4는 `then`의 두 번째 인수, 예제 8은 `catch`), 끝에 `Promise.resolve().then(...)`으로 마이크로태스크를 하나 등록해 거부가 언제 일어나는지를 가릅니다([마이크로태스크 큐](/concepts/microtask-queue)). `p`가 이미 거부되어 있으면 반응을 붙이는 순간 Job이 큐에 들어가므로 나중에 등록한 `microtask`보다 먼저 나오고, 아직 정해지지 않았으면 `microtask`가 먼저 나옵니다. 잘못된 URL은 `fetch()` 호출 안에서 이미 거부되므로 예제 8은 앞의 경우이고, network error는 응답 처리 태스크에서 정해지므로 예제 4는 뒤의 경우입니다. 반응을 `p`에 직접 붙여야 이 비교가 성립합니다. `fetch(...).then(...).catch(...)`처럼 사이에 `then`이 끼면, `p`가 이미 거부되어 있어도 거부가 `then`이 돌려준 프로미스를 한 번 더 거쳐 `catch`에 닿으므로 `microtask`가 먼저 나옵니다.

여기서 거부 기준을 "서버가 응답했는가"로 잡으면 틀립니다. 표준의 HTTP fetch 단계는 `fetch`의 기본 모드로 보낸 교차 출처 요청에서 CORS 검사가 실패하면 network error를 결과로 돌려준다고 정하므로, 서버가 응답을 보냈어도 `fetch`의 결과는 network error가 되어 `p`가 거부될 수 있습니다. 기준은 응답을 받았는지가 아니라 결과가 network error인지입니다. CORS 자체는 이 페이지에서 다루지 않습니다.

### ④ ok는 200~299

`response.ok`는 표준이 ok status라고 부르는 범위, 곧 상태 코드가 200 이상 299 이하(양 끝 포함)일 때 `true`입니다. 예제 3의 출력은 `[200,true]`, `[201,true]`, `[404,false]`, `[500,false]`입니다. 예제로 확인한 것은 이 네 값뿐이며, 200~299의 위쪽 경계와 3xx 상태는 실행하지 않았습니다. 이 범위는 표준의 정의를 가져온 것입니다. 요청의 리다이렉트 모드가 기본값 "follow"이면 리다이렉트 상태(301·302·303·307·308) 응답은 Location 헤더가 있을 때 그 주소로 따라가므로, 보통 최종 응답의 상태가 보입니다. 300이나 304 같은 다른 3xx는 리다이렉트 상태가 아니어서 따라가지 않습니다.

### ⑤ 본문은 따로 읽고, 그 결과도 프로미스다

`fetch`의 프로미스가 이행된 값인 Response에는 상태 코드와 헤더가 들어 있고, 본문(body)은 그 Response에서 따로 읽어야 합니다. 표준의 HTTP-network fetch 단계는 응답 헤더가 모두 전송될 때까지 기다린 뒤 응답을 돌려줍니다. 본문 바이트를 받아 스트림에 넣는 일은 그 뒤에도 병행해서 이어지고, 표준은 HTTP-network fetch 단계의 끝에 "Typically response's body's stream is still being enqueued to after returning."이라고 적습니다. 그래서 `p`가 이행된 시점에 본문이 전부 도착했다는 보장이 없습니다.

`json()`·`text()`처럼 본문을 읽는 메서드는 표준의 consume body 절차를 부릅니다. 이 절차는 body가 쓸 수 없는 상태(unusable)가 아니면 새 프로미스를 만들어 돌려주고, 본문을 끝까지 읽은 뒤 그 프로미스를 이행시킵니다. 본문을 받는 도중 연결이 비정상적으로 끝나거나 요청이 중단되면 본문 stream이 오류 상태가 되어 이 프로미스는 거부됩니다(이 페이지에서는 실행하지 않음). 본문이 이미 도착했는지와 상관없이 항상 프로미스를 돌려줍니다. 그래서 예제 1의 `response.json()`은 파싱된 결과 값이 아니라 그 값으로 이행될 프로미스를 돌려주고, 결과 값은 그 프로미스를 `then`으로 받아야 얻습니다.

예제 1에서 `body instanceof Promise`의 `true`는 `json()`이 프로미스를 돌려준다는 사실, 곧 반환 타입만 보입니다. 가짜 서버가 응답 본문을 한 번에 주기 때문에 본문이 아직 도착하지 않은 상태를 만든 것이 아니며, 이 출력이 본문이 늦게 온다는 증거는 아닙니다. 본문이 나중에 도착할 수 있다는 근거는 위의 표준 단계입니다.

### ⑥ 본문이 있는 Response는 한 번만 읽을 수 있다

consume body는 body가 null이 아니면서 그 stream이 disturbed(읽기가 시작됐거나 취소됨)이거나 locked(리더가 스트림을 잠가 둠)이면 unusable로 보고, 이때 TypeError로 거부된 프로미스를 돌려줍니다. 본문을 읽기 시작한 Response에서 다시 읽으려 하면 이 경우에 해당합니다. body가 null인 Response는 이 조건에 해당하지 않아 빈 본문으로 읽힙니다. 본문이 두 번 필요하면 읽기 전에 `response.clone()`으로 복제본을 만들어 각각 읽거나, `text()`로 한 번 읽은 문자열을 `JSON.parse`로 파싱합니다(이 페이지에서는 실행하지 않음).

```js file=./examples/body-used.js

```

예제 6에서 `response.bodyUsed`는 본문을 읽기 전에는 `false`이고, `text()`를 부른 바로 다음 줄에서는 `true`입니다. `text()`의 프로미스가 아직 이행되지 않았는데도 `true`이므로, 읽기가 끝나서가 아니라 읽기가 시작돼서 바뀐 것입니다. `bodyUsed`는 본문 stream이 disturbed인지를 알려 줍니다. `text()`가 끝난 뒤 같은 Response에 `json()`을 부르면 그 프로미스가 TypeError로 거부되어 `catch`가 불립니다.

### ⑦ JSON이 아니면 json()이 거부한다

`json()`은 본문을 끝까지 읽은 바이트를 UTF-8로 디코드한 뒤 ECMAScript의 `JSON.parse`로 파싱합니다(WHATWG Infra 표준의 JSON 파싱 절차). `JSON.parse`가 던진 SyntaxError는 consume body가 받아 `json()`의 프로미스를 거부합니다. 이것은 결과가 network error가 아니어서 `fetch`의 프로미스가 이미 이행된 뒤의 일이므로, 본문 파싱 실패는 `fetch`가 아니라 `json()`이 돌려준 프로미스를 거부합니다.

### ⑧ 실패를 한 catch로 모으기

`fetch`는 404도 이행하므로, 4xx·5xx를 실패로 다루려면 `ok`를 직접 확인해야 합니다. 예제 5의 `getJSON`은 `ok`가 `false`일 때 `then` 콜백 안에서 `throw`합니다. 콜백이 던지면 그 `then`이 돌려준 프로미스가 거부되는 것은 프로미스의 규칙이어서, 이 거부가 체인을 따라 내려가 `catch` 한 곳에서 잡힙니다. `throw`와 `Error`의 자세한 내용은 [try/catch/finally](/concepts/error-handling)에서 다루는 별도 개념입니다.

## 결과와 이유

### 예제 1의 출력

`sync end`가 가장 먼저 나오는 것은 1번째 줄의 `fetch`가 프로미스를 바로 돌려주고, 2번째 줄의 `then` 콜백은 응답이 도착해 프로미스가 이행된 뒤에 불리기 때문입니다. 3번째 줄이 `200 true`를 출력하고, 4번째 줄의 `response.json()`은 파싱된 값이 아니라 그 값으로 이행될 프로미스를 돌려주므로 5번째 줄은 `true`를 출력합니다. 6번째 줄에서 이 프로미스를 반환하면 `then`이 돌려준 프로미스가 그 결과를 따라가고, 8번째 줄의 다음 `then`이 파싱된 값을 받아 9번째 줄에서 `Kim`을 출력합니다. `true`는 `json()`의 반환 타입을 보일 뿐이며, 본문이 늦게 온다는 증거는 아닙니다.

### 예제 2의 출력

2번째 줄의 `then` 콜백이 불렸다는 것은 `fetch`의 프로미스가 이행됐다는 뜻입니다. 3번째 줄이 `then 404 false`를 출력하므로 `status`는 `404`, `ok`는 `false`입니다. 9번째 줄의 `catch`는 불리지 않았습니다. 4번째 줄의 `json()`은 404 응답의 본문(`{"message":"not found"}`)도 읽어 파싱하고, 6번째 줄의 다음 `then`이 그 값을 받아 7번째 줄에서 `not found`를 출력합니다. 상태 코드는 본문을 읽을 수 있는지와 별개입니다.

### 예제 3의 출력

1번째 줄은 네 경로, 2번째 줄은 `fetch` 네 개를 `Promise.all`에 모읍니다. 모든 프로미스가 이행되어야 `Promise.all`의 프로미스도 이행되고, 그 결과 배열은 완료 순서가 아니라 입력 순서를 따릅니다. 3번째 줄이 각 응답을 `[status, ok]` 쌍으로 만들고 4번째 줄이 `JSON.stringify`로 출력해 `[[200,true],[201,true],[404,false],[500,false]]`가 나옵니다. 404와 500 요청의 프로미스도 이행됐다는 뜻이고, 하나라도 거부됐다면 `Promise.all`이 거부되어 이 줄은 출력되지 않았을 것입니다. `ok`의 `true`/`false`는 200~299 범위로 갈립니다.

### 예제 4의 출력

1번째 줄의 `then`은 `p`에 직접 반응을 붙이는데, 이때 `p`는 아직 정해지지 않았습니다. 그래서 먼저 9~11번째 줄에서 등록한 마이크로태스크가 `microtask`를 출력합니다. `fetch`의 거부는 응답 처리 태스크에서 일어나므로, 지금 실행 중인 스크립트와 그 뒤의 마이크로태스크가 모두 끝난 다음입니다. 거부되면 2~4번째 줄의 이행 처리 함수는 불리지 않고(`then` 줄이 출력에 없음), 5~7번째 줄의 거부 처리 함수가 `rejected TypeError true`를 출력합니다. `/offline.json`은 가짜 서버가 응답 없이 요청을 실패시켜 `fetch`의 결과가 network error가 되고, 표준의 `fetch()` 단계는 이때 프로미스를 `TypeError`로 거부하기 때문입니다. `error.name`이 `TypeError`이고 `error instanceof TypeError`가 `true`입니다. 오류 메시지 문장은 브라우저마다 다를 수 있어 출력하지 않았습니다.

### 예제 5의 출력

1~8번째 줄의 `getJSON`은 `fetch`의 프로미스에 `then`을 붙이고, 3번째 줄에서 `ok`가 `false`이면 4번째 줄에서 던집니다. 10번째 줄의 첫 호출은 `ok`가 `true`라 6번째 줄의 `response.json()`의 결과로 이행되어, 12번째 줄이 `data Kim`을 출력합니다. 13번째 줄의 두 번째 호출은 `fetch`가 이행되지만 `ok`가 `false`여서 4번째 줄이 던지고, `getJSON`이 돌려준 프로미스가 거부됩니다. 11번째 줄 `then`의 콜백이 13번째 줄에서 이 거부된 프로미스를 반환하므로, 그 `then`이 돌려준 프로미스도 거부를 따라갑니다. 15번째 줄의 `then`에는 거부 처리 함수가 없어 거부가 그대로 넘어가고, 18번째 줄의 `catch`가 `error.message`인 `HTTP 404`를 출력합니다. 프로미스의 규칙상 `fetch`가 네트워크 오류로 거부된 경우(예제 4)도 같은 길로 이 `catch`에 도착합니다.

### 예제 6의 출력

3번째 줄은 본문을 읽기 전이라 `false`를 출력합니다. 4번째 줄에서 `text()`를 부르면 본문 읽기가 시작되고, 바로 다음 5번째 줄은 `text()`의 프로미스가 아직 이행되지 않은 시점인데도 `true`를 출력합니다. `bodyUsed`가 읽기 완료가 아니라 stream이 disturbed인지를 보기 때문입니다. 6번째 줄에서 `text()`가 이행된 뒤 7번째 줄이 `string`을 출력하고, 8번째 줄에서 같은 Response에 `json()`을 부르면 consume body가 TypeError로 거부된 프로미스를 돌려줍니다. 이 프로미스를 반환했으므로 체인이 거부되어 11~13번째 줄의 `catch`가 `catch TypeError`를 출력합니다.

### 예제 7의 출력

3번째 줄의 `then 200 true`는 `fetch`의 프로미스가 이행됐고, 상태가 200, `ok`가 `true`라는 뜻입니다. 4번째 줄의 `json()`이 본문 `{name: "Kim"}`을 파싱하다 실패합니다. 키가 따옴표로 감싸이지 않아 JSON 문법에 맞지 않기 때문입니다([JSON](/concepts/json)). `json()`이 돌려준 프로미스가 `SyntaxError`로 거부되고, 6~8번째 줄의 `catch`가 `catch SyntaxError true`를 출력합니다. `fetch`의 프로미스는 본문을 JSON으로 파싱하지 않고 이행하며, 파싱은 `json()`이 합니다.

### 예제 8의 출력

1번째 줄의 `fetch('http://[')`에서 내부의 Request 생성자가 예외를 던지지만, `fetch()` 단계는 그 예외로 프로미스를 거부할 뿐 호출한 쪽에 던지지 않습니다. 그래서 2번째 줄이 `after fetch`를 먼저 출력합니다. 3번째 줄의 `catch`는 이미 거부된 프로미스에 붙으므로 그 자리에서 반응이 마이크로태스크로 들어갑니다. 6번째 줄의 `Promise.resolve().then(...)`은 그 뒤에 마이크로태스크를 넣으므로, 스크립트가 끝난 뒤 `catch TypeError`가 먼저, `microtask`가 나중에 출력됩니다. network error처럼 응답 처리 태스크에서 거부됐다면 예제 4처럼 `microtask`가 먼저 나왔을 것입니다. 이 예제는 요청이 나가지 않으므로 가짜 서버 경로가 필요 없습니다.

### 흔한 오해

<Callout type="misconception" title="404 응답이면 catch로 간다">

`fetch`의 프로미스는 결과가 network error가 아니면 상태 코드와 상관없이 Response로 이행합니다. 표준의 `fetch()` 단계에 상태 검사가 없기 때문입니다. 예제 2에서 `then 404 false`가 출력됐고 `catch`는 불리지 않았습니다. 4xx·5xx를 실패로 다루려면 `ok`를 확인해 직접 던져야 합니다(예제 5).

</Callout>

<Callout type="misconception" title="서버가 응답만 하면 fetch는 거부되지 않는다">

기준은 서버가 응답했는지가 아니라 `fetch`의 결과가 network error인지입니다. 표준의 HTTP fetch 단계는 `fetch`의 기본 모드로 보낸 교차 출처 요청에서 CORS 검사가 실패하면 network error를 결과로 돌려주므로, 서버가 응답을 보냈어도 프로미스가 거부될 수 있습니다. 거부 경로에는 network error 외에 Request 생성자의 예외(예제 8)와 중단도 있습니다.

</Callout>

<Callout type="misconception" title="response.json()이 바로 파싱된 값이다">

`json()`은 파싱된 결과 값이 아니라 그 값으로 이행될 프로미스를 돌려줍니다. consume body 절차가 항상 프로미스를 돌려주기 때문입니다. 예제 1에서 `body instanceof Promise`가 `true`였고, 값은 `then`으로 받아야 합니다. 이 프로미스는 본문이 JSON이 아니면 `SyntaxError`로 거부될 수 있습니다(예제 7).

</Callout>

<Callout type="misconception" title="본문은 여러 번 읽을 수 있다">

본문(body)이 있는 Response는 본문을 한 번만 읽을 수 있습니다. 읽기를 시작한 본문은 unusable이어서 다시 읽으려 하면 TypeError로 거부된 프로미스를 돌려받습니다. 예제 6에서 `text()` 뒤의 `json()`이 `catch TypeError`로 이어졌습니다. 두 번 필요하면 읽기 전에 `response.clone()`을 쓰거나, `text()`로 읽은 문자열을 `JSON.parse`로 파싱합니다.

</Callout>
