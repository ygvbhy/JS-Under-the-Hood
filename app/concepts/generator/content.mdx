제너레이터 함수를 불렀는데 왜 본문의 첫 줄도 실행되지 않을까요? 제너레이터 함수를 부르면 본문의 `console.log`는 찍히지 않고 객체 하나만 돌아옵니다. 이 페이지는 이 질문에서 출발해 제너레이터 객체가 어떤 상태로 시작하는지, `next`와 `yield`가 값을 어떻게 주고받는지, `return` 값이 어떤 결과로 나오고 `for...of`와 스프레드는 그 값을 어떻게 다루는지, 제너레이터로 이터러블을 만들 때 왜 한 번 소비하면 끝나는 객체가 생기는지, `return()`과 `throw()`가 멈춰 있던 지점에서 어떻게 재개되고 `break`로 나가도 `finally`가 실행되는 이유가 무엇인지, 값을 다른 이터러블에 어떻게 위임하는지, 제너레이터 함수에 `new`를 쓰면 왜 TypeError인지, 매개변수 기본값은 언제 평가되는지를 예제 열 개로 차례로 확인합니다. 제너레이터는 ECMAScript 언어의 동작이고, 예제의 출력은 Node.js의 `vm`에서 실행한 값이며 `console`은 호스트가 제공하는 API입니다. 이 페이지는 [실행 컨텍스트](/concepts/execution-context)에서 본 실행 컨텍스트 스택, [이터러블과 for...of](/concepts/iterable-for-of)에서 본 이터레이션 프로토콜과 `break`의 닫기 동작, [클로저](/concepts/closure)에서 본 함수가 끝나도 환경이 남을 수 있다는 점, [스프레드와 디스트럭처링](/concepts/spread-destructuring)에서 본 이터러블을 펼치는 방식을 전제합니다. `try...catch...finally` 문 자체와 `async`/`await`를 비롯한 비동기 처리는 별도 개념(작성 예정)입니다.

## 동작 원리

### 불러도 본문은 실행되지 않는다

일반 함수는 부르면 본문을 실행합니다. 제너레이터 함수는 다릅니다. 부르면 명세의 EvaluateGeneratorBody가 먼저 FunctionDeclarationInstantiation으로 매개변수를 바인딩하고 `var` 변수 같은 이름을 만듭니다. 본문의 문장은 아직 하나도 실행하지 않습니다. 그다음 제너레이터 객체를 만들어 상태를 suspended-start로 두고, GeneratorStart로 본문을 나중에 시작할 준비를 한 뒤 그 객체를 돌려줍니다. 제너레이터 객체의 상태는 suspended-start, suspended-yield, executing, completed 네 가지입니다.

이 호출 동안에도 일반 함수처럼 제너레이터 함수의 실행 컨텍스트가 [실행 컨텍스트 스택](/concepts/execution-context)에 올라가고, FunctionDeclarationInstantiation은 그 컨텍스트 안에서 일어납니다. GeneratorStart는 지금 실행 중인 그 컨텍스트를 제너레이터 객체에 기억시켜 두고, 호출이 끝나면 이 컨텍스트는 스택에서 빠집니다. 명세는 이렇게 빠진 컨텍스트를 버리지 않는다고 적습니다.

> When calleeContext is removed from the execution context stack in step 7 it must not be destroyed if it is suspended and retained for later resumption by an accessible Generator.

이 페이지는 이 컨텍스트를 제너레이터의 실행 컨텍스트(또는 본문 컨텍스트)라고 부르고, 시뮬레이터의 스택 그림에는 `talk 본문`처럼 함수 이름을 붙여 그립니다. 뒤에서 볼 `next`가 이 컨텍스트를 다시 스택에 올려 본문을 실행합니다.

예제 1에서 `count()`를 부르면 2번 줄의 `console.log('본문 시작')`이 아니라 `제너레이터 객체를 받음`이 먼저 찍힙니다. 본문은 `it.next()`를 부를 때 시작해 `yield 1`에서 멈추고, 호출한 쪽은 `1 false`를 받습니다. `본문 끝`은 찍히지 않습니다. 두 번째 `next`를 부르지 않았으므로 `yield 1` 뒤의 문장은 끝내 실행되지 않기 때문입니다.

매개변수는 본문과 달리 호출할 때 처리됩니다. 기본값 평가를 포함한 매개변수 처리는 FunctionDeclarationInstantiation이 하므로 제너레이터 객체를 돌려주기 전, 즉 호출하는 때에 일어납니다. 예제 10에서 `start()`를 부르면 `기본값 평가`가 먼저 찍히고, `본문 시작`은 `next`를 부른 뒤에야 찍힙니다.

### next와 yield는 값을 주고받는다

`it.next(v)`를 부르면 `%GeneratorPrototype%.next`가 받은 인수를 GeneratorResume에 넘깁니다.

> Return ? GeneratorResume(this value, value, empty).

GeneratorResume은 먼저 GeneratorValidate로 `this`가 제너레이터인지, 지금 실행 중이 아닌지 확인합니다. suspended-start나 suspended-yield이면 상태를 executing으로 바꾸고 제너레이터의 실행 컨텍스트를 [실행 컨텍스트 스택](/concepts/execution-context)의 맨 위에 올려 실행합니다. 본문이 `yield`에 닿으면 Yield 연산이 `{ value, done: false }` 모양의 결과 객체를 만들어 GeneratorYield에 넘기고, GeneratorYield가 상태를 suspended-yield로 바꿉니다. 제너레이터의 실행 컨텍스트는 스택에서 빠지고 호출한 쪽(명세상으로는 `next` 메서드의 실행 컨텍스트)이 다시 실행 중이 되어 그 결과를 받습니다. 멈춰 있는 동안에도 제너레이터의 실행 컨텍스트는 버려지지 않으므로 본문의 지역 변수 값이 다음 `next`까지 이어집니다(예제 2의 `a`, `b`). completed가 되면 비로소 버려도 됩니다.

값은 양쪽으로 오갑니다. `yield` 뒤에 쓴 식의 값은 바깥으로 나가 결과 객체의 `value`가 됩니다. `next(x)`의 인수 `x`는 안으로 들어가 멈춰 있던 `yield` 식의 값이 됩니다. 예제 2에서 `it.next('hi')`를 부르면 `var a = yield 'first'`의 `yield` 식이 `'hi'`가 되어 `a`에 대입되고 `a = hi`가 찍힙니다.

그러면 첫 `next`의 인수는 어디로 갈까요? 첫 `next`에서는 받아 줄 `yield`가 아직 없습니다. GeneratorStart는 본문을 시작하는 방식을 이렇게 정합니다.

> Set the code evaluation state of genContext such that when evaluation is resumed for that execution context, closure will be called with no arguments.

본문을 시작하는 클로저는 인수 없이 불리므로 `it.next('ignored')`의 `'ignored'`는 어디에도 쓰이지 않습니다. 예제 2의 출력에 `ignored`가 없는 이유입니다. 인수가 쓰이는 것은 `yield`에서 멈춘 제너레이터를 다시 시작하는 두 번째 `next`부터입니다.

### return 값과 completed

본문이 끝까지 실행되거나 `return`을 만나면 GeneratorStart의 단계가 상태를 completed로 바꾸고, `return`의 값(없으면 `undefined`)을 `value`로, `done`을 `true`로 한 결과 객체를 돌려줍니다. 예제 2의 `return 'end'`가 `end true`로 나온 것이 이 결과입니다. completed 상태는 되돌아가지 않습니다.

> Once a generator enters the completed state it never leaves it and its associated execution context is never resumed.

그래서 completed가 된 뒤에는 `next`를 몇 번 불러도 본문은 다시 실행되지 않고, GeneratorResume이 곧바로 결과를 정합니다.

> If state is completed, return CreateIteratorResultObject(undefined, true).

예제 2의 마지막 `it.next('again')`이 `undefined true`를 돌려주는 이유입니다. 인수 `'again'`을 받아 줄 본문이 더는 없습니다.

`return` 값은 `done: true` 결과의 `value`에만 실립니다. [이터러블과 for...of](/concepts/iterable-for-of)에서 본 반복 규칙에서 `done`이 `true`인 결과를 받으면 루프가 끝나고 `value`는 루프 변수에 넣지 않습니다. 스프레드도 `done`이 `true`가 되면 모으기를 마칩니다. 그래서 예제 3의 `for...of`와 `[...steps()]`는 `return 3`의 `3`을 받지 못하고, `next`를 직접 부른 마지막 결과에서만 `3 true`로 보입니다.

### 제너레이터로 이터러블 만들기

[이터러블과 for...of](/concepts/iterable-for-of)에서는 `Symbol.iterator` 메서드와 `next` 메서드를 가진 객체를 직접 만들었습니다. 제너레이터를 쓰면 이 메서드를 제너레이터 메서드로 쓸 수 있습니다. 예제 4의 `*[Symbol.iterator]()`는 [메서드 축약](/concepts/arrow-functions)과 [계산된 프로퍼티 이름](/concepts/property-keys)을 쓴 제너레이터 메서드입니다. 이 메서드를 부르면 본문이 아니라 제너레이터 객체가 돌아오고, 그 객체가 이터레이터입니다. 본문의 `yield i`가 `next`마다 값을 하나씩 내보냅니다. 메서드로 불리므로 본문의 `this`는 `range`입니다.

`range`를 스프레드로 두 번 펼친 예제 4의 처음 두 줄은 똑같이 `[1,2,3]`입니다. 스프레드가 펼칠 때마다 `range[Symbol.iterator]()`를 새로 불러 새 제너레이터 객체를 받기 때문입니다. `range`처럼 `Symbol.iterator` 메서드가 부를 때마다 새 이터레이터를 만드는 이터러블은 몇 번이든 돌 수 있습니다.

반면 세 번째 줄부터는 제너레이터 객체 `it` 하나를 다룹니다. `it[Symbol.iterator]() === it`가 `true`인 것은 제너레이터 객체가 프로토타입 체인으로 `%Iterator.prototype%`의 `Symbol.iterator` 메서드를 상속하기 때문입니다([프로토타입 체인](/concepts/prototype-chain)). 그 메서드의 본문은 이것뿐입니다.

> Return the this value.

제너레이터 객체는 자기 자신을 돌려주는 이터레이터이므로 이터러블로도 쓸 수 있고, 펼치면 `it` 자신이 이터레이터가 됩니다. 처음 `[...it]`은 끝까지 돌아 `[1,2,3]`을 만들지만 그 순간 `it`은 completed가 됩니다. 두 번째 `[...it]`은 `next`가 곧바로 `undefined true`를 돌려주어 `[]`입니다. 제너레이터 객체는 한 번 소비하면 끝이므로, 다시 돌고 싶으면 이터러블 쪽에서 새 제너레이터를 만들어야 합니다.

### return()과 throw(), finally, break

제너레이터 객체에는 `next` 말고도 `return`과 `throw` 메서드가 있고, 둘 다 GeneratorResumeAbrupt로 갑니다. 상태에 따라 세 갈래입니다.

먼저 아직 시작하지 않은 suspended-start일 때입니다.

> If state is suspended-start, then

이때는 상태를 completed로 바꾼 뒤, 아래의 이미 completed인 경우와 같은 갈래로 갑니다. 본문을 재개하지 않으므로 본문 안의 `finally` 블록도 실행되지 않습니다. 예제 5의 `early.return('시작 전')`이 `정리` 없이 `시작 전 true`를 돌려주는 이유입니다(이 페이지의 예제는 시작 전 `throw()`를 실행해 보이지 않습니다).

이미 completed인 제너레이터도 이 갈래를 탑니다. 본문을 재개하지 않고 `return(v)`이면 `value`가 `v`이고 `done`이 `true`인 결과를 곧바로 돌려주며, `throw(e)`이면 `e`를 호출한 쪽으로 던집니다. completed 뒤의 `next`가 `undefined`와 `true`를 돌려주는 것과 다른 점입니다. 예제 5의 마지막 `it.return('또')`는 `또 true`를, 예제 6의 마지막 `it.throw(new Error('또'))`는 예외를 그대로 던져 바깥의 `catch`가 `바깥에서 잡음: 또`를 찍습니다.

다음으로 `yield`에서 멈춘 suspended-yield일 때입니다. 상태를 executing으로 바꾸고 제너레이터의 실행 컨텍스트를 스택에 올려, 멈춰 있던 `yield` 지점에서 재개합니다. `next`는 거기서 값을 주어 재개하지만 `return()`은 그 자리에서 `return`이 일어난 것처럼, `throw()`는 그 자리에서 예외가 던져진 것처럼 재개합니다. 멈춘 `yield`가 `finally`가 있는 `try` 블록 안에 있으면, 본문을 빠져나가려는 이 흐름은 그 `finally` 블록을 실행하고 지나갑니다. `try...catch...finally` 문의 의미는 별도 개념(작성 예정)이고, 이 페이지는 빠져나갈 때 `finally` 블록이 실행된다는 결과만 씁니다. 예제 5에서 `it.return('중단')`을 부르면 `yield 'step 1'`에서 재개되어 `정리`가 찍힌 뒤 `중단 true`가 돌아옵니다. 그 뒤의 `next()`는 completed라서 `undefined true`입니다. 단, `finally` 블록 안에서 다시 `yield`하거나 `return`하면 `return()`의 결과가 인수와 `true`가 아닐 수 있고 제너레이터가 completed가 되지 않을 수도 있습니다. 이 경우는 이 페이지의 범위 밖입니다.

`throw()`는 같은 지점에서 예외로 재개됩니다. 예제 6에서 `it.throw(new Error('boom'))`은 `yield 'ready'` 자리에서 예외가 던져진 것처럼 재개하고, 본문의 `catch`가 이를 잡아 `잡음: boom`을 찍은 뒤 `yield 'recovered'`로 새 결과를 돌려줍니다. 명세에 따르면 본문이 예외를 잡지 못하면 GeneratorStart의 단계가 상태를 completed로 바꾸고 예외는 `throw()`를 부른 쪽으로 나갑니다. 이 경우는 이 페이지의 예제로 실행해 보이지 않습니다.

`for...of`에서 `break`로 나가는 경우도 같은 길을 탑니다. [이터러블과 for...of](/concepts/iterable-for-of)에서 본 대로 `break`는 IteratorClose를 통해 이터레이터의 `return` 메서드를 부릅니다. 제너레이터 객체에는 `return`이 있으므로 `return()`이 `yield` 지점에서 재개되어 `finally` 블록이 실행됩니다. 예제 7에서 `3`을 찍고 `break`하면 `finally`가 찍힌 뒤에야 `루프 뒤`가 찍힙니다.

### `yield*`로 위임하기

`yield*`는 뒤에 오는 이터러블에서 이터레이터를 얻고, 안쪽 `next`의 결과가 끝나지 않았으면 그 결과 객체를 그대로 바깥 `next`의 결과로 넘깁니다. 명세의 `yield*` 평가 단계는 이렇게 적습니다.

> Else, set received to Completion(GeneratorYield(innerResult)).

안쪽 이터레이터가 `done: true`를 돌려주면 위임이 끝나고, 그 결과는 바깥으로 나가지 않고 `value`가 `yield*` 식 전체의 값이 됩니다. 명세상 안쪽은 제너레이터에 한정되지 않고 이터러블이면 됩니다. 또 `yield*`는 값을 내보내기만 하지 않고, 위임하는 동안 바깥 `next`의 인수를 안쪽 `next`에 넘기며, 바깥에 부른 `return()`과 `throw()`는 안쪽 이터레이터에 그 메서드가 있으면 전달합니다. 예를 들어 위임 중에 바깥에 `return()`을 부르면 안쪽 제너레이터의 `finally` 블록이 실행됩니다. 이 페이지는 이 전달 동작을 예제로 다루지 않습니다.

예제 8에서 `outer`는 `o1`을 내보낸 뒤 `inner`에 위임합니다. `inner`가 내보낸 `i1`, `i2`는 `outer`를 도는 `for...of`에 그대로 전달됩니다. `inner`의 `return 'inner의 반환값'`은 위임을 끝내는 `done: true` 결과의 `value`이므로 `for...of`에는 전달되지 않고 `yield*` 식의 값이 되어 `r`에 들어갑니다. 그래서 `outer` 안에서 `yield* 식의 값: inner의 반환값`이 찍히고, 바깥에서 모은 `values`에는 `o1`, `i1`, `i2`, `o2`만 들어 있습니다. `values`에 `inner의 반환값`이 없는 것은 `for...of`가 버려서가 아니라, 안쪽의 `done: true` 결과를 `yield*`가 받아 식의 값으로 썼기 때문에 처음부터 바깥 `next`의 결과로 나오지 않았기 때문입니다.

### 생성자가 아니고, 실행 중에는 next를 부를 수 없다

`function*`로 만든 함수는 생성자로 쓸 수 없는 함수 객체입니다. `new gen()`처럼 쓰면 [new 연산자](/concepts/new-operator)가 대상이 생성자가 아니라고 보고 TypeError를 던집니다. 예제 9의 첫 `try`가 `new: TypeError`를 찍습니다.

또 하나의 TypeError는 GeneratorValidate에서 나옵니다. 상태가 executing인 제너레이터 객체에 `next`를 부르는 경우입니다(`return()`과 `throw()`도 같은 검사를 거치므로 실행 중에 부르면 TypeError입니다. 이 페이지의 예제는 `next`만 실행해 봅니다).

> If state is executing, throw a TypeError exception.

예제 9의 `selfCall`은 첫 `next`에서 `var me = yield`까지 실행하고 멈춥니다. 두 번째 호출 `it.next(it)`은 제너레이터 자신을 `yield` 식의 값으로 넣어 `me`가 됩니다. 이때 제너레이터는 executing 상태이므로 본문 안의 `me.next()`는 TypeError입니다. 이 호출은 이미 실행 중인 제너레이터를 같은 제너레이터가 다시 시작하려는 것이기 때문입니다.

### 이 페이지가 다루지 않는 것

async 제너레이터와 `for await...of`, 제너레이터로 비동기 흐름을 다루는 방식, `async`/`await`는 별도 개념(작성 예정)입니다. `try...catch...finally` 문 자체와 예외 처리도 별도 개념(작성 예정)이라, 이 페이지는 `finally` 블록이 실행되는지 여부만 다룹니다. `finally` 안에서 다시 `yield`하거나 `return`하는 경우, `GeneratorFunction` 생성자, Iterator helpers도 다루지 않습니다. 명세는 판마다 GeneratorResume 등의 서술 방식과 매개변수 이름이 다릅니다. 이 페이지는 ES2026판과 현재 초안에 똑같이 있는 문장만 인용하고, 링크는 현재 초안을 가리킵니다.

### 흔한 오해

<Callout type="misconception" title="제너레이터 함수를 부르면 첫 yield까지 실행된다">

제너레이터 함수를 부르면 본문은 한 줄도 실행되지 않고 suspended-start 상태의 제너레이터 객체가 돌아옵니다. 예제 1에서 `제너레이터 객체를 받음`이 `본문 시작`보다 먼저 찍혔습니다. 본문은 첫 `next`가 시작하고, 예제 10처럼 매개변수 처리(기본값 평가 등)는 호출하는 때 일어납니다.

</Callout>

<Callout type="misconception" title="첫 next의 인수가 첫 yield의 값이 된다">

`next(x)`의 인수는 멈춰 있던 `yield` 식의 값이 되는데, 첫 `next`에는 멈춘 `yield`가 없고 본문이 인수 없이 시작합니다. 예제 2의 `it.next('ignored')`에서 `ignored`는 어디에도 쓰이지 않았고, `a`에는 두 번째 호출의 `hi`가 들어갔습니다. 첫 `yield 'first'`의 `first`는 바깥으로 나가는 값이고, 그 `yield` 식 자체의 값은 다음 `next`의 인수입니다.

</Callout>

<Callout type="misconception" title="for...of도 return 값을 준다">

`return` 값은 <code>{"done: true"}</code> 결과의 `value`에 실리는데, `for...of`와 스프레드는 `done`이 `true`인 결과의 `value`를 쓰지 않습니다. 예제 3의 `[...steps()]`는 `[1,2]`이고 `3`은 `next`를 직접 부른 결과에서만 보였습니다. 예제 8에서도 `inner`의 `return` 값은 바깥 `for...of`가 아니라 `yield*` 식의 값으로 `outer` 안에 전달되었습니다.

</Callout>

<Callout type="misconception" title="제너레이터 객체는 몇 번이든 다시 돌 수 있다">

몇 번이든 도는 것은 `range`처럼 부를 때마다 새 이터레이터를 만드는 이터러블이고, 제너레이터 객체 자체는 아닙니다. `range`는 펼칠 때마다 `Symbol.iterator` 메서드로 새 제너레이터 객체를 만들지만, 제너레이터 객체의 `Symbol.iterator`는 자기 자신을 돌려줍니다. 예제 4에서 `it`은 한 번 끝까지 돌며 completed가 되었고, completed는 되돌아가지 않으므로 두 번째 `[...it]`은 `[]`였습니다.

</Callout>
